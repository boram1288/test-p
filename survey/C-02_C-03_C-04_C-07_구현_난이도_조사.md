# C-02·C-03·C-04·C-07 구현 난이도 조사

- 조사일: 2026-08-29
- 상태: 구현 난이도 조사, 최종 구조 선택 전
- 조사 대상: C-02, C-03, C-04, C-07

## 1. 조사 목적

이 문서는 [C-02·C-03·C-04·C-07이 정의된 설계 공간 문서](../docs-align/문제3_virtio-blk_공용저장_암호화_설계공간.md)를 기준으로, 각 후보를 실제로 만들기 쉬운지 어려운지 판단한다.

다음 세 종류의 자료를 구분해서 확인했다.

- 공식 문서와 원본 코드: 기존 기능이 실제로 무엇을 제공하는지 확인
- 공개 구현 사례: 비슷한 구조가 실제로 사용되거나 구현된 범위 확인
- 논문: 성능, 변조 확인, 최신 상태 확인과 비정상 종료 복구에서 알려진 어려움 확인

공개 사례가 현재 조건과 비슷하더라도 그대로 쓸 수 있다고 간주하지 않았다. 특히 “TEE가 키를 감싸 보관하다가 Linux에 평문 키를 풀어 주는 방식”은 이번 조건을 만족하지 않는다.

## 2. 결론

### 2.1 한눈에 보는 판정

| 후보 | 자료 경로만 확인하는 최소 시제품 | 현재 보안·복구 조건을 넣은 시제품 | 제품 수준 | 핵심 판단 |
| --- | --- | --- | --- | --- |
| C-02: pVM 사용자 영역의 마운트형 암호 파일시스템 | 보통 | 어려움 | 매우 어려움 | 기존 FUSE 암호 파일시스템을 가장 많이 참고할 수 있고 커널을 바꾸지 않는다. 다만 파일 이름, 일반 파일 동작과 RPMB 복구는 새로 연결해야 한다. |
| C-03: pVM 커널 파일 계층의 TEE 연동 | 어려움 | 매우 어려움 | 매우 어려움 | fscrypt는 성숙했지만 키 사용 방식과 디스크 형식이 현재 조건과 맞지 않는다. 파일 내용·이름·인증값 처리를 함께 바꿔야 한다. |
| C-04: pVM 커널의 전용 Device Mapper 대상 | 어려움. 수정한 dm-crypt 방식은 보통~어려움 | 매우 어려움 | 매우 어려움 | Device Mapper의 요청 처리 기능은 쓸 수 있지만, TEE 비동기 호출, 인증값, 위치표, RPMB 확정과 복구는 새로 만들어야 한다. |
| C-07: EL2가 연결하는 보호된 virtio-blk 경계 | 매우 어려움 | 최고 난이도 | 최고 난이도 | 표준 virtio-blk에 없는 보호 규약이 필요하고 pVM·EL2·TEE·Host를 함께 바꿔야 한다. 작은 EL2 원칙과도 충돌한다. |

여기서 “자료 경로만 확인하는 최소 시제품”은 한 pVM에서 제한된 읽기·쓰기를 TEE 암복호화와 연결해 보는 수준이다. Host 변조, 이전 상태 되돌리기, 모든 중단 시점의 복구가 빠진 결과이므로 구조 선택의 최종 근거로 사용할 수 없다.

현재 고정 조건을 모두 적용해 난이도를 한 칸으로만 표시하면 다음과 같다.

- C-02: **어려움**, 네 후보 중 상대적으로 가장 구현하기 쉬움
- C-03: **매우 어려움**, 파일 계층과 디스크 형식 변경 위험이 큼
- C-04: **매우 어려움**, 안전한 블록 저장과 복구 기능을 새로 만드는 범위가 큼
- C-07: **매우 어려움 중에서도 가장 어려움**, 여러 실행 영역과 새 virtio 규약을 함께 검증해야 함

C-03과 C-04는 전체 난이도가 모두 매우 높아 단순 순위를 정하지 않았다. C-03은 기존 파일시스템 경로를 깊게 고치는 위험이 더 크고, C-04는 인증된 블록 위치표와 비정상 종료 복구를 새로 만드는 양이 더 크다.

### 2.2 현재 조사에서 찾지 못한 것

이번 조사 범위에서는 다음 조건을 모두 만족하는 공개 구현을 찾지 못했다.

- 평문 키와 키를 만들 수 있는 비밀값이 항상 TEE 안에만 있음
- pVM이 Host 제공 virtio-blk를 직접 사용함
- Host가 보는 버퍼와 UFS에는 암호문만 있음
- 파일 또는 블록의 변조와 이전 상태 되돌리기를 알아냄
- RPMB를 최신 상태의 기준으로 사용함
- 비정상 종료 뒤 이전 또는 새 정상 상태로 복구함

따라서 모든 후보에는 새 구현과 검증이 필요하다. 기존 사례는 일부 기능을 재사용하거나 위험을 확인하는 근거다.

## 3. 고정 조건과 판정 기준

### 3.1 고정 조건

이 문서는 다음 조건을 바꾸지 않는다.

1. 물리 저장장치는 비신뢰 Host가 제공한다.
2. pVM은 Host가 제공한 논리 블록 장치를 virtio-blk로 연결해 직접 마운트한다.
3. 평문 키와 키를 만들 수 있는 비밀값은 TEE 밖으로 내보내지 않는다.
4. Host가 읽을 수 있는 저장 경로와 virtio-blk 공유 버퍼에는 암호문만 둔다.
5. EL2는 작게 유지하며 대용량 암호 처리나 파일시스템을 맡지 않는 것이 기본 원칙이다.
6. TEE는 RPMB를 제공한다고 가정한다.
7. RPMB에는 큰 자료가 아니라 최신 버전과 `root_hash` 같은 작은 확인 상태만 둔다.
8. Host가 자료를 바꾸거나 이전 상태로 되돌리면 이를 알아내야 한다.
9. 같은 Workload 저장 공간에는 한 시점에 하나의 쓰기 주체만 둔다.

[시스템 개요](../docs/01_시스템_개요.md)는 기본적으로 RPMB를 사용하지 않는다고 적고 있다. 이 문서는 사용자가 문제 3에만 지정한 RPMB 가정을 따른다. [설계 범위와 모듈](../docs/02_설계_범위_모듈.md)의 M-09 (DMA/S2MPU Isolation Controller), M-10 (Secure OS Adapter), M-11 (Secure Persistent Storage) 책임은 그대로 사용한다.

RPMB가 있어도 Host가 지운 암호문을 복구할 수는 없다. 이 구조가 목표로 하는 것은 기밀성, 변조 확인과 이전 상태 되돌리기 확인이다. 악의적인 Host가 저장을 거부하거나 자료를 삭제했을 때의 가용성은 보장하지 못한다.

### 3.2 난이도 등급

| 등급 | 이 문서에서의 뜻 |
| --- | --- |
| 쉬움 | 이미 검증된 기능을 설정하거나 작은 연결부만 추가하면 됨 |
| 보통 | 기존 기능을 많이 쓸 수 있지만 후보 전용 구성요소와 시험이 필요함 |
| 어려움 | 커널 또는 저장 경로의 중요한 부분을 새로 만들고 여러 오류 경로를 검증해야 함 |
| 매우 어려움 | 여러 실행 영역이나 디스크 형식을 함께 바꾸고, 보안·복구·성능을 처음부터 함께 검증해야 함 |
| 최고 난이도 | 매우 어려움에 더해 EL2나 장치 규약처럼 장애 영향이 큰 플랫폼 핵심부까지 변경함 |

등급은 개발 기간을 수치로 예측한 결과가 아니다. 목표 Linux와 TEE 구현, M-10 완성도, 지원할 파일 기능과 허용 성능이 정해지지 않았기 때문이다.

### 3.3 비교 항목

다음 항목을 후보마다 같은 기준으로 확인했다.

- 기존 코드와 시험 자료를 얼마나 재사용할 수 있는가
- pVM 사용자 영역, pVM 커널, EL2, TEE, Host 중 몇 곳을 바꾸는가

- 비정상 종료, 메모리 부족, TEE 중단과 Host의 거짓 응답을 어떻게 처리하는가
- 오류가 발생했을 때 영향을 받는 범위가 파일시스템 프로그램, pVM 커널 또는 EL2 중 어디까지인가
- 현재 조건과 가까운 공개 구현과 논문이 있는가

## 5. C-02: pVM 사용자 영역의 마운트형 암호 파일시스템

### 5.1 판정

- 자료 경로만 확인하는 최소 시제품: **보통**
- 현재 보안·복구 조건을 넣은 시제품: **어려움**
- 제품 수준: **매우 어려움**

C-02는 네 후보 중 첫 시제품을 가장 빨리 만들 가능성이 높다. pVM 커널, EL2와 virtio-blk 규격을 바꾸지 않고 사용자 영역에서 기능을 고칠 수 있기 때문이다. 그러나 기존 FUSE 암호 파일시스템에 TEE 호출만 붙이면 끝나는 것은 아니다. RPMB 최신 상태 확인과 모든 파일 동작의 중단 복구는 기존 사례가 제공하지 않는다.

### 5.2 재사용할 수 있는 부분

- [Linux FUSE 공식 문서](https://docs.kernel.org/filesystems/fuse/)는 커널과 사용자 영역 파일시스템 사이의 요청 방식을 제공한다.
- [libfuse](https://github.com/libfuse/libfuse)는 높은 수준의 동기 방식과 낮은 수준의 비동기 방식, 통과형 파일시스템 예제를 제공한다.
- [gocryptfs](https://github.com/rfjakob/gocryptfs)는 FUSE 기반 암호 파일시스템의 파일 조각, 파일 이름, 긴 이름, 희소 파일과 시험 코드를 제공한다. [gocryptfs 암호 형식](https://github.com/rfjakob/gocryptfs-website/blob/master/docs/forward_mode_crypto.md)은 파일 식별자와 조각 번호를 인증 자료에 넣는 구체적인 사례다.
- [securefs 설계 문서](https://github.com/netheril96/securefs/blob/master/docs/design.md)도 파일별 인증 암호화와 이름 암호화의 공개 구현 사례다.
- [OP-TEE client](https://github.com/OP-TEE/optee_client)의 libteec를 통해 사용자 영역에서 TEE를 호출할 수 있다.

FUSE 자체는 키 위치를 정하지 않는다. gocryptfs와 securefs의 키가 사용자 영역에 있다는 사실은 해당 구현의 선택이다. C-02는 파일 처리 부분을 참고하되 암호 연산과 평문 키 사용을 TEE로 옮겨야 한다.

### 5.3 새로 만들어야 하는 부분

| 항목 | 필요한 구현 | 난이도에 미치는 영향 |
| --- | --- | --- |
| TEE 암호 연결 | 기존 암호 함수 대신 TEE 키 손잡이, 암호 TA와 호출 명령 사용 | 보통 |
| 동시 요청 | FUSE 요청 대기열, 여러 TEE 세션, 취소, 시간 제한과 같은 파일의 쓰기 순서 | 어려움 |
| 버퍼 | FUSE 요청 버퍼, TEE 공유 버퍼와 아래 파일 쓰기 버퍼의 수명 관리 | 어려움 |
| 파일 이름 | 경로의 각 이름을 TEE에서 처리하고 긴 이름, 이름 충돌, `rename`과 `readdir` 처리 | 어려움 |
| 인증 | Workload, `storage_id`, 파일 식별자, 조각 번호와 버전을 인증값에 결합 | 어려움 |
| 최신성 | 파일별 자료 목록과 최상위 `root_hash`를 RPMB 상태에 연결 | 매우 어려움 |
| 중단 복구 | 새판 쓰기, `fsync`, 원자적 이름 전환, RPMB 확정과 미확정 자료 회수 | 매우 어려움 |
| 제품 호환성 | `mmap`, 희소 파일, `truncate`, 하드 링크, 확장 속성(xattr), 잠금과 동시 접근 시험 | 매우 어려움 |

libfuse의 낮은 수준 방식은 요청을 받은 뒤 나중에 응답할 수 있으므로 TEE 작업 실행 흐름을 붙이기 쉽다. 반면 `TEEC_InvokeCommand()`는 호출한 실행 흐름이 결과를 기다린다. 여러 요청을 처리하려면 작업 실행 흐름 묶음, 여러 세션 또는 TA의 여러 세션 처리와 요청 취소 연결을 별도로 만들어야 한다.

FUSE의 직접 통과 기능은 아래 파일을 커널이 바로 읽고 쓰도록 해 복사를 줄인다. C-02는 중간에서 자료를 암호화해야 하므로 보호 대상 자료 경로에 이 기능을 그대로 적용할 수 없다. [FUSE passthrough 공식 문서](https://docs.kernel.org/filesystems/fuse/fuse-passthrough.html)

### 5.4 사례와 논문에서 확인된 위험

- gocryptfs는 파일 조각의 변조를 확인하지만 [gocryptfs 위협 범위](https://github.com/rfjakob/gocryptfs-website/blob/master/docs/threat_model.md)는 암호문 파일 이름 변경과 파일 바꿔치기를 모두 막는 범위가 아님을 밝힌다.
- [securefs 프로젝트](https://github.com/netheril96/securefs)는 비정상 종료 때 디렉터리 정보가 손상될 수 있고, 같은 위치의 예전 암호문으로 되돌리는 공격을 알아내지 못할 수 있다고 제한을 밝힌다.
- [To FUSE or Not to FUSE, FAST 2017](https://www.usenix.org/conference/fast17/technical-sessions/presentation/vangoor/)은 FUSE의 성능 부담이 작업 종류와 저장장치에 따라 크게 달라짐을 측정했다. 논문의 수치를 현재 장치 예상값으로 옮길 수는 없지만, 작은 요청과 이름 조회가 많은 시험을 반드시 해야 한다는 근거가 된다.
- [eCryptfs 성능 분석, Linux Symposium 2012](https://www.kernel.org/doc/ols/2012/ols2012-wang.pdf)은 겹쳐 올린 암호 파일시스템에서 평문과 암호문 저장 공간, 자료 복사와 캐시가 추가될 수 있음을 실제 구현으로 설명한다.

RPMB를 추가해도 위 문제가 자동으로 해결되지는 않는다. RPMB의 작은 최신 상태와 UFS에 있는 파일별 자료 목록을 안전하게 연결하는 확정 절차가 필요하다.

### 5.5 최소 확인 시험

1. `open`, `create`, `read`, `write`, `fsync`, `rename`, `unlink`만 지원하는 작은 FUSE 파일시스템을 만든다.
2. 4 KiB, 64 KiB, 256 KiB와 1 MiB 단위로 TEE 호출 지연, 처리량, CPU 사용과 복사 횟수를 잰다. 크기는 사전에 정답으로 고정하지 않고 측정값으로 정한다.
3. 파일 이름 조회가 많은 작업과 큰 순차 파일 작업을 따로 측정한다.
4. 암호문, 인증값과 파일별 버전을 Host가 바꿨을 때 읽기가 실패하는지 확인한다.
5. 아래 파일 `fsync` 전후, 이름 전환 전후와 RPMB 확정 전후에 강제로 중단하고 복구 결과를 확인한다.
6. 이 시험이 통과한 뒤에만 `mmap`, 하드 링크, 희소 파일, 확장 속성과 여러 Workload를 추가한다.

## 6. C-03: pVM 커널 파일 계층의 TEE 연동

### 6.1 판정

- 자료 경로만 확인하는 최소 시제품: **어려움**
- 현재 보안·복구 조건을 넣은 시제품: **매우 어려움**
- 제품 수준: **매우 어려움**

C-03은 “fscrypt에 TEE 호출 하나를 추가하는 일”이 아니다. 현재 fscrypt의 키 파생, 파일 내용, 파일 이름과 디스크 배치는 평문 키를 커널 암호 기능이나 저장 암호 장치가 사용하는 방식에 맞춰져 있다. 현재 조건은 모든 비밀값 사용과 인증 암호화를 TEE에 두므로 여러 부분을 함께 바꿔야 한다.

### 6.2 재사용할 수 있는 부분

- [Linux fscrypt 공식 문서](https://docs.kernel.org/next/filesystems/fscrypt.html)에 따르면 fscrypt는 ext4, F2FS, UBIFS와 CephFS에 연결돼 있다.
- 디렉터리별 정책, 파일별 비밀값, 내용 위치에 따른 암호 처리, 파일 이름과 긴 이름 처리, `rename`, 링크와 키 없는 조회 규칙을 참고할 수 있다.
- [Android 파일 기반 암호화](https://source.android.com/docs/security/features/encryption/file-based)는 fscrypt가 실제 제품에 사용되는 사례다.
- [Linux TEE 커널 Driver API](https://docs.kernel.org/driver-api/tee.html)는 커널 Client(호출 구성요소)가 TA를 호출하는 규약을 제공한다. [OP-TEE RNG 커널 드라이버](https://github.com/torvalds/linux/blob/master/drivers/char/hw_random/optee-rng.c)는 커널에서 공유 메모리와 `tee_client_invoke_func()`를 사용하는 원본 코드 사례다.
- fscrypt의 시험에는 Linux 파일시스템 표준 시험 모음인 xfstests를 활용할 수 있다.

이 기능은 파일 동작과 VFS 연결을 이해하는 데 유용하지만, 현재 C-03의 암호 처리부를 그대로 제공하지는 않는다.

### 6.3 표준 fscrypt를 그대로 쓸 수 없는 이유

첫째, 키 조건이 다르다.

- 일반 fscrypt는 기준 키와 파생 키를 커널이 사용한다.
- 하드웨어로 감싼 키(`hardware-wrapped keys`)를 써도 파일 내용 키만 소프트웨어에서 숨길 수 있다.
- 파일 이름 키와 다른 보조 키를 만들기 위한 소프트웨어용 비밀값(`software secret`)은 커널에 남는다.

이 제한은 [Linux fscrypt의 하드웨어로 감싼 키 설명](https://docs.kernel.org/next/filesystems/fscrypt.html#hardware-wrapped-keys)과 [Android의 하드웨어로 감싼 키 설명](https://source.android.com/docs/security/features/encryption/hw-wrapped-keys)에 명시돼 있다. 따라서 파일 이름용 비밀값까지 TEE 밖으로 내보내지 않는 조건에서는 표준 방식을 사용할 수 없다.

둘째, 인증값을 넣을 자리가 없다.

[fscrypt 지원 암호 방식](https://docs.kernel.org/next/filesystems/fscrypt.html#supported-modes)은 암호문 길이가 늘어나는 문제 때문에 인증 암호화를 현재 지원하지 않는다고 밝힌다. 현재 조건은 Host의 변조를 알아내야 하므로 내용 조각마다 인증값과 버전이 필요하다. 이를 별도 파일, 확장 속성, 파일시스템 내부 블록 또는 새로운 파일 형식 중 어디에 둘지 정하고 자료와 함께 갱신해야 한다.

셋째, fscrypt의 위협 범위가 더 좁다.

fscrypt 공식 문서는 저장장치의 한 시점 유출에 대한 내용과 이름의 기밀성을 주된 범위로 두며, 공격자가 저장 내용을 바꾼 뒤 다시 접근하는 경우 진위를 보장하지 않는다고 설명한다. RPMB 최신성, Host 변조와 이전 상태 되돌리기 확인은 별도 기능이다.

### 6.4 새로 만들어야 하는 부분

| 항목 | 필요한 구현 | 부담 |
| --- | --- | --- |
| 정책 | TEE 키 손잡이와 Workload·`storage_id` 결합값을 표현하는 새 정책 | 어려움 |
| 키 설정 | 커널의 키 파생과 파일별 평문 키 생성을 TEE 명령으로 교체 | 매우 어려움 |
| 내용 처리 | 쓰기용 별도 페이지, TEE 공유 버퍼, 대기 요청과 오류 완료 처리 | 매우 어려움 |
| 파일 이름 | 조회·생성·이름 변경 중 TEE 호출, 이름 길이와 디렉터리 검색 유지 | 매우 어려움 |
| 인증값 | 내용 조각마다 늘어나는 인증값을 저장할 디스크 형식 | 매우 어려움 |
| 직접 입출력 | `O_DIRECT`, `mmap`, 페이지 캐시와 TEE 완료 시점 연결 | 매우 어려움 |
| 복구 | 파일시스템 기록, 파일 새판과 RPMB 확정 순서 연결 | 매우 어려움 |
| 유지보수 | 목표 커널 갱신마다 fscrypt와 ext4 또는 F2FS 변경 재검증 | 매우 어려움 |

현재 파일 이름 조회는 즉시 암호 결과가 있어야 디렉터리 검색을 계속할 수 있다. 파일 내용 처리도 읽기 완료와 쓰기용 별도 페이지에 직접 연결돼 있다. TEE 완료를 기다리는 동안 커널 파일 경로 전체를 막지 않으려면 작업 대기열, 요청 상태, 공유 버퍼 수명, 취소, 시간 제한과 오류 변환을 새로 넣어야 한다.

### 6.5 사례와 논문에서 확인된 위험

- Android의 fscrypt 제품 사례는 파일 동작의 성숙도를 보여 주지만 현재의 엄격한 키 위치와 인증·최신성 조건을 만족하는 사례는 아니다.
- Android의 제조사 전용 `FSCRYPT_MODE_PRIVATE` 사례는 제조사별 구현이 공통 커널의 디스크 형식과 다를 수 있어 장기 호환 부담이 생기는 예다. Android 11 이후 출시 장치에서는 이 방식이 허용되지 않는다. [Android 암호 방식 선택](https://source.android.com/docs/security/features/encryption/file-based#select-encryption-modes)
- [OP-TEE secure storage](https://optee.readthedocs.io/en/3.19.0/architecture/secure_storage.html)는 작은 보안 저장 객체를 새 위치에 쓴 뒤 바꾸는 방식과 RPMB 사용의 참고가 된다. 이 구현을 ext4 또는 F2FS 전체에 바로 적용할 수는 없다.
- [SPEICHER, FAST 2019](https://www.usenix.org/conference/fast19/presentation/bailleu)는 비신뢰 저장장치에서 인증 암호화만으로 최신성이 생기지 않으며 중단, 재부팅과 이전 상태 되돌리기를 별도로 설계해야 함을 보여 준다.

### 6.6 최소 확인 시험

1. 목표 파일시스템 하나와 목표 커널 버전 하나를 먼저 고정한다.
2. 파일 내용 한 조각을 TEE에서 처리하고 읽기 완료와 쓰기용 별도 페이지가 정상 동작하는지 확인한다.
3. 파일 이름 하나를 TEE에서 처리해 조회, 생성과 이름 변경 경로가 막히지 않는지 확인한다.
4. 인증값을 둘 위치를 하나 선택해 자료와 함께 갱신할 수 있는지 확인한다.
5. `fsync`와 파일시스템 기록 완료 뒤 RPMB를 갱신하는 순서를 중단 시험으로 검증한다.
6. 위 네 가지가 각각 성립하지 않으면 전체 C-03 구현에 들어가지 않는다.

## 7. C-04: pVM 커널의 전용 Device Mapper 대상

### 7.1 판정

- 전용 Device Mapper 대상의 자료 경로 시제품: **어려움**
- 수정한 dm-crypt를 이용한 자료 경로 시제품: **보통~어려움**
- 인증값·RPMB·복구를 포함한 시제품: **매우 어려움**
- 제품 수준: **매우 어려움**

수정한 dm-crypt 방식은 요청 나누기, 작업 대기열과 메모리 부족 처리를 재사용할 수 있어 첫 성능 시험에는 유리하다. 그러나 dm-crypt와 dm-integrity는 최신 버전, 위치표, RPMB 확정과 전체 복구를 제공하지 않는다. 전체 조건을 넣으면 전용 대상과 수정한 dm-crypt의 총난이도 차이는 작아진다.

### 7.2 재사용할 수 있는 부분

- [Linux Device Mapper 공식 문서](https://docs.kernel.org/admin-guide/device-mapper/index.html)는 파일시스템 아래에 블록 변환 대상을 쌓는 기존 기능을 제공한다.
- [dm-crypt 공식 문서](https://docs.kernel.org/admin-guide/device-mapper/dm-crypt.html)와 [dm-crypt 원본 코드](https://github.com/torvalds/linux/blob/master/drivers/md/dm-crypt.c)는 블록 요청 나누기, 작업 대기열, 비동기 암호 완료와 메모리 묶음 처리를 제공한다.
- [dm-integrity 공식 문서](https://docs.kernel.org/admin-guide/device-mapper/dm-integrity.html)는 자료와 블록별 인증값을 함께 저장하고 기록장을 사용해 둘의 중단 일관성을 유지하는 기능을 제공한다.
- [Linux TEE 커널 Driver API](https://docs.kernel.org/driver-api/tee.html)는 커널 Client(호출 구성요소)가 TA를 호출할 수 있게 한다.
- [Linux 저장장치 FLUSH·FUA 설명](https://docs.kernel.org/block/writeback_cache_control.html)은 아래 장치의 기록 완료 규약을 확인하는 기준이다.

`dm-integrity`를 사용해도 이전의 정상 암호문과 인증값을 함께 되돌리는 공격은 막지 못한다. 최신 버전과 `root_hash`는 RPMB에 두고 별도 위치표와 연결해야 한다.

### 7.3 새로 만들어야 하는 부분

| 항목 | 전용 대상 | 수정한 dm-crypt |
| --- | --- | --- |
| 블록 요청 수신과 완료 | Device Mapper 기능 일부 재사용, 대상 처리는 새로 구현 | 기존 처리 대부분 재사용 가능 |
| 요청 나누기와 작업 대기열 | 새 구현 비중이 큼 | 기존 기능 재사용 가능 |
| TEE 세션과 키 손잡이 | 새 구현 | 새 TEE Crypto API 제공자 또는 dm-crypt 변경 |
| 비동기 TEE 완료 | 새 작업 대기열과 완료 연결 | 기존 암호 완료 틀에 TEE 실행 흐름을 연결 |
| 평문·암호문 버퍼 분리 | 새 구현 | 새 구현 |
| 블록별 인증값 | 새 구현 또는 dm-integrity 연결 | dm-integrity 일부 재사용 |
| Workload·저장 공간·논리 블록 결합 | 새 구현 | 표준 dm-crypt 요청 정보로 부족하므로 새 구현 |
| 버전별 위치표와 `root_hash` | 새 구현 | 새 구현 |
| RPMB 확정과 중단 복구 | 새 구현 | 새 구현 |

Device Mapper의 블록 요청(`bio`)은 여러 메모리 페이지로 나뉠 수 있고 TEE가 바로 쓸 수 있는 연속 공간이라는 보장이 없다. 다음 두 버퍼를 분리해야 한다.

- Host에 공유하지 않는 pVM 평문 버퍼
- virtio-blk에 넘기는 Host 공유 암호문 버퍼

매 요청마다 공유 메모리를 새로 만들지 않고 고정 크기의 버퍼 묶음을 미리 만들어 재사용하는 방법을 우선 시험해야 한다. 버퍼를 돌려주기 전에 평문을 지우고, 메모리가 부족할 때 요청을 줄이거나 안전하게 실패시키는 규칙도 필요하다.

### 7.4 가장 어려운 구현 부분

#### 비동기 TEE 호출

Device Mapper의 요청 처리 함수에서 TEE 완료를 그대로 기다리면 블록 요청 처리가 막힐 수 있다. 요청을 별도 작업 대기열로 옮기고, 여러 연속 블록을 한 번에 TEE로 보낸 뒤, TEE 완료와 아래 장치 완료를 차례로 원래 요청에 연결해야 한다.

수정한 dm-crypt는 Linux Crypto API의 비동기 완료 형식을 활용할 수 있다. 그러나 Linux TEE 호출이 이 형식의 암호 제공자를 바로 제공하는 것은 아니다. TEE 요청 대기열, 동시에 처리할 수 있는 요청 수, 작업 실행 흐름, 취소, 장치 제거와 세션 재연결을 만들어야 한다.

#### 인증값과 최신 위치표

TEE의 인증 암호화에는 적어도 다음 값을 함께 넣어야 한다.

```text
stable_workload_id
storage_id
writer_generation
논리 블록 번호
자료 버전
암호 방식 버전
```

UFS에는 암호문, 인증값과 버전별 위치표를 두고 RPMB에는 최신 버전과 `root_hash`를 둔다. Host가 다른 블록, 다른 Workload 또는 과거 위치표로 바꾸면 확인에 실패해야 한다.

#### FLUSH와 RPMB 확정

상위 `FLUSH`는 다음 순서가 끝난 뒤에만 성공해야 한다.

1. 앞선 TEE 암호 요청 완료
2. 암호문과 인증값 기록 완료
3. 새 위치표 기록 완료
4. 아래 장치의 `FLUSH` 또는 FUA 완료
5. TEE가 RPMB의 최신 버전과 `root_hash` 확정
6. 상위 파일시스템에 `FLUSH` 완료 반환

RPMB 확정 전 중단은 이전 버전을 사용하고, 확정 뒤 중단은 새 버전을 사용해야 한다. 이전 위치표와 블록은 RPMB 확정 전까지 회수하면 안 된다.

### 7.5 사례와 논문에서 확인된 위험

- [STMicroelectronics의 OP-TEE Trusted Key와 dm-crypt 사례](https://wiki.st.com/stm32mpu/wiki/How_to_encrypt_a_disk_with_dm-crypt)의 일반 절차는 TEE가 감싼 키를 풀어 dm-crypt가 사용하게 한다. 같은 문서의 선택적 `shared key mode`는 평문 키를 CPU에 주지 않고 SAES와 CRYPT 하드웨어 사이에서 전달한다. [TI의 OP-TEE fTPM·dm-crypt 사례](https://software-dl.ti.com/processor-sdk-linux/esd/AM62X/latest/exports/docs/linux/Foundational_Components/System_Security/Filesystem_Encryption.html)는 fTPM으로 키와 부팅 상태를 보호하고 Linux dm-crypt로 자료를 처리한다. 어느 방식도 C-04처럼 각 블록 묶음의 암복호화를 TEE의 TA에 맡기는 직접 사례는 아니다.
- [MlsDisk, FAST 2026](https://www.usenix.org/system/files/fast26-xu.pdf)은 비신뢰 Host 저장장치 위의 보안 가상 디스크와 Linux 연결부를 실제로 구현했다. 논문과 [공개 구현 자료](https://github.com/asterinas/fast26-artifact-evaluation)는 최신성·복구·동기화를 제공하는 블록 저장 계층이 큰 작업임을 보여 준다. MlsDisk는 보호 실행 환경과 키 배치가 C-04와 달라 그대로 재사용할 수 없다.
- [AtomicDisk, FAST 2025](https://www.usenix.org/conference/fast25/presentation/tian-hongliang)는 `sync` 이전의 임시 기록과 확정된 기록을 구분하지 않으면 보안 저장장치에 정상으로 보이는 중간 상태가 남을 수 있음을 보였다. C-04도 `FLUSH`, UFS 기록과 RPMB 확정을 명시적으로 연결해야 한다.
- [OP-TEE secure storage](https://optee.readthedocs.io/en/3.19.0/architecture/secure_storage.html)는 REE 파일 저장과 RPMB 저장을 제공하지만, pVM 대용량 블록 장치를 직접 제공하는 기능은 아니다.

### 7.6 최소 확인 시험

1. 수정한 dm-crypt와 TEE 암호 제공자 또는 작은 전용 대상을 이용해 암복호화 경로를 먼저 만든다.
2. 4 KiB 단일 요청과 여러 크기의 묶음 요청을 비교해 TEE 전환, 복사와 동시 요청 한도를 잰다.
3. dm-integrity를 연결하거나 고정 인증값 영역을 만들어 변조 확인을 시험한다.
4. 버전별 위치표와 RPMB 확정 관리자를 별도로 붙인다.
5. 암호문, 인증값, 위치표, UFS `FLUSH`와 RPMB 확정 전후의 모든 중단 지점을 시험한다.
6. Host가 완료를 늦추거나 중복 완료, 잘못된 블록과 이전 자료를 반환할 때 안전하게 실패하는지 확인한다.

첫 네 단계에서 dm-crypt 변경이 최신 위치표 관리와 맞지 않는다고 확인되면 전용 Device Mapper 대상으로 옮긴다. 이 시제품 순서는 구조를 미리 결정한다는 뜻이 아니라, 재사용 가능한 부분과 새로 만들 부분을 빨리 구분하기 위한 것이다.

## 8. C-07: EL2가 연결하는 보호된 virtio-blk 경계

### 8.1 판정

- 제한된 자료 경로 시제품: **매우 어려움**
- 현재 보안·복구 조건을 넣은 시제품: **최고 난이도**
- pVM의 표준 virtio-blk 드라이버까지 그대로 유지하는 시제품: **최고 난이도**
- 현재 보안·복구 조건을 넣은 제품: **최고 난이도**

C-07은 기존 기능을 단순히 연결하는 수준이 아니다. pVM의 비공개 평문 버퍼, Host 공유 암호문 버퍼, TEE 암호 요청과 Host의 virtio-blk 요청을 하나의 보호된 요청으로 묶는 새 플랫폼 기능이 필요하다.

### 8.2 공개 구현에서 재사용할 수 있는 부분

- [OASIS Virtio 1.4 규격](https://docs.oasis-open.org/virtio/virtio/v1.4/virtio-v1.4.pdf)은 virtio-blk 요청, 여러 대기열, `FLUSH`, `DISCARD`, `WRITE_ZEROES`, 결과와 초기화 규칙을 제공한다.
- [Android Virtualization Framework 구조](https://source.android.com/docs/core/virtualization/architecture)는 pKVM이 pVM 비공개 메모리와 Host 공유 창을 나누고, virtqueue와 자료 버퍼를 고정 공유 창에 둔 뒤 필요한 자료를 복사하는 실제 구조를 설명한다.
- [Linux Intel TDX 문서](https://docs.kernel.org/arch/x86/tdx.html)는 비공개 메모리와 Host 공유 메모리를 구분하며 공유 메모리를 비신뢰 통신 영역으로 다루도록 한다.
- [Hyper-V Confidential VMBus](https://docs.kernel.org/virt/hyperv/coco.html)는 신뢰되는 중간 실행 영역이 기밀 VM의 장치 통신을 중계하고 필요할 때 별도 버퍼를 사용하는 공개 사례다.
- [Arm CCA 설계와 검증, OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/li)는 보호 VM 메모리와 비신뢰 Host 사이의 소유권과 검증 원칙을 제공한다.

이 사례들은 비공개 버퍼와 공유 버퍼를 나누는 방법을 보여 준다. EL2가 virtio-blk 경계에서 TEE 암호화, 인증값, RPMB와 중단 복구까지 수행하는 직접 사례는 이번 조사에서 찾지 못했다.

### 8.3 표준 virtio-blk로 부족한 부분

OASIS Virtio 1.4의 블록 기능 목록과 요청 형식에는 다음 정보가 정의돼 있지 않다.

- 비공개 평문 버퍼와 공유 암호문 버퍼의 구분
- TEE 요청과 키 손잡이
- 일회용 값(`nonce`), 인증값과 블록 버전
- RPMB 갱신 순서
- pVM 요청, TEE 요청과 Host 요청을 묶는 보호된 작업 번호
- 암호문과 인증값의 실제 저장 위치 관계

`VIRTIO_F_ACCESS_PLATFORM`은 장치가 플랫폼의 DMA 주소 변환과 접근 제한을 따르게 한다. 이 기능은 암호화나 TEE 연결을 제공하지 않는다.

### 8.4 두 가지 구현 형태와 부담

#### pVM의 표준 virtio-blk 드라이버를 그대로 유지

EL2가 pVM에 완전한 virtio-blk 장치처럼 보여야 한다. pVM의 virtqueue 처리, 평문 버퍼 보호, TEE 호출, 별도 Host virtqueue 생성, Host 완료와 pVM 완료 연결, 기능 협상, 알림, 인터럽트와 초기화를 모두 처리해야 한다.

이 방식은 pVM 드라이버를 바꾸지 않지만 EL2가 장치 구현을 가져야 하므로 가장 어렵다.

#### 보호된 기능과 pVM 드라이버를 함께 추가

pVM 드라이버가 EL2에 비공개 평문 버퍼, 공유 암호문 버퍼, 작업 번호, 논리 블록 주소, 길이와 요청 종류를 명시적으로 전달한다. EL2가 일반 virtio 요청 설명자(`descriptor`) 전체를 해석하는 범위는 줄어든다.

대신 새 virtio 기능 또는 보호 호출 규약, pVM 드라이버, EL2 모듈, Host 전달부와 TEE 비동기 처리 규약을 함께 만들어야 한다. 두 형태 중 시제품에는 더 현실적이지만 표준 virtio-blk만으로 구현할 수는 없다.

### 8.5 EL2에 추가되는 상태와 위험

각 요청마다 적어도 다음 상태를 Host가 접근하지 못하는 메모리에 둬야 한다.

- pVM 식별자와 실행 세대
- 대기열과 요청 설명자 번호
- 논리 블록 주소, 길이와 읽기·쓰기 종류
- pVM 평문 버퍼와 Host 공유 버퍼 위치
- TEE 작업 번호와 Host 작업 번호
- 암호문 버전과 인증값 위치
- 현재 처리 단계, 취소, 시간 제한과 초기화 상태

읽기에서는 Host가 공유 버퍼에 쓴 암호문을 보호된 버퍼로 옮긴 뒤 TEE가 인증값과 버전을 확인해야 한다. 확인에 성공한 뒤에만 평문을 pVM 비공개 버퍼에 넣어야 한다.

쓰기에서는 pVM이 요청 중 평문을 바꾸지 못하게 고정하거나 보호된 버퍼로 복사하고, TEE 결과만 Host 공유 버퍼에 넣어야 한다. DMA 완료 전에는 공유 버퍼를 다시 사용하면 안 된다.

Host가 제공하는 요청 설명자, 장치 용량과 완료 정보도 신뢰할 수 없다. EL2는 길이, 방향, 주소 범위, 겹친 버퍼, 정수 넘침, 중복 완료와 초기화를 확인해야 한다. [VIA: Analyzing Device Interfaces of Protected Virtual Machines](https://arxiv.org/abs/2109.10660)는 악의적인 가상 장치 입력이 보호 VM 드라이버의 공격 경로가 될 수 있음을 실제 분석으로 보여 준다. 이 입력 처리를 EL2로 옮기면 EL2가 같은 종류의 입력을 안전하게 검증해야 한다.

### 8.6 FLUSH·RPMB 복구와 작은 EL2 원칙

C-07도 C-04와 같은 암호문, 인증값, 위치표, UFS `FLUSH`와 RPMB 확정 순서가 필요하다. 여기에 virtio 요청 취소, 장치 초기화, DMA가 끝났는지 알 수 없는 상태와 공유 버퍼 회수가 추가된다.

[Android pKVM 모듈 문서](https://source.android.com/docs/core/virtualization/pkvm-modules)는 EL2 코드가 선점되지 않으므로 호출을 짧게 끝내야 한다고 명시한다. 따라서 EL2 호출 안에서 TEE와 UFS 완료를 동기식으로 기다릴 수 없고, 보호된 비동기 상태 관리가 필요하다. 이는 [시스템 개요](../docs/01_시스템_개요.md)의 작은 EL2 원칙과 직접 충돌한다. 오류가 있으면 한 pVM 파일시스템을 넘어 EL2와 다른 pVM 격리 신뢰까지 영향을 줄 수 있어 검증 기준도 가장 높다.

### 8.7 최소 확인 시험

1. pVM 드라이버를 바꾸는 형태로 범위를 제한하고 대기열 하나, 순서대로 처리하는 읽기·쓰기만 구현한다.
2. Host 공유 암호문 버퍼를 시작할 때 미리 할당하고 요청마다 공유 상태를 바꾸지 않는다.
3. S2MPU 또는 IOMMU가 UFS DMA를 공유 암호문 버퍼로만 제한하는지 검증한다.
4. pVM 작업 번호, TEE 작업 번호와 Host 작업 번호의 상태표를 EL2에서 시험한다.
5. 중복 완료, 잘못된 요청 설명자, 시간 제한, 장치 초기화와 DMA 지연을 주입한다.
6. 이 단계가 성립한 뒤에만 인증값 위치표와 RPMB 확정을 추가한다.

이 최소 범위도 pVM, EL2, TEE와 Host를 함께 바꾼다. 작은 EL2 원칙을 유지해야 한다면 C-07은 구현 난이도 이전에 설계 원칙 적합성 검토가 먼저 필요하다.

## 9. Herdr를 통한 Claude 검토

Claude에게는 후보 설계에 참여시키지 않고, 독립적으로 다음 사항을 검토하도록 요청했다.

- 표준 FUSE, fscrypt, dm-crypt와 virtio-blk를 그대로 쓸 수 없는 지점
- 후보별 변경 범위와 공개 선례
- 비동기 요청, 버퍼, 파일 이름, 인증값, `FLUSH`와 RPMB 부담
- 상대 난이도와 판정을 바꿀 수 있는 전제

Claude의 답변은 사실 근거로 직접 사용하지 않고, 빠진 쟁점과 내부 모순을 찾는 검토 의견으로 사용했다. 기술 판단은 각 절에 연결한 공식 문서, 원본 코드와 논문으로 다시 확인했다.

Claude 검토와 본 조사에서 일치한 내용은 다음과 같다.

- C-02는 커널을 바꾸지 않아 제한된 시제품은 가장 빨리 만들 수 있다.
- 하드웨어로 감싼 키를 사용한 fscrypt도 파일 이름용 비밀값을 커널에 남기므로 C-03의 키 조건을 그대로 만족하지 않는다.
- dm-crypt의 요청 처리 기능은 C-04에서 참고할 수 있지만, 표준 dm-crypt는 사용 중인 키를 Linux가 소비하므로 그대로 쓸 수 없다.
- 표준 virtio-blk만으로 C-07을 구현할 수 없으며 C-07은 네 후보 중 가장 어렵다.

C-02와 C-04의 초기 순서에는 견해 차이가 있었다. Claude는 파일 이름 문제가 없고 Device Mapper와 커널 TEE 기능을 쓸 수 있다는 이유로 C-04를 더 유리하게 보았다. 본 문서는 다음 근거로 “첫 자료 경로 시제품은 C-02가 더 쉬움”으로 판정했다.

- C-02에는 gocryptfs와 securefs처럼 파일 처리까지 포함한 공개 구현이 있다.
- C-02는 커널과 EL2를 바꾸지 않는다.
- C-04의 수정한 dm-crypt 방식은 기존 비동기 암호 완료 형식을 더 많이 쓸 수 있다. 그래도 TEE 암호 제공자와 보호된 평문 버퍼 연결의 공개 완성품은 찾지 못했다.
- C-04의 전체 조건에는 인증된 위치표와 블록 단위 중단 복구가 처음부터 필요하다.

다만 M-10 커널 호출 경로와 TEE 비동기 암호 제공자가 이미 구현돼 있고, 일반 파일 동작 전체를 빨리 지원해야 한다면 C-04의 초기 난이도가 C-02보다 낮아질 수 있다는 Claude의 지적은 유효하다.

## 10. 구현 순서에 대한 제안

최종 후보를 지금 결정하지 않고, 난이도를 실제 수치로 줄여 판단하려면 다음 순서가 적절하다.

1. 공통 M-10 시험 도구로 사용자 영역과 커널 영역에서 TEE 호출 크기별 지연, 처리량, 동시 요청 수와 복사 횟수를 잰다.
2. C-02의 제한된 파일 동작 시제품으로 파일 단위 설계가 요구 성능과 복구 조건을 만족할 가능성을 확인한다.
3. 동시에 C-04의 수정한 dm-crypt 또는 작은 전용 대상 시제품으로 블록 묶음 처리량을 확인한다.
4. C-03은 내용, 파일 이름과 인증값 저장 위치의 세 가지 성립 여부를 각각 작은 시험으로 먼저 확인한다.
5. C-07은 플랫폼 담당자가 EL2와 virtio 확장을 허용하고 작은 EL2 원칙을 바꿀 수 있을 때만 시제품 범위에 넣는다.
6. 가장 유리한 두 경로에 변조, 이전 상태 되돌리기, UFS `FLUSH`와 RPMB 중단 시험을 추가한다.

구조 선택 전에 최소한 다음 결과가 있어야 한다.

- 요청 크기별 TEE 호출 비용과 처리량
- FUSE와 커널 방식의 pVM 메모리 사용과 자료 복사 횟수
- 파일 이름 조회가 많은 작업과 큰 순차 파일 작업의 성능 차이
- RPMB 한 번 갱신하는 데 걸리는 시간과 안전 갱신 크기
- UFS `FLUSH`와 FUA의 플랫폼 보장 범위
- 중단 지점별로 선택되는 이전 또는 새 버전
- Host가 암호문, 인증값과 위치표를 바꿨을 때의 오류 결과

## 11. 최종 정리

- 가장 빠른 구조 확인 후보는 C-02다. 다만 전체 조건 시제품은 이미 어려운 작업이다.
- C-03은 fscrypt의 기존 기능이 많아 보여도 인증값 크기와 파일 이름용 비밀값 때문에 현재 조건에서 재사용 범위가 제한된다.
- C-04는 파일시스템과 응용프로그램을 바꾸지 않는 장점이 있지만, 실제 구현은 보안 가상 블록 장치와 복구 관리자를 만드는 큰 작업이다.
- C-07은 pVM·EL2·TEE·Host와 새 virtio 규약을 함께 바꿔야 하므로 현재 조건에서 가장 구현하기 어렵다.
- RPMB는 최신 상태의 작은 기준을 제공할 뿐이다. 자료·인증값·위치표·UFS 기록과 RPMB를 잇는 확정 및 복구 절차는 어느 후보에서도 별도로 구현해야 한다.

이 판정은 공개 자료를 바탕으로 한 구조 변경 난이도다. 목표 장치에서 측정하기 전에는 처리량이나 개발 일정을 확정할 수 없다.
