# 설계 범위 모듈 인벤토리

## 1. 목적과 기준

이 문서는 여러 모듈을 가로지르는 문제와 후보 구조를 찾기 전에, 이번 과제가
설계해야 하는 논리 책임을 모듈 단위로 고정한다. 아직 문제를 새로 선정하거나
후보의 배치·소유권을 결정하지 않는다.

저장소에는 `docs-align-final`이라는 경로가 없다. 이 문서에서는 마지막 정합성
작업의 산출물인 `docs-align-full`을 사용자가 말한 `docs-align-final`로 해석했다.
산출물 경로는 요청에 적힌 철자를 그대로 사용해 `docs-align-fnal-extension`으로
두었다.

범위 판정에는 다음 우선순위를 적용했다.

1. `docs/00_overview.md`의 과제 범위와 `docs/02_requirements.md`의 현재 FR
2. `docs-align-full/01_근거_원장.md`와 `02_문제_커버리지_매트릭스.md`
3. `docs-align-full/03_DP_목록.md`와 DP-01~10 상세 문서
4. `docs-align`의 기존 세 문제와 후보 구조
5. `docs/05_context_view.md`의 기존 8개 내부 모듈 후보

`docs/05_context_view.md`의 모듈 역할은 유효한 출발점이지만 FR 연결은 구 번호를
사용한다. 현재 FR은 `FR-03=Workload 동적 탑재`, `FR-04=Camera/AI HW 공유`,
`FR-05=도메인 간 보안 데이터 전송`이므로 이 문서에서 현재 번호로 정규화했다.

## 2. 모듈 판정 원칙

이 문서에서 모듈은 **Framework가 설계 책임을 져야 하는 응집된 논리 책임과
상태의 묶음**이다. 다음 원칙을 적용한다.

- Host, pVM, protected service pVM, EL2와 TEE는 모듈 이름이 아니라 실행·격리·
  신뢰 배치 경계다.
- 하나의 논리 모듈은 후보 구조에 따라 서로 다른 경계에 배치되거나 둘 이상의
  실행 컴포넌트로 분해될 수 있다.
- 비신뢰 Host에서 실행된다는 이유만으로 Framework 모듈이 범위 밖이 되지 않는다.
  단, 그 모듈의 판단은 보호 경계의 최종 보안 근거가 될 수 없다.
- 외부 platform/HW를 직접 만들지 않더라도 Framework가 그 interface, adapter,
  lifecycle 또는 정책을 설계·수정해야 하면 해당 통합 책임은 범위 안이다.
- 독립 DP가 없다는 사실은 모듈 부재를 뜻하지 않는다. API façade처럼 다른 DP의
  하위 결정인 책임도 구현 범위에는 포함된다.
- 이 목록은 현재 2-domain Camera→AI Reference Scenario를 기준으로 한다. 미래
  N-domain topology와 제품군별 HW abstraction은 이번 범위 밖이다.

## 3. 실행 경계와 구현 범위의 구분

| 실행/자원 경계 | 성격 | 과제에서 직접 설계하는 부분 | 직접 만들지 않는 부분 |
|---|---|---|---|
| 비신뢰 Host Linux | Framework process, relay, 저장 backend와 kernel mechanism이 실행될 수 있는 경계 | Host 측 Framework process, pVM/HW 제어 kernel driver, relay·adapter·상태 관리 | Linux OS 자체, Host Application, Normal Camera Application |
| pVM Guest | Workload와 guest-side adapter/bootstrap이 실행되는 보호 domain | measured bootstrap, buffer/TEE/storage/HW guest adapter와 Framework 계약 | Camera/AI Workload의 업무 로직, guest OS 제품 선택 |
| pKVM/EL2 | Host 밖의 Stage-2 trust anchor와 protected entry/PEP 후보 경계 | hypercall/ABI 계약, Stage-2·device·resource 집행 연동, 후보가 요구하는 최소 extension | pKVM 자체 포팅과 일반 core 개발 |
| protected service pVM | policy, buffer, HW, QoS authority의 후보 배치 경계 | 선택 후보의 protected service와 service protocol | 별도 고정 platform으로 미리 확정하지 않음 |
| TEE/Secure OS | GP 기능과 key/session을 보유하는 trust anchor | 기존 Secure OS 이식·수정, pVM adapter, caller binding, session lifecycle 연동 | 신규 Secure OS의 from-scratch 개발과 TA 제품 기능 자체 |
| Camera/AI HW, SMMU/S2MPU, CPU/memory, 저장 매체 | 외부 물리 자원과 보호 mechanism | 할당·회수·격리 adapter, native driver의 배치와 Framework 통합 계약 | HW IP 설계, register/firmware 제품 구현, 물리 자원 자체 |

`pKVM 자체 포팅 제외`와 `EL2 연동 설계 제외`는 같은 말이 아니다. 현재 문서는
EL2 extension이 필요한 후보를 탐색 범위에서는 유지한다. 다만 과거 문서의
`EL2 수정 불가` 제약이 아직 유효한지는 확인되지 않았으므로, 실제 EL2 변경은
platform owner 확인과 후보별 feasibility gate를 통과해야 한다.

마찬가지로 Secure OS core와 Camera/AI HW는 외부 요소지만, 기존 Secure OS의 pVM
연동 수정과 HW 할당 kernel driver·native driver 배치는 명시적인 과제 범위다.

## 5. 기존 문제·DP와 모듈의 역추적

이 표는 모듈 누락을 점검하기 위한 것이며 새 문제나 후보를 선택하는 표가 아니다.
마지막 열은 입력과 결과 방향을 섞지 않는 의존 그래프가 아니라, 해당 문제를
설명할 때 함께 경계를 확인해야 하는 결합 범위다. 방향이 필요한 변경 영향 분석은

## 6. 범위 밖과 경계 interface

| 범위 밖 대상 | 이유 | 범위 안에 남는 interface/책임 |
|---|---|---|
| Host/Normal Camera Application | 외부 요청 actor | M-01 API, identity와 authorization request contract |
| Camera/AI Workload 업무 로직 | 동적으로 탑재되는 확장 payload | M-05 package/bootstrap, M-07/08/10/11 guest adapter 계약 |
| Linux와 guest OS 제품 자체 | 실행 platform/제품 선택 | Host process·kernel driver와 guest adapter의 Linux native interface |
| pKVM 자체 포팅 | 기 포팅된 pKVM을 전제로 함 | hypercall/ABI, resource-specific PEP와 조건부 최소 extension |
| 신규 Secure OS 개발 | 기존 Secure OS를 전제로 함 | 기존 Secure OS 이식·수정, pVM adapter/session 연동 |
| Camera/AI/SMMU/S2MPU HW 설계 | SoC 물리 자원은 외부 제공 | M-08/09의 driver, allocation, reset/zeroize와 access-control 계약 |
| guest OS/RTOS/unikernel 선택 | A-13 `OUT-OF-SCOPE` | 선택과 무관한 Framework/guest contract |
| 미래 HW class/SoC abstraction | A-07 `OUT-OF-SCOPE` | 현재 Camera/AI HW integration |
| fleet audit/OTA/SLA/MTBF | A-10 `OUT-OF-SCOPE` | 현재 단일 device의 local gate/KPI와 로그 hook |
| N-domain graph/fan-in/fan-out | A-17 `OUT-OF-SCOPE` | 현재 Camera→AI 2-domain pipeline |
| 일정/인력 배분 | A-16 `OUT-OF-SCOPE` | 후보 feasibility의 구현량 측정만 유지 |

attestation, fault injection과 격리 증빙은 현재 A-09 `EVIDENCE-ONLY`다. 따라서
Observability/Audit를 독립 핵심 모듈로 추가하지 않고 각 모듈의 측정·증거 contract로
둔다. protected log authority가 별도 요구로 승인되면 그때 독립 모듈 여부를 다시
판정한다.

## 7. 아직 고정하면 안 되는 모듈 경계

- M-02의 process/Context, M-04의 generation/epoch recovery owner
- M-05의 common loader/pVM bootstrap, M-06의 분산 gate/common PDP
- M-07의 buffer owner·mapping lifetime·ledger owner·request route와 join protocol
- M-08의 client/service pVM physical owner와 native driver 배치
- M-09의 EL2 extension 가능성, resource별 실제 PEP primitive와 변경량
- M-10의 Host relay/direct route와 session cleanup authority
- M-11의 Host 공용 저장/pVM volume I/O 책임과 비-RPMB rollback 대응
- M-12의 fixed partition/shared-pool authority와 quota/lease parameter

이 항목들은 모듈이 존재하는지의 문제가 아니라 **모듈의 authoritative state를
누가 어느 신뢰 경계에서 소유하는가**의 문제다. 후보 구조를 찾기 전에 모듈 이름에
특정 후보 위치를 포함하지 않는다.

특히 M-09의 단일 ID는 반복되는 집행 책임을 찾기 위한 분류용 모듈군이다. buffer,
HW와 runtime PEP가 하나의 codebase, process, 신뢰 경계 또는 개발 조직으로 통합된다는
뜻이 아니다. 통합·분리 여부는 각 resource 후보와 feasibility를 확인한 뒤 정한다.

## 8. Claude와의 범위 검토 결과

Herdr 오른쪽 pane의 Claude와 두 차례 읽기 전용으로 대조했다.

1. Claude는 기존 Context View의 8개 모듈을 출발점으로 확인하고, 최신 10개 DP가
   policy, buffer ledger/route, HW lease와 runtime QoS의 책임 경계를 더 세분화했다고
   보았다.
2. Codex는 Context View의 legacy FR 번호와 `외부 runtime=설계 범위 밖`으로 볼 때의
   드라이버·Secure OS 범위 누락을 지적했다. Claude는 현재 FR 매핑과
   `docs/00_overview.md`의 kernel driver/Secure OS 이식·수정 범위를 다시 대조해 이를
   확인했다.
3. Claude의 제안에 따라 Multi-pVM Orchestrator(M-03)와 Fault/Recovery
   Manager(M-04), policy decision(M-06)과 resource-specific enforcement(M-09)를
   분리했다. EL2 extension은 확정 범위가 아니라 조건부 후보로 표시했다.
4. 독립 DP가 없는 M-01과 M-09를 빼자는 관점도 검토했다. M-01은 RS/API에 필요한
   하위 interface 책임이고, M-09는 기존 Context View와 과제 범위의 kernel driver,
   C-01/C-02/DP-05/09/10의 actual-state 집행에 반복해서 필요하므로 유지했다. 대신
   M-09가 하나의 중앙 authority가 아니라 resource-specific adapter 계열임을 명시했다.
5. M-11은 최신 라운드의 신규 결정이 아니라 기존 문제 C-03의 범위를 유지한
   항목이며, RPMB와 최종 후보가 확정되지 않았다는 낮은 결정 성숙도를 표시했다.

## 9. 다음 단계의 탐색 단위

후속 단계에서는 다음 교차점을 먼저 검사할 수 있다. 아직 새 문제로 판정하지 않는다.

- identity/generation/policy version의 종단 일관성: M-02, M-05, M-06과 M-07~12
- 장애 transaction과 resource별 reclaimer의 완료 합성: M-02~04, M-07~12
- policy decision, logical ledger와 actual state의 reconciliation: M-06~10, M-12
- Camera→AI end-to-end latency·capacity·recovery 공유 예산: M-03, M-07/08/10/12
- Workload 교체·pVM 재생성·영구 상태 재연결의 수명 결합: M-02/05/10/11

각 교차점은 기존 C-01~03과 DP-01~10의 `원인 + 결정 변수 + 책임/실행 위치/신뢰
경계`와 먼저 대조해야 한다. 같은 축이면 새 문제를 만들지 않고 기존 DP의
상위 합성 문제 또는 interface gap으로 기록한다.
