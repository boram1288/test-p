# 과제의 필요성: 품질을 위협하는 세 가지 기술 문제

## 1. 문서 목적

본 문서는 과제 필요성 슬라이드에서 제시한 다음 세 가지 문제를 기술적으로 구체화한다.

1. **HW 공유 시 기밀 데이터가 노출될 수 있다.**
2. **강한 메모리 격리로 인해 VM 간 대용량 데이터를 효율적으로 공유하기 어렵다.**
3. **암호화 파일이 pVM 수명에 묶여 있어 pVM 삭제 후 다시 사용할 수 없다.**

### 이 문서에서 사용하는 최소 용어

| 용어 | 의미 |
|---|---|
| Host | pVM을 관리하는 일반 Linux 영역. 본 과제에서는 커널까지 침해될 수 있는 비신뢰 영역이다. |
| pKVM/Hypervisor | Host보다 높은 권한에서 pVM의 CPU와 메모리 접근을 통제하는 보호 계층이다. |
| pVM | pKVM이 Host로부터 메모리를 보호하는 VM(Protected VM)이다. |
| Stage-2 격리 | Hypervisor가 pVM의 메모리 주소 변환을 통제하여 Host의 CPU 접근을 차단하는 기능이다. |
| DMA | Camera/AI HW가 CPU를 거치지 않고 메모리를 직접 읽고 쓰는 방식이다. |
| MMIO | CPU가 메모리 주소 형태로 HW 제어 레지스터에 접근하는 방식이다. |
| SMMU/S2MPU | HW의 DMA 접근 가능 메모리 범위를 제한하는 SoC 보호 장치다. |
| DMA-BUF | Linux에서 HW와 SW가 대용량 버퍼를 복사하지 않고 공유하기 위한 객체다. |
| zero-copy | 실제 프레임 데이터를 다른 메모리로 복사하지 않고 같은 물리 페이지의 접근권만 넘기는 방식이다. |
| TEE/Secure OS | TrustZone의 신뢰 영역에서 키 관리, 인증, 암복호화를 수행하는 실행 환경이다. |
| GP Client API | pVM Workload가 TEE의 암복호화 기능을 호출하는 기준선 API다. 문제 3에서는 이 호출 경로를 변경하지 않는다. |
| Workload 식별자 | 새 pVM이 이전 저장 공간을 다시 찾고 다른 Workload와 분리하기 위한 안정적인 신원이다. |
| 영구 저장 공간 | pVM 삭제와 무관하게 유지되고 같은 Workload의 새 pVM에 다시 연결되는 저장 자원이다. |
| 되돌리기 공격 | 공격자가 최신 저장 파일을 과거의 정상 암호문으로 바꾸어 이전 상태를 다시 사용하게 하는 공격이다. |
| DMA fence | HW의 버퍼 읽기 또는 쓰기 완료 시점을 다른 주체와 동기화하는 수단이다. |
| fail-closed | 오류가 발생했을 때 서비스를 억지로 계속하지 않고 접근권을 닫힌 상태로 유지하는 원칙이다. |

여기서 세 문제는 pKVM의 Stage-2 격리 자체가 약하다는 뜻이 아니다. pKVM이 제공하는 기본 메모리 격리를 실제
Secure Vision AI 파이프라인에 적용할 때 추가로 해결해야 하는 **HW DMA 접근 제어**, **보안 데이터 경로**,
**암호화 파일의 영구 보관**에서 발생하는 구조적 공백을 의미한다.

문제 설명은 `reference` 자료에서 공통으로 사용한 다음 전개 방식을 따른다.

`기존 동작 → 문제가 발생하는 지점 → 품질 속성에 미치는 영향 → 설계가 보장해야 할 조건 → 검증 방법`

## 핵심 결론: 메모리 격리만으로 제품 품질을 보장할 수 없다

세 문제를 해결하지 않으면 pVM을 실행하는 데 성공해도 Secure Vision AI 제품은 완성되지 않는다.

| 문제 | 실제 실패 결과 | 구조적으로 어려운 이유 | 설계 결과로 증명해야 할 것 |
|---|---|---|---|
| HW 공유 | Camera/AI HW를 통해 영상·모델 데이터가 Host에 노출되거나 실시간 처리가 중단됨 | 보안 도메인과 일반 기능이 하나의 HW를 함께 써야 하므로 격리와 성능을 동시에 만족해야 함 | 권한 중첩 0회, 잔류 데이터 0건, 전환 지연 수치 |
| VM 간 데이터 전달 | Host 중계 시 영상 노출, 복사 시 지연·메모리 사용량 증가 | 강한 격리를 유지하면서 매 프레임의 접근권만 빠르게 넘겨야 함 | Host 매핑 0회, 실제 프레임 복사 0회, 프레임 유실과 지연 수치 |
| 암호화 파일 보관 | pVM 재생성 후 기존 모델·보안 상태 복구 실패, 저장 파일 변조·되돌리기 | 비신뢰 Host에 영구 저장을 맡기면서 저장 수명, Workload 신원과 무결성을 함께 보장해야 함 | 재생성 후 복구 100%, 저장 경로 평문 노출 0건, 오연결 0건, 시작 지연 수치 |

즉, 본 과제의 목표는 단순히 pVM을 생성하는 기능이 아니다. **Host가 침해된 상태에서도 HW 사용, 영상 전달과
암호화 파일 보관의 전 구간을 보호하면서 제품의 실시간성·복구 가능성을 수치로 입증하는 것**이다.

이 문서의 수치는 아직 완료 결과가 아니라 설계가 만족해야 할 판정 기준이다. 실제 HW가 준비되면 개념 검증(PoC)과
침투 시험으로 측정하고, 준비 전에는 실행 기록 기반 시뮬레이션과 오류 주입 시험으로 구조 간 차이를 먼저 비교한다.

## 2. 공통 시스템 전제와 보호 대상

### 2.1 레퍼런스 파이프라인

```text
Camera Sensor
    │
    ▼
Camera HW ──DMA──> Secure Camera pVM
                         │
                         │ 영상 프레임
                         ▼
                   Secure AI pVM ──AI HW──> 추론 결과
                         │
                         ├──> Host Application: 판단 결과만 전달
                         └──> Secure OS(TEE): 키 관리, 암호화/복호화
                                      │
                                      └──암호문──> 영구 저장 공간
```

### 2.2 신뢰 경계

| 구성요소 | 신뢰 전제 | 주요 책임 |
|---|---|---|
| Host Linux | 비신뢰 | pVM 생성 요청, 일반 Camera/AI 기능 제공, 결과 소비 |
| pKVM Hypervisor(EL2) | 신뢰 | pVM 메모리의 Stage-2 격리 강제 |
| Secure Camera pVM | 신뢰 도메인 | 영상 캡처와 전처리 |
| Secure AI pVM | 신뢰 도메인 | AI 모델 및 영상 추론 처리 |
| Secure OS(TrustZone TEE) | 신뢰 | 키 관리, 인증, 암호화/복호화 |
| Camera/AI HW | 정책에 따라 할당되는 공유 자원 | 대용량 영상 처리와 AI 가속 |

### 2.3 보호 대상

- 카메라 원본 프레임과 전처리 영상
- AI 모델 가중치와 추론 중간 데이터
- 암호화 키, 인증 정보, 암호화 파일과 최신 버전 메타데이터
- Camera/AI HW의 레지스터, 내부 SRAM, DMA descriptor와 잔류 데이터
- pVM의 Workload 신원과 영구 저장 공간의 연결 상태

공격자는 Host의 사용자 공간뿐 아니라 **Host 커널 권한까지 획득한 상태**를 포함한다. 따라서 Host 드라이버나
Host 중재 프로세스가 올바르게 동작한다는 가정만으로 기밀성과 무결성을 보장할 수 없다.

## 3. 문제 1: HW 공유 시 기밀 데이터 노출 위험

### 3.1 한 문장 문제 정의

Camera/AI HW를 Host와 pVM이 함께 사용해야 하지만, HW 사용 주체를 전환하는 동안 **MMIO 접근권, DMA 주소 공간,
HW 내부 상태를 원자적으로 회수·소거·재부여하지 못하면** 이전 보안 작업의 데이터가 비신뢰 Host에 노출되거나
변조될 수 있다.

### 3.2 왜 HW 공유가 필요한가

Camera와 AI 가속기는 실시간 영상 파이프라인의 성능을 결정하는 고가의 SoC 자원이다. 보안 기능만을 위해 HW를
영구 전용하면 Host의 일반 촬영과 일반 AI 기능을 제공할 수 없고, Host에만 할당하면 pVM이 SW 처리로 폴백하여
실시간 성능을 만족하기 어렵다. 따라서 단일 Context HW를 다음과 같이 시분할해야 한다.

```text
시간 ───────────────────────────────────────────────────────────>

HW 소유자     Host      Secure Camera pVM      Host      Secure AI pVM
             ──────┬──────────────────────┬─────────┬──────────────
권한 전환           A                      B         C
```

각 전환점 A/B/C에서는 단순히 드라이버의 `owner` 변수만 변경해서는 안 된다. HW 사용권은 최소한 다음 세 종류의
권한으로 구성되기 때문이다.

1. **제어 권한**: MMIO 레지스터를 읽고 쓰는 권한
2. **메모리 권한**: HW가 DMA로 접근할 수 있는 물리 주소 범위
3. **상태 권한**: 인터럽트, DMA 작업 목록, 펌웨어 실행 상태, 내부 SRAM과 캐시 등 실행 상태의 소유권

### 3.3 기밀 데이터가 노출되는 구체적인 실패 경로

#### 실패 경로 A: DMA 권한 중첩

1. Secure Camera pVM이 보안 프레임 버퍼를 Camera HW에 DMA 대상으로 등록한다.
2. 전환 시 기존 SMMU/S2MPU 매핑이 완전히 해제되기 전에 Host에 HW 제어권이 부여된다.
3. Host의 악성 드라이버가 이전 DMA 주소 또는 descriptor를 재사용한다.
4. Camera HW가 pVM의 프레임을 Host가 읽을 수 있는 메모리로 송출한다.

CPU의 Stage-2 격리가 유지되어도, 장치의 DMA 경로가 같은 보호 정책에 묶이지 않으면 이 누출을 차단할 수 없다.
즉, **CPU 접근 격리와 DMA 접근 격리는 별개의 검증 대상**이다.

#### 실패 경로 B: HW 잔류 데이터 노출

1. Secure AI pVM이 모델 가중치나 중간 연산값을 AI HW 내부 SRAM 또는 DMA 작업 목록에 남긴다.
2. HW 사용권만 Host로 변경하고 내부 상태를 초기화하지 않는다.
3. Host가 디버그/상태 레지스터, 재사용된 버퍼 또는 실행 상태 저장 영역을 통해 이전 데이터를 읽는다.

메모리 매핑을 정확히 전환하더라도 HW 내부에 남은 데이터까지 소거하지 않으면 기밀성이 깨진다.

#### 실패 경로 C: 비신뢰 중재자의 정책 우회

1. HW 중재 로직이 Host 커널 드라이버에만 존재한다.
2. Host가 침해되어 대기열 순서, owner 상태 또는 권한 설정 요청을 조작한다.
3. 두 주체에 동시에 접근권을 부여하거나, 회수 실패를 성공으로 위장한 뒤 다음 주체에 HW를 넘긴다.

Host의 SW mutex는 동시 실행을 줄일 수 있지만 보안 경계를 강제하지 못한다. 최종 접근권은 Host가 조작할 수 없는
SMMU/S2MPU 또는 동등한 격리 주체가 강제해야 한다.

#### 실패 경로 D: 오류·시간 초과 처리 중 권한이 열린 채 복구

1. pVM이 HW 작업 중 비정상 종료되거나 인터럽트를 잃어버린다.
2. 중재자는 서비스 복구를 위해 강제로 Host에 HW를 재할당한다.
3. DMA 중지, pending transaction drain, 매핑 회수 또는 소거 중 하나가 끝나지 않았는데 재할당을 진행한다.
4. 가용성을 회복하려던 예외 경로가 기밀성 침해 경로가 된다.

정상 경로만 안전해서는 충분하지 않다. 초기화 실패, DMA 시간 초과, pVM 비정상 종료, 연속 재할당 요청 같은 예외 상황에서
항상 **fail-closed**해야 한다.

### 3.4 위협받는 품질 속성

| 품질 속성 | 위협 내용 |
|---|---|
| 보안성 | 권한 중첩, stale DMA 매핑, 잔류 데이터로 영상·모델이 Host에 노출되거나 변조됨 |
| 성능 | 권한 전환마다 HW 초기화, TLB 무효화, 캐시 정리와 소거가 발생해 프레임 처리 지연이 증가함 |
| 신뢰성 | 전환 중 인터럽트와 DMA 처리를 잘못하면 HW 정지, pVM 비정상 종료 또는 Host 장애로 전파됨 |
| 자원 효율 | 보안을 이유로 HW를 전용하거나 복제하면 HW 활용률과 제품 원가가 악화됨 |
| 확장성 | HW별 전환 절차가 Framework에 직접 결합되면 새로운 HW IP 추가 시 코어 수정이 필요함 |

보안성을 높이기 위해 매 전환마다 HW 전체 reset을 수행하면 안전성은 높아질 수 있지만 전환 시간이 늘어난다.
반대로 전환 지연을 줄이기 위해 일부 상태를 유지하면 잔류 데이터 위험이 커진다. 이 문제는 단순 구현 문제가 아니라
**보안성–성능–가용성 간 트레이드오프를 결정해야 하는 아키텍처 문제**다.

### 3.5 단순 접근으로 해결되지 않는 이유

| 단순 접근 | 한계 |
|---|---|
| HW를 pVM에 영구 전용 | Host 일반 기능을 지원하지 못하고 HW 활용률이 낮아짐 |
| 모든 HW 요청을 Host 드라이버가 중재 | 비신뢰 Host가 정책과 전환 결과를 위조할 수 있음 |
| SW mutex로 동시 접근 차단 | MMIO와 DMA 권한을 하드웨어적으로 강제하지 못함 |
| 매 전환 시 무조건 전체 reset | 보안에는 유리하지만 실시간 처리 예산을 초과할 수 있음 |
| DMA 버퍼만 소거 | DMA 작업 목록, 레지스터, SRAM, 캐시 등 다른 잔류 상태가 남을 수 있음 |

### 3.6 설계가 반드시 보장해야 할 조건

후보 구조와 무관하게 다음 불변조건이 성립해야 한다.

1. 특정 시점의 HW 소유자는 정확히 하나여야 한다.
2. 이전 소유자의 MMIO/DMA 권한 회수가 완료되기 전에 다음 소유자의 권한을 부여하지 않는다.
3. 전환 순서는 `요청 차단 → DMA 정지 → pending transaction drain → 권한 회수 → 잔류 상태 소거 → 새 권한 부여`를 따른다.
4. 권한 전환 결과는 비신뢰 Host가 아닌 신뢰 주체가 검증하거나 강제한다.
5. 비정상 종료, 시간 초과, 초기화 실패 시 HW를 격리 상태로 유지하고 다음 사용자에게 넘기지 않는다.
6. HW별 정책과 소거 절차는 Framework 코어에서 분리하여 새로운 HW IP를 추가할 수 있어야 한다.

### 3.7 검증해야 할 지표

- HW 사용권 중복 부여 횟수: **0회**
- 이전 소유자 DMA 매핑 잔존 횟수: **0회**
- 비인가 MMIO/DMA 접근 차단률: **100%**
- 전환 후 잔류 데이터 검출 건수: **0건**
- 정상/오류별 HW 전환 지연: 평균뿐 아니라 최악값과 상위 백분위수 측정
- pVM 비정상 종료, DMA 시간 초과, 초기화 실패, 요청 폭주 시 fail-closed 동작률: **100%**

관련 요구사항은 `FR-04`, `VOS-02`, `VOS-08`, `QS-01`, `QS-02`, `QS-06`, `QS-07`이다.

## 4. 문제 2: 강한 메모리 격리로 인한 VM 간 데이터 공유 불가

### 4.1 한 문장 문제 정의

pKVM은 Host와 각 pVM의 메모리를 강하게 분리하지만, Secure Camera pVM이 생성한 대용량 프레임을 Secure AI pVM에
전달하려면 격리 경계를 선택적으로 열어야 한다. 이때 Host 비노출, pVM 간 최소 권한, zero-copy, 버퍼 수명과
오류 회수를 동시에 만족하는 표준 데이터 경로가 현재 과제 기준선에 없다.

### 4.2 격리와 데이터 공유가 충돌하는 이유

Secure Vision AI는 다음 두 요구를 동시에 만족해야 한다.

- **격리 요구**: Camera pVM 메모리를 Host와 다른 pVM이 임의로 읽거나 쓸 수 없어야 한다.
- **파이프라인 요구**: Camera pVM의 프레임을 AI pVM이 매 프레임 소비해야 한다.

하지만 강한 격리에서 공유는 예외다. 공유 메모리를 허용하는 순간 다음 정보를 명시적으로 관리해야 한다.

- 어떤 페이지 또는 DMA-BUF를 공유하는가?
- 송신자와 수신자는 누구인가?
- 읽기/쓰기 중 어떤 권한을 부여하는가?
- 권한은 언제 시작하고 언제 회수하는가?
- 공유 중 Host와 제3의 pVM은 확실히 배제되는가?
- 송신자 또는 수신자가 비정상 종료됐을 때 누가 버퍼를 회수하는가?

### 4.3 DMA-BUF가 VM 경계를 그대로 넘을 수 없는 이유

DMA-BUF file descriptor는 한 Linux 커널 인스턴스 안의 파일 객체를 가리킨다. Camera pVM의 fd 숫자를 AI pVM에
전달해도 AI pVM의 fd table에는 대응하는 객체가 없으므로 같은 버퍼를 참조하지 않는다. VM 간 전달의 실체는
fd 전달이 아니라 다음 두 단계다.

1. 송신 pVM의 DMA-BUF 뒤에 있는 물리 페이지에 대한 접근권을 수신 pVM에 부여한다.
2. 수신 pVM이 전달받은 페이지를 자신의 DMA-BUF 객체로 import한다.

따라서 VM 간 zero-copy를 구현하려면 DMA-BUF API뿐 아니라 pKVM의 Stage-2 매핑, SMMU/S2MPU DMA 권한,
캐시 동기화, DMA fence와 버퍼 수명주기를 하나의 프로토콜로 묶어야 한다.

### 4.4 성능 문제가 발생하는 구체적인 경로

1080p RGB24 프레임을 단순 산정하면 한 프레임은 약 6.22 MB이고 30 fps 입력은 약 186.6 MB/s다. 한 번의 전체
프레임 `memcpy`도 원본 read와 대상 write를 합쳐 최소 약 373.2 MB/s의 메모리 트래픽을 추가한다. Host를 거쳐
두 번 복사하면 추가 트래픽은 약 746.5 MB/s가 된다. 실제 포맷과 stride에 따라 값은 달라지지만, 대용량 영상에서
복사 횟수가 latency, memory bandwidth와 전력에 직접 영향을 준다는 점은 동일하다.

```text
[복사 기반]
Camera pVM 버퍼
    └─복사─> Host 중계 버퍼
                 └─복사─> AI pVM 버퍼

문제: Host 노출 + 2회 복사 + 버퍼 3벌 + 캐시 오염

[필요한 의미론]
Camera pVM 버퍼
    └─소유권/접근권 전환─> AI pVM이 같은 물리 페이지 사용

목표: Host 비매핑 + 실제 프레임 memcpy 0회 + 명확한 소유권
```

### 4.5 보안·신뢰성 문제가 발생하는 구체적인 경로

#### 실패 경로 A: Host 중계를 통한 노출

1. pVM 간 직접 전달 경로가 없어 Camera pVM이 Host의 virtio/vsock 또는 공유 버퍼로 프레임을 보낸다.
2. Host가 중계 buffer를 매핑해 AI pVM으로 복사한다.
3. 침해된 Host가 전송 중인 원본 프레임을 읽거나 변조한다.

암호화 후 중계하면 기밀성은 높일 수 있지만 매 프레임 암복호화와 복사가 추가되어 HW 가속의 성능 이점을 잠식한다.

#### 실패 경로 B: 영구 공유 영역의 과도한 권한

1. 성능을 위해 Camera pVM과 AI pVM에 큰 메모리 pool을 항상 동시에 매핑한다.
2. AI pVM이 처리할 필요가 없는 미래/과거 프레임까지 읽을 수 있다.
3. 한 pVM이 침해되면 공유 pool 전체가 공격 표면이 되고, stale frame이 장기간 남는다.

정적 공유는 매핑 전환 비용을 줄이지만 최소 권한과 시간 제한 권한을 약화한다.

#### 실패 경로 C: 소유권 전환 중 동시 접근

1. Camera HW가 버퍼 쓰기를 완료하기 전에 AI pVM에 읽기 권한을 부여한다.
2. AI pVM이 불완전한 frame을 읽거나 Camera pVM이 AI 처리 중 buffer를 재사용한다.
3. 영상 손상, 추론 오류 또는 TOCTOU(Time-of-check to time-of-use)가 발생한다.

DMA fence, 캐시 정리/무효화, Stage-2 권한 전환의 순서가 일치해야 한다.

#### 실패 경로 D: 비정상 종료 시 권한과 메모리 누수

1. AI pVM이 프레임을 소유한 상태에서 비정상 종료된다.
2. 반환 신호가 오지 않아 Camera pVM이 buffer를 재사용하지 못한다.
3. 강제 회수 과정에서 DMA가 남아 있으면 use-after-revoke가 발생하고, 회수하지 않으면 pool이 고갈된다.

정상 프레임 흐름뿐 아니라 시간 초과, 중복 반환, 순서 역전, pVM 재시작을 포함한 회수 프로토콜이 필요하다.

### 4.6 위협받는 품질 속성

| 품질 속성 | 위협 내용 |
|---|---|
| 보안성 | Host 중계, 과도한 공유 범위, 권한 중첩으로 프레임이 비인가 주체에 노출됨 |
| 성능 | 반복 복사, 페이지 재매핑, TLB/캐시 동기화가 프레임 예산을 잠식함 |
| 자원 효율 | pVM별 복제 버퍼와 고정 공유 pool로 메모리 사용량이 증가함 |
| 신뢰성 | 버퍼 고갈, 중복 반환, 비정상 종료 후 회수 실패로 파이프라인이 정지함 |
| 확장성 | 송수신 pVM이 늘어날수록 점대점 전용 경로와 권한 조합이 급증함 |

격리를 극대화하면 공유가 어려워지고, 공유를 단순화하면 격리가 약해진다. 프레임마다 권한을 엄격히 전환하면
보안은 강화되지만 전환 비용이 커지고, 고정 공유 pool을 사용하면 성능은 좋아지지만 공격 표면과 메모리 사용량이
증가한다. 따라서 이 문제는 **보안성–성능–메모리 효율 간 트레이드오프**다.

### 4.7 단순 접근으로 해결되지 않는 이유

| 단순 접근 | 한계 |
|---|---|
| fd 숫자를 다른 pVM에 전달 | fd는 각 커널 인스턴스에 로컬이므로 같은 DMA-BUF를 가리키지 않음 |
| Host가 프레임을 복사해 중계 | Host 비노출 요구 위반, 복사 지연과 메모리 대역폭 증가 |
| pVM마다 별도 버퍼 유지 | 메모리 사용량과 복사 횟수가 증가함 |
| 모든 pVM에 공유 pool 영구 매핑 | 최소 권한 위반, 침해 영향 범위 확대, stale data 노출 |
| 매 프레임 전체 매핑 재구성 | Stage-2/SMMU 전환과 TLB 동기화 비용이 실시간성을 해칠 수 있음 |

### 4.8 설계가 반드시 보장해야 할 조건

1. 실제 프레임 payload 경로와 권한 판정용 제어 경로를 분리하고, 제어 명령이 프레임마다 발생해도 payload를 싣지 않는다.
2. Host는 제어를 중계할 수 있어도 프레임 payload를 읽거나 매핑할 수 없어야 한다.
3. 버퍼마다 소유자, 허용된 접근 모드, 버퍼 재사용 세대 번호 및 상태를 추적한다.
4. 상태는 최소한 `FREE → CAMERA_OWNED → IN_TRANSFER → AI_OWNED → RECLAIMING → FREE`로 관리한다.
5. 송신자의 쓰기 완료와 권한 회수 후 수신자의 접근권을 부여한다.
6. CPU Stage-2 권한과 Camera/AI HW의 DMA 권한을 같은 버퍼 상태 전이에 맞춰 변경한다.
7. DMA fence, 캐시 동기화와 메모리 접근 순서 보장을 프로토콜에 포함한다.
8. 시간 초과, pVM 비정상 종료, 중복 반환, 잘못된 식별자 입력 시 버퍼를 안전하게 회수하거나 폐기한다.
9. 새로운 pVM 쌍을 추가해도 Framework 코어를 수정하지 않도록 통신 종단점과 정책을 데이터로 기술한다.

### 4.9 검증해야 할 지표

- 프레임 전달 과정의 실제 프레임 `memcpy` 호출 횟수: **0회**
- 전송 중 Host가 frame page를 매핑할 수 있었던 횟수: **0회**
- 버퍼 권한 중첩 및 무소유 상태 위반 횟수: **0회**
- 비인가 pVM 접근 차단률: **100%**
- 1080p 30 fps 지속 입력 시 프레임 유실, 전체 구간 지연과 비격리 구성 대비 성능 저하 측정
- pVM 비정상 종료/시간 초과 후 버퍼 회수율: **100%**
- 다중 pVM 운용 시 버퍼 pool 크기와 추가 메모리 사용량 측정

관련 요구사항은 `FR-05`, `VOS-01`, `VOS-09`, `QS-01`, `QS-02`, `QS-04`, `QS-06`, `QS-07`이다.

## 5. 문제 3: pVM 수명에 종속된 암호화 파일 유실

### 5.1 한 문장 문제 정의

TEE가 데이터를 안전하게 암호화해도 암호문을 pVM 내부 파일시스템에 저장하면 pVM 삭제와 함께 파일도 사라진다.
키와 평문의 신뢰 경계는 유지하면서, 암호화 파일의 수명을 pVM 실행 수명과 분리해 같은 Workload의 새 pVM에
안전하게 다시 연결하는 영구 보관 구조가 현재 과제 기준선에 없다.

### 5.2 현재 저장 흐름과 필요한 흐름

```text
[현재 흐름]
pVM Workload
    └─ 평문/ENC·DEC 요청 ─> TEE
        └─ 암호문 ─> pVM 저장 서비스
            └─ pVM 파일시스템
                    └─ pVM 삭제 시 서비스와 파일이 함께 소멸

[필요한 흐름]
pVM Workload
    └─ 평문/ENC·DEC 요청 ─> TEE
        └─ 암호문 ─> Workload별 영구 저장 공간
                    └─ pVM 삭제 후 유지, 같은 Workload의 새 pVM에 재연결
```

키는 TEE 밖으로 나오지 않아야 한다. Workload와 TEE 사이에는 암호화 전·복호화 후 평문이 존재할 수 있지만,
pVM 저장 서비스, Framework, Host와 영구 저장 매체로 이어지는 저장 경로에는 평문이 노출되면 안 된다.
GP Client API를 통한 pVM–TEE 호출 경로와 TEE의 키 관리·암복호화 책임은 기준선으로 고정하고, 여기서는 TEE가
만든 암호화 파일의 보관 수명과 입출력 책임만 다룬다.

### 5.3 구체적인 기술 공백

#### 공백 A: 저장 수명의 소유권

pVM 파일시스템은 pVM 수명주기에 포함된다. pVM과 독립적으로 저장 공간을 생성·유지·폐기할 주체와 pVM 삭제,
Workload 폐기를 구분하는 회수 규칙이 정의되지 않았다.

#### 공백 B: Workload 신원과 재연결

새 pVM의 일시적인 VM 식별자만으로는 이전 저장 공간을 안정적으로 찾을 수 없다. 침해된 Host가 다른 Workload의
저장 공간을 연결하지 못하도록 안정적인 Workload 식별자와 저장 공간의 결합을 검증해야 한다.

#### 공백 C: 비신뢰 저장소의 무결성과 재생 방지

암호화만으로는 파일 삭제, 비트 변조와 과거의 정상 암호문 재사용을 모두 검출할 수 없다. RPMB를 사용하지 않는
기준선에서 최신 버전을 판정할 메타데이터와 검증 방식이 아직 정해지지 않았다.

#### 공백 D: 보관과 입출력 책임의 위치

Host 공용 서비스가 모든 Workload의 암호문 입출력을 맡으면 연결과 자원 공유는 단순해지지만 장애 영향이 넓어진다.
Framework가 Workload별 영구 볼륨의 수명·연결을 관리하고 pVM 저장 서비스가 파일 입출력을 맡으면 장애 영향은
분리되지만 구성·재연결 단계와 자원 사용이 늘어난다.

### 5.4 문제가 발생하는 구체적인 실패 경로

#### 실패 경로 A: pVM 삭제와 함께 파일 유실

1. Workload가 TEE를 통해 모델 또는 보안 상태를 암호화한다.
2. pVM 저장 서비스가 암호문을 pVM 파일시스템에 기록한다.
3. 장애 복구나 자원 회수를 위해 pVM을 삭제한다.
4. 새 pVM이 이전 파일을 찾지 못해 모델 재배포 또는 보안 상태 초기화가 필요해진다.

#### 실패 경로 B: 다른 Workload의 저장 공간 오연결

1. 새 pVM 생성 시 Host 또는 Framework가 Workload 식별자와 저장 공간의 매핑을 선택한다.
2. 침해된 Host가 다른 Workload의 볼륨을 연결하거나 이전 연결 정보를 재사용한다.
3. 소유권을 검증하지 않으면 다른 Workload의 암호문을 읽거나 덮어써 서비스 거부를 일으킬 수 있다.

#### 실패 경로 C: 저장 파일 변조와 되돌리기

1. Host가 영구 저장소의 최신 암호문과 메타데이터를 보관한다.
2. 공격자가 파일을 삭제·변조하거나 과거의 정상 암호문으로 교체한다.
3. 새 pVM이 위조되거나 오래된 상태를 최신 파일로 받아들인다.

#### 실패 경로 D: 저장 장애와 자원 누수의 확산

공용 서비스의 오류는 여러 Workload의 저장·복구를 동시에 중단시킬 수 있다. Workload별 구조에서도 pVM이 연결 중
비정상 종료되면 고아 볼륨이나 중복 연결이 남을 수 있으므로 결정적인 연결·분리·회수 규칙이 필요하다.

### 5.5 위협받는 품질 속성

| 품질 속성 | 위협 내용 |
|---|---|
| 보안성 | 저장 경로의 평문 노출, 다른 Workload의 저장 공간 오연결, 파일 삭제·변조·되돌리기 |
| 가용성 | pVM 재생성 후 복구 실패 또는 공용 저장 서비스 장애로 파이프라인이 중단됨 |
| 성능 | 저장 공간 검색·연결·검증 단계가 pVM cold start 지연을 증가시킴 |
| 신뢰성 | 중복 연결, 불완전한 갱신과 비정상 종료 후 회수 실패로 저장 상태가 일관성을 잃음 |
| 자원 효율 | Workload별 서비스와 볼륨을 둘 경우 프로세스와 저장 자원이 증가함 |
| 확장성 | Workload별 구성이 Framework 코어에 결합되면 신규 Workload마다 수정이 필요함 |

Host 공용 영구 저장 서비스는 재연결과 자원 공유에 유리하지만 장애가 여러 Workload로 전파될 수 있다.
Workload별 영구 볼륨은 장애 영향을 분리하지만 볼륨 구성, 재연결 단계와 자원 사용을 늘린다. 따라서 이 문제는
**가용성–성능–자원 효율–장애 격리 간 아키텍처 트레이드오프**다.

### 5.6 단순 접근으로 해결되지 않는 이유

| 단순 접근 | 한계 |
|---|---|
| pVM 파일시스템에 계속 저장 | pVM 삭제 시 암호화 파일도 사라져 재생성 후 복구할 수 없음 |
| Host 디렉터리를 그대로 다시 연결 | Workload 매핑, 저장 수명과 예외 처리 책임이 불명확함 |
| 암호화만 적용 | 평문 기밀성은 보호해도 파일 삭제·오연결·되돌리기를 막지 못함 |
| 모든 Workload가 하나의 공용 서비스 사용 | 자원 효율은 높지만 장애 영향과 공격 표면이 전체 Workload로 확대됨 |
| Workload별 저장소를 수동 구성 | 장애 격리는 좋아지지만 온보딩 공수와 자원 사용이 선형으로 증가함 |

### 5.7 설계가 반드시 보장해야 할 조건

1. 암호화 파일의 수명은 pVM의 생성·삭제 수명과 독립적이어야 한다.
2. 키는 TEE 밖으로 나오지 않고 pVM 저장 서비스, Framework, Host와 저장 매체에는 평문이 노출되지 않아야 한다.
3. 안정적인 Workload 식별자와 저장 공간을 결합하고 다른 Workload의 연결 요청을 차단해야 한다.
4. pVM 삭제 시 저장 공간을 유지하고 Workload 폐기 시에만 저장 공간과 메타데이터를 회수해야 한다.
5. 생성·연결·분리·재연결·회수 상태와 책임 주체를 명시하고 중복 연결을 방지해야 한다.
6. 비-RPMB 저장소에서 파일 삭제·변조·되돌리기를 검출하는 메커니즘과 실패 시 동작을 정의해야 한다.
7. 저장 또는 연결 중 pVM이 비정상 종료돼도 불완전한 파일을 정상 상태로 확정하지 않아야 한다.
8. 공용 서비스의 장애 격리 또는 Workload별 볼륨의 자원 회수·구성 자동화를 검증해야 한다.
9. 신규 Workload 추가 시 Framework 코어를 수정하지 않도록 저장 정책과 연결 정보를 데이터로 기술해야 한다.

### 5.8 검증해야 할 지표

- pVM 삭제·재생성 후 최신 암호화 파일 복구 성공률: **100%**
- 저장 데이터 경로에서 키와 평문이 관찰된 건수: **0건**
- 다른 Workload의 저장 공간 연결 및 접근 성공 건수: **0건**
- 삭제·변조·되돌리기 공격 검출률: **100%** — 메커니즘 정의 후 필수 gate로 검증
- 비정상 종료 후 중복 연결 및 고아 볼륨 발생 건수: **0건**
- 저장 공간 재연결을 포함한 cold start p95: **2초 이하**
- 신규 Workload 저장 구성 시 Framework 코어 변경량: **0 LoC**, 통합 리드타임: **5인일 이하**

관련 항목은 `SEC-05`, `PERF-07`, `EXT-01`, `EXT-03`과 비-RPMB 저장소의 무결성·재생 방지 gate다.

## 6. 세 문제의 연결 관계

세 문제는 같은 Secure Vision AI 파이프라인을 위협하지만 모두 한 방향으로 이어지는 처리 단계는 아니다. 문제 1과 2는
실시간 프레임 데이터 경로에 연속으로 나타나고, 문제 3은 pVM 생성·삭제를 가로지르는 저장 수명주기 축에 나타난다.

```text
[실시간 프레임 데이터 경로]
① HW 공유                              ② 도메인 간 데이터 전달
Camera/AI HW의 소유권 전환 ───────────> Camera pVM에서 AI pVM으로 frame 소유권 전환

[pVM과 저장 자원의 수명주기]
pVM 생성 ──> 처리·TEE 암호화 ──> ③ 암호화 파일 영구 보관 ──> pVM 삭제
                                      │                       │
                                      └──── 저장 공간 유지 ───┘
                                                  │
                                                  └──> 동일 Workload의 새 pVM에 재연결
```

| 문제 | 격리만 우선하면 | 성능·편의만 우선하면 | 핵심 설계 과제 |
|---|---|---|---|
| HW 공유 | HW 전용화와 잦은 전체 reset으로 활용률·성능 저하 | 권한 중첩과 잔류 데이터 노출 | 배타적 소유권과 원자적 전환 |
| VM 간 데이터 전달 | 복사·재매핑 증가와 버퍼 고갈 | 과도한 영구 공유와 Host 노출 | Host 비노출 zero-copy 소유권 프로토콜 |
| 암호화 파일 보관 | Workload별 자원과 재연결 단계 증가 | 공용 서비스 장애가 여러 Workload로 전파 | pVM과 저장 수명 분리, 안전한 재연결 |

따라서 최종 Framework는 다음 공통 원칙을 가져야 한다.

- **권한은 명시적으로 부여하고 사용 후 반드시 회수한다.**
- **Host는 관리 요청을 수행하더라도 보안 데이터의 신뢰 경계에는 포함하지 않는다.**
- **정상 경로보다 비정상 종료, 시간 초과, 초기화 실패 같은 예외 경로에서 fail-closed를 우선한다.**
- **CPU 메모리 권한, HW DMA 권한, 버퍼 소유권과 영구 저장 자원의 수명주기를 정합시킨다.**
- **보안 보장은 정성 설명이 아니라 권한 중첩 0회, 노출 0건, 차단률 100%와 지연 수치로 증명한다.**
