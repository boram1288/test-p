# 문제 1. 아키텍처 스타일과 태틱 조사

## 1. 조사 목적과 범위

이 문서는 Camera pVM이 생성한 프레임을 AI pVM에 Host 비노출·zero-copy로
전달하는 문제에 적용할 아키텍처 스타일과 태틱을 선정하기 위한 조사 결과다.

아키텍처 스타일에는 전 세계적으로 합의된 하나의 닫힌 목록이 없다. 따라서
"모두"의 범위를 다음 두 권위 있는 분류에 포함된 항목 전체로 한정했다.

1. Garlan과 Shaw가 정리한 공통 아키텍처 스타일
2. SEI가 아키텍처 태틱과의 관계를 분석한 주요 아키텍처 패턴

태틱은 이 프로젝트의 문제 1과 직접 연결된 성능 효율성, 자원사용성, 보안성,
신뢰성·가용성, 복구성과 모듈성 범주를 조사했다. UI 중심의 사용성 태틱과 화면
분리 패턴은 목록에는 포함하되 후보 구조 적용 대상에서는 제외했다.

## 2. 용어 구분

| 구분 | 의미 | 문제 1의 예 |
|---|---|---|
| 아키텍처 스타일 | 컴포넌트·connector 어휘와 조합 제약으로 시스템 계열을 정의한다. | Pipe-and-Filter, Broker, Repository |
| 아키텍처 패턴 | 반복되는 구조 문제와 force에 대한 알려진 구조 해법이다. | Microkernel, Adapter/Proxy 조합 |
| 아키텍처 태틱 | 하나의 품질속성 응답을 개선하기 위한 구체적인 설계 결정이다. | 중간자 사용, queue 상한, zero-copy |
| 구현 mechanism | 태틱이나 패턴을 실현하는 기술이다. | DMA-BUF, `dma_fence`, Stage-2 mapping |

Garlan과 Shaw는 스타일을 컴포넌트와 connector의 어휘, 조합 제약과 실행 의미로
설명한다. 서로 다른 스타일은 한 시스템에서 혼합될 수 있다.
[Garlan–Shaw, An Introduction to Software Architecture](https://www.cs.cmu.edu/afs/cs/project/vit/ftp/pdf/intro_softarch.pdf)

SEI는 태틱을 특정 품질속성의 응답 측정값을 개선하는 아키텍처 결정으로 정의하며,
패턴은 여러 태틱을 묶은 더 큰 구조 해법으로 설명한다.
[SEI, Modifiability Tactics](https://www.sei.cmu.edu/library/modifiability-tactics/)

## 3. 아키텍처 스타일·패턴 전체 목록

### 3.1 Data-flow 계열

| 스타일 | 구조적 핵심 | 일반적인 장점 | 일반적인 위험 | 문제 1 적합성 |
|---|---|---|---|---|
| Pipe-and-Filter | 독립 filter가 typed pipe를 통해 stream을 순차 처리한다. | pipeline 병렬성, throughput 분석, 단계 교체 | format 변환·복사가 개입하면 지연 증가 | **높음** — Camera→AI frame pipeline에 직접 대응 |
| Batch Sequential | 한 단계가 전체 입력 처리를 끝낸 뒤 다음 단계가 시작한다. | 단순한 순서와 오류 위치 | streaming과 30 fps 연속 처리에 불리 | 낮음 |

Pipe-and-Filter는 독립 컴포넌트가 stream을 증분 처리하며 bounded/typed pipe로
특화할 수 있다. 원 논문은 신호 처리 영역과 복사하지 않는 pipe의 제품 적용 사례도
설명한다. 문제 1에서는 payload를 pipe 안에서 복사하지 않고 DMA-BUF handle과 fence가
connector가 되도록 특화해야 한다.

### 3.2 Data abstraction·call-return 계열

| 스타일 | 구조적 핵심 | 일반적인 장점 | 일반적인 위험 | 문제 1 적합성 |
|---|---|---|---|---|
| Data Abstraction / Object-Oriented | 데이터 표현과 불변식을 manager 객체가 캡슐화한다. | 정보 은닉과 무결성 유지 | 상대 객체 identity 결합, call coupling | 높음 — DMA-BUF handle과 lifetime 캡슐화 |
| Main Program / Subroutine | 중앙 제어부가 하위 procedure를 순서대로 호출한다. | 단순한 제어 흐름 | 중앙 제어 결합과 확장 한계 | 낮음 |
| Client–Server | server가 다수 client에 명시적 서비스를 제공한다. | 공통 서비스와 정책 중앙화 | server 병목·장애 영향 | 중간 — 보호 broker 후보의 기초 |

### 3.3 Event 계열

| 스타일 | 구조적 핵심 | 일반적인 장점 | 일반적인 위험 | 문제 1 적합성 |
|---|---|---|---|---|
| Event-based / Implicit Invocation | producer가 event를 발행하고 등록된 consumer가 반응한다. | 생산자·소비자 결합 완화, 비동기 처리 | 완료 순서·오류 전파 추론이 어려움 | **높음** — fence 완료 알림에 한정 적용 |
| Publish–Subscribe | intermediary가 topic 기반 구독자에게 event를 전달한다. | 동적 fan-out과 runtime binding | 1:1 경로에는 과도하며 queue 지연 가능 | 낮음~중간 |

프레임 payload 자체를 event에 넣지 않는다. event에는 보호 buffer handle, format,
generation과 fence 정보만 싣고 payload는 같은 보호 물리 페이지에 둔다.

### 3.4 Layered 계열

| 스타일 | 구조적 핵심 | 일반적인 장점 | 일반적인 위험 | 문제 1 적합성 |
|---|---|---|---|---|
| Layered | 상위 layer가 바로 아래 layer의 추상화된 서비스만 사용한다. | platform 변화 격리, 인터페이스 안정화 | layer crossing과 marshaling 비용 | **높음** — Workload/DMA-BUF/보호 mapping 계층 분리 |
| Partially Opaque Layered | 성능상 필요한 일부 하위 기능에 제한적 직접 접근을 허용한다. | abstraction과 fast path 절충 | 우회 경로가 늘면 결합 증가 | 높음 — payload는 HW가 직접 접근 |

### 3.5 Data-centered 계열

| 스타일 | 구조적 핵심 | 일반적인 장점 | 일반적인 위험 | 문제 1 적합성 |
|---|---|---|---|---|
| Repository | 중앙 데이터 구조를 독립 컴포넌트들이 읽고 갱신한다. | 일관된 metadata와 관측 지점 | 중앙 병목·공용 장애점·lock contention | 중간~높음 — metadata registry에만 적합 |
| Blackboard | 공유 상태 변화가 실행할 knowledge source를 선택한다. | 불완전 정보의 점진적 문제 해결 | 결정 순서와 실시간성 예측이 어려움 | 낮음 |
| Shared Memory | 여러 실행 주체가 같은 물리 데이터를 mapping한다. | payload zero-copy | 동기화와 격리 실패의 영향이 큼 | **필수 기반** — 단독 상위 스타일로 쓰지는 않음 |

Repository를 적용하더라도 broker가 frame payload를 CPU mapping하는 구조는 채택하지
않는다. repository에는 handle, reference, format, generation과 fence metadata만 둔다.

### 3.6 Virtual-machine·rule 계열

| 스타일 | 구조적 핵심 | 일반적인 장점 | 일반적인 위험 | 문제 1 적합성 |
|---|---|---|---|---|
| Table-driven Interpreter | engine이 table/rule을 읽어 동작을 결정한다. | 정책 변경의 데이터화 | interpreter overhead와 상태 복잡성 | 낮음~중간 — setup 정책에만 가능 |
| State-transition System | 명시적 상태와 transition으로 reactive 동작을 정의한다. | 순서와 불변식 검증 | 상태 폭증과 fast-path overhead | 낮음 — 이번 전제에서는 프레임별 상태 머신 제외 |
| Process-control | sensor 입력과 feedback으로 환경을 제어한다. | 폐루프 실시간 제어 | 데이터 전달 자체의 핵심 구조는 아님 | 낮음 |

### 3.7 Distributed·structural pattern 계열

| 스타일·패턴 | 구조적 핵심 | 문제 1 적합성 |
|---|---|---|
| Distributed Processes / Peer-to-Peer | 독립 process가 protocol로 직접 통신한다. | **높음** — 두 pVM의 direct pair 후보 |
| Broker | client와 server 사이 intermediary가 등록·탐색·전달을 중재한다. | **높음** — 중앙 보호 DMA-BUF service 후보 |
| Microkernel | 최소 core와 교체 가능한 외부 service로 책임을 분리한다. | 중간 — EL2 최소화 원칙 설명에 유용 |
| Reflection | meta-level이 base-level 구조나 정책을 동적으로 바꾼다. | 낮음 — 검증 범위와 공격면 증가 |
| MVC | model, view와 controller를 분리한다. | 부적합 — UI 구조가 아님 |
| Presentation–Abstraction–Control | 계층화된 agent가 UI와 기능을 분리한다. | 부적합 |

SEI의 패턴–태틱 분석 대상은 Layers, Pipe-and-Filter, Blackboard, Broker, MVC,
Presentation–Abstraction–Control, Microkernel과 Reflection이다.
[SEI Modifiability Tactics 보고서 표 1](https://resources.sei.cmu.edu/asset_files/TechnicalReport/2007_005_001_14858.pdf)

### 3.8 보조 패턴

다음은 후보 전체를 규정하는 상위 스타일이 아니라 style을 실현하는 보조 패턴이다.

| 패턴 | 문제 1 적용 |
|---|---|
| Adapter | 표준 Linux DMA-BUF 호출을 cross-pVM protocol에 연결한다. |
| Proxy | 다른 kernel에 존재하는 backing buffer를 로컬 DMA-BUF처럼 표현한다. |
| Facade | Workload에는 단순한 export/import API만 노출한다. |
| Resource Pool | 사전 할당 buffer를 bounded slot으로 재사용한다. |
| Registry | 보호 handle과 backing page, endpoint, generation을 연결한다. |
| Watchdog | fence timeout이나 pVM 비정상 종료를 탐지한다. |

## 4. 품질속성별 태틱 전체 목록

### 4.1 성능 효율성·자원사용성 태틱

SEI의 성능 태틱은 resource demand 관리, resource 관리와 resource arbitration으로
분류된다.
[SEI, Reasoning Frameworks의 Performance Tactics](https://www.sei.cmu.edu/documents/749/2005_005_001_14588.pdf)

| 범주 | 태틱 | 문제 1 해석 |
|---|---|---|
| Demand | Manage Event Rate | 입력 폭주 시 capture rate 또는 publish rate를 제한한다. |
| Demand | Control Sampling Frequency | 최신 frame 우선 정책 등으로 sampling을 낮춘다. 요구 승인 전 기본 적용하지 않는다. |
| Demand | Reduce Computational Overhead | Host relay, payload copy와 불필요한 VM exit를 제거한다. |
| Demand | Bound Execution Time | bridge와 fence 처리 시간에 상한과 timeout을 둔다. |
| Demand | Bound Queue Size | outstanding buffer와 descriptor 수를 제한한다. |
| Demand | Increase Computational Efficiency | handle lookup과 reference update를 O(1)에 가깝게 유지한다. |
| Demand | Control Resource Demand | format·resolution·동시 frame 상한을 admission 조건으로 둔다. |
| Resource | Introduce Concurrency | Camera 생산과 AI 소비를 서로 다른 buffer에서 pipeline한다. |
| Resource | Maintain Multiple Copies | 읽기 복제본을 둔다. zero-copy와 충돌하므로 적용하지 않는다. |
| Resource | Increase Available Resources | buffer 또는 CPU를 늘린다. Embedded 상한 때문에 최후 수단이다. |
| Arbitration | Scheduling Policy | FIFO, deadline, latest-frame 등 slot 선택 정책을 둔다. |
| Arbitration | Synchronization Policy | `dma_fence`와 `dma_resv` 규칙으로 producer/consumer 순서를 정한다. |

Linux DMA-BUF는 exporter/importer, `dma_fence`, `dma_resv`, attachment와 reference
count를 제공한다. 공식 문서는 fence 완료가 cache flush 자체를 의미하지 않으며 CPU
access 전후 cache 처리는 별도로 필요하다고 명시한다.
[Linux DMA-BUF 공식 문서](https://docs.kernel.org/driver-api/dma-buf.html)

### 4.2 보안성 태틱

SEI의 보안·생존성 태틱은 예방, 탐지와 복구 관점에서 identification/authentication,
intrusion detection, recovery/adaptation 및 물리·논리·암호·시간 분리를 포함한다.
[SEI, Security and Survivability Reasoning Frameworks](https://www.sei.cmu.edu/documents/2050/2004_004_001_14330.pdf)

| 범주 | 태틱 | 문제 1 해석 |
|---|---|---|
| Resist | Identify / Authenticate | endpoint와 buffer handle의 발급 주체·generation을 검증한다. |
| Resist | Authorize / Limit Access | 등록된 Camera/AI pair만 backing page mapping을 요청할 수 있다. |
| Resist | Limit Exposure | Host와 제3 pVM에는 frame page를 mapping하지 않는다. |
| Resist | Logical Separation | pVM Stage-2와 보호 handle namespace를 분리한다. |
| Resist | Temporal Separation | fence 완료 전 consumer HW job을 제출하지 않는다. |
| Resist | Encrypt Data | 보호 메모리 내부 frame에는 기본 적용하지 않는다. threat model 변경 시 재검토한다. |
| Detect | Detect Invalid Input / Intrusion | 위조·stale handle, 잘못된 format/range를 거부하고 기록한다. |
| React | Revoke / Quarantine | pVM 종료 시 해당 generation의 handle과 mapping을 강제 만료한다. |
| Recover | Restore / Adapt | 안전한 buffer만 반환하고 불확실한 page는 격리 후 초기화한다. |

두 pVM을 동시에 mapping하는 최신 전제에서는 Camera와 AI 사이의 배타적 CPU
접근권은 보안 gate가 아니다. 보안 gate는 Host·제3 pVM 비매핑과 handle 위조 차단이다.

### 4.3 신뢰성·가용성·복구성 태틱

SEI의 가용성 catalog는 fault detection, fault recovery와 fault prevention으로
구성된다.
[SEI, Realizing and Refining Architectural Tactics: Availability](https://resources.sei.cmu.edu/asset_files/TechnicalReport/2009_005_001_15101.pdf)

| 범주 | 태틱 | 문제 1 적용 여부 |
|---|---|---|
| Detect | Ping/Echo | pVM channel health 확인에는 가능하지만 frame fast path에는 제외 |
| Detect | System Monitor / Watchdog | fence timeout, bridge health와 pVM 종료 탐지에 적용 |
| Detect | Exception Detection | invalid handle, mapping, attach와 fence 오류에 적용 |
| Detect | Voting | 같은 계산을 중복하지 않으므로 제외 |
| Recover | Retry | 일시적 descriptor 전달 오류에 bounded retry 적용 |
| Recover | Exception Handling | 오류를 호출자에게 반환하고 새 frame 제출을 중지 |
| Recover | Rollback | ref 등록과 mapping의 부분 실패를 이전 상태로 정리 |
| Recover | Active/Passive Redundancy / Spare | 비용이 커 기본 후보에서는 제외 |
| Recover | State Resynchronization | broker 후보 재시작 시 EL2 mapping ledger와 대조 |
| Recover | Reconfiguration | 실패한 endpoint generation을 폐기하고 새 endpoint에 재연결 |
| Prevent | Transaction | handle 등록·mapping·원격 ref 등록을 원자적 transaction으로 취급 |
| Prevent | Removal from Service | 불확실한 page나 broker를 격리 |
| Prevent | Predictive Model | 현재 근거가 없어 제외 |

reference count는 정상 `get/put` 수명을 관리하지만 pVM crash로 `put`이 실행되지 않는
경우를 해결하지 않는다. 따라서 generation 기반 forced detach는 가용성·복구 태틱으로
남긴다.

### 4.4 모듈성·적응성 태틱

SEI의 변경용이성 태틱은 cohesion 증가, coupling 감소와 binding time 지연으로
분류된다.
[SEI, Modifiability Tactics 보고서](https://resources.sei.cmu.edu/asset_files/TechnicalReport/2007_005_001_14858.pdf)

| 범주 | 태틱 | 문제 1 해석 |
|---|---|---|
| Increase Cohesion | Maintain Semantic Coherence | handle·reference·fence translation을 하나의 bridge에 배치한다. |
| Increase Cohesion | Abstract Common Services | exporter/importer 공통 protocol을 표준 adapter contract로 만든다. |
| Reduce Coupling | Use Encapsulation | backing page와 원격 reference 표현을 bridge 뒤에 숨긴다. |
| Reduce Coupling | Use a Wrapper | local DMA-BUF Proxy가 cross-pVM 차이를 감싼다. |
| Reduce Coupling | Restrict Communication Paths | Camera와 AI는 지정 bridge를 통해서만 metadata를 교환한다. |
| Reduce Coupling | Use an Intermediary | direct kernel dependency 대신 bridge 또는 broker를 둔다. |
| Defer Binding | Raise Abstraction Level | fd가 아니라 typed protected handle을 교환한다. |
| Defer Binding | Runtime Registration | endpoint와 format을 실행 시 registry에 등록할 수 있다. |
| Defer Binding | Configuration-Time Binding | Camera–AI pair와 buffer 정책을 manifest에서 결합한다. |
| Defer Binding | Start-Up-Time Binding | pipeline 시작 시 exporter/importer를 연결한다. |
| Defer Binding | Runtime Binding | 동적 N:M routing이 필요할 때만 broker 후보에서 사용한다. |

## 5. 문제 1에 선정한 스타일과 태틱

### 5.1 공통 적용

| 선정 항목 | 적용 이유 |
|---|---|
| Pipe-and-Filter | Camera→AI가 연속 frame stream을 처리하며 producer/consumer 병렬성이 필요하다. |
| Layered | Workload, local DMA-BUF, cross-pVM bridge와 보호 mapping 책임을 분리한다. |
| Adapter + Proxy | 서로 다른 kernel의 로컬 DMA-BUF 객체를 동일 backing page에 연결한다. |
| Shared Memory | payload copy 없이 동일 물리 페이지를 사용한다. |
| Event-based | fence와 ready/completion metadata만 비동기로 전달한다. |
| Reduce Computational Overhead | Host payload relay와 `memcpy`를 제거한다. |
| Bound Queue Size | 보호 메모리와 outstanding frame 수를 제한한다. |
| Synchronization Policy | DMA-BUF fence 규칙을 cross-pVM bridge까지 확장한다. |
| Limit Exposure / Logical Separation | Host와 제3 pVM의 mapping을 금지한다. |
| Encapsulation / Wrapper | pVM Workload에서 cross-pVM 구현 차이를 숨긴다. |
| Watchdog / Exception / Transaction | timeout, 부분 mapping 실패와 crash를 bounded cleanup으로 수렴시킨다. |

### 5.2 후보를 가르는 스타일

| 후보 | 주 스타일 | 구조 결정 |
|---|---|---|
| A | Direct Peer-to-Peer Pipe | pair별 bridge가 Camera exporter와 AI proxy를 직접 연결한다. |
| B | Protected Broker + Metadata Repository | 독립 보호 broker가 exporter, registry, reference와 fence relay를 중앙 제공한다. |

동적 개별 buffer와 사전 할당 pool은 두 후보 모두에서 선택할 수 있는 하위 resource
관리 태틱으로 내린다. 이번 상위 후보를 가르는 결정 변수로 사용하지 않는다.

## 6. 적용하지 않는 스타일·태틱

- Batch Sequential: streaming 지연과 pipeline concurrency 요구에 부적합하다.
- Blackboard: frame 전달은 opportunistic problem solving이 아니며 순서 예측이 더 중요하다.
- 프레임별 State-transition System: 두 pVM mapping을 유지하는 합의와 충돌한다.
- Maintain Multiple Copies: zero-copy gate와 충돌한다.
- payload Repository: 중앙 CPU mapping은 Host 비노출·최소 TCB와 성능에 불리하다.
- Publish–Subscribe fan-out: 현재 1:1 Camera→AI topology에 과도하다.
- Active Redundancy: 상주 메모리·vCPU 비용에 대한 요구 근거가 없다.
- 암호화된 in-memory frame: 현재 보호 메모리 threat model에서 필수성이 확인되지 않았다.

## 7. 공식 기술 전제와 실현 가능성

Linux DMA-BUF 표준은 같은 kernel이 관리하는 fd, `struct dma_buf`, `dma_resv`와
reference count를 전제로 한다. 서로 다른 pVM kernel 사이에는 protected handle,
proxy DMA-BUF, fence translation과 global backing-page lifetime protocol이 추가로
필요하다. 이는 표준을 그대로 사용하는 것이 아니라 표준의 exporter/importer 계약을
응용하는 것이다.

현재 Linux 공식 pKVM 문서는 기능을 experimental로 설명하고, pVM의 Host 공유
hypercall은 기술하지만 pVM 간 공유를 표준 기능으로 제시하지 않는다. 또한 해당 문서
버전에서 IOMMU 기반 DMA isolation은 미구현 상태다.
[Linux pKVM 공식 문서](https://docs.kernel.org/7.1/virt/kvm/arm/pkvm.html)

따라서 다음 항목은 두 후보의 공통 PoC gate다.

1. Host에 mapping하지 않고 동일 보호 page를 두 pVM Stage-2에 연결할 수 있는가?
2. 두 kernel의 local DMA-BUF와 동일 backing page를 proxy exporter/importer로 연결할 수 있는가?
3. fence와 cache coherency 의미를 pVM 경계에서 보존할 수 있는가?
4. pVM crash 시 정상 `put` 없이 원격 reference와 mapping을 강제 정리할 수 있는가?
5. Camera/AI HW가 해당 보호 page를 platform IOMMU/S2MPU 계약으로 DMA할 수 있는가?

PoC gate가 확인되기 전에는 두 후보 모두 실현 가능성 **확인 필요** 상태다.
