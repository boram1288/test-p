# 품질 위협 문제 2: 강한 격리로 인한 pVM 간 데이터 전달 공백

> 통합 문서: [과제의 필요성: 품질을 위협하는 세 가지 기술 문제](과제의_필요성_품질_위협_3가지_문제점.md)

## 1. 핵심 결론

pKVM은 Host와 각 pVM의 메모리를 강하게 분리하지만, Secure Camera pVM이 만든 대용량 프레임을 Secure AI pVM에
전달하려면 격리 경계를 선택적으로 열어야 한다. **Host 비노출, pVM 간 최소 권한, zero-copy, 버퍼 수명과 오류
회수를 동시에 만족하는 데이터 경로가 현재 과제 기준선에 없다.**

| 실제 실패 결과 | 구조적으로 어려운 이유 | 설계 결과로 증명해야 할 것 |
|---|---|---|
| Host 중계 시 영상 노출, 복사 시 지연·메모리 증가, 회수 실패 시 파이프라인 정지 | 격리를 유지하면서 매 프레임의 접근권만 빠르게 넘겨야 함 | Host 매핑 0회, 실제 프레임 복사 0회, 권한 중첩 0회, 지연 수치 |

## 2. 관련 시스템 전제와 용어

- **Host Linux**: 커널까지 침해될 수 있는 비신뢰 영역
- **pVM**: pKVM이 Host로부터 메모리를 보호하는 보안 VM
- **Stage-2 격리**: Hypervisor가 pVM 메모리의 CPU 접근권을 강제하는 기능
- **DMA-BUF**: Linux에서 HW와 SW가 대용량 버퍼를 공유하기 위한 객체
- **zero-copy**: 실제 프레임을 다른 메모리로 복사하지 않고 물리 페이지의 접근권만 넘기는 방식
- **DMA fence**: HW의 버퍼 읽기 또는 쓰기 완료 시점을 다른 주체와 동기화하는 수단

보호 대상은 카메라 원본 프레임, AI 입력 영상, 추론 중간 데이터와 해당 버퍼의 접근권이다.

## 3. 격리와 데이터 전달이 충돌하는 이유

Secure Vision AI는 다음 두 요구를 동시에 만족해야 한다.

- **격리 요구**: Camera pVM 메모리를 Host와 다른 pVM이 임의로 읽거나 쓸 수 없어야 한다.
- **파이프라인 요구**: Camera pVM의 프레임을 AI pVM이 매 프레임 소비해야 한다.

공유 메모리를 허용하는 순간 다음 정보를 명시적으로 관리해야 한다.

- 어떤 페이지 또는 DMA-BUF를 공유하는가?
- 송신자와 수신자는 누구인가?
- 읽기/쓰기 중 어떤 권한을 부여하는가?
- 권한은 언제 시작하고 언제 회수하는가?
- 공유 중 Host와 제3의 pVM은 확실히 배제되는가?
- 송신자 또는 수신자가 비정상 종료됐을 때 누가 버퍼를 회수하는가?

## 4. DMA-BUF가 VM 경계를 그대로 넘을 수 없는 이유

DMA-BUF file descriptor는 한 Linux 커널 인스턴스 안의 파일 객체를 가리킨다. Camera pVM의 fd 숫자를 AI pVM에
전달해도 AI pVM의 fd table에는 대응하는 객체가 없으므로 같은 버퍼를 참조하지 않는다.

pVM 간 전달의 실체는 fd 전달이 아니라 다음 두 단계다.

1. 송신 pVM의 DMA-BUF 뒤에 있는 물리 페이지의 접근권을 수신 pVM에 부여한다.
2. 수신 pVM이 전달받은 페이지를 자신의 DMA-BUF 객체로 import한다.

따라서 zero-copy를 구현하려면 DMA-BUF API뿐 아니라 pKVM의 Stage-2 매핑, SMMU/S2MPU DMA 권한, 캐시 동기화,
DMA fence와 버퍼 수명주기를 하나의 프로토콜로 묶어야 한다.

## 5. 복사 기반 전달의 성능 비용

1080p RGB24 프레임은 한 장당 약 6.22 MB이고 30 fps 입력은 약 186.6 MB/s다. 한 번의 전체 프레임 `memcpy`도
원본 read와 대상 write를 합쳐 최소 약 373.2 MB/s의 메모리 트래픽을 추가한다. Host를 거쳐 두 번 복사하면
추가 트래픽은 약 746.5 MB/s가 된다.

실제 값은 영상 포맷과 stride에 따라 달라지지만, 복사 횟수가 처리 지연, 메모리 대역폭과 전력에 직접 영향을
준다는 점은 동일하다.

```text
[복사 기반]
Camera pVM 버퍼
    └─복사─> Host 중계 버퍼
                 └─복사─> AI pVM 버퍼

문제: Host 노출 + 2회 복사 + 버퍼 3벌 + 캐시 오염

[필요한 의미론]
Camera pVM 버퍼
    └─소유권/접근권 전환─> AI pVM이 같은 물리 페이지 사용

목표: Host 비매핑 + 실제 프레임 memcpy 0회 + 명확한 소유권
```

## 6. 구체적인 실패 경로

### 6.1 Host 중계를 통한 노출

1. pVM 간 직접 전달 경로가 없어 Camera pVM이 Host 중계 버퍼로 프레임을 보낸다.
2. Host가 버퍼를 매핑하고 AI pVM으로 복사한다.
3. 침해된 Host가 전송 중인 원본 프레임을 읽거나 변조한다.

암호화 후 중계하면 기밀성은 높일 수 있지만 매 프레임 암복호화와 복사가 추가되어 성능 이점을 잠식한다.

### 6.2 영구 공유 영역의 과도한 권한

1. 성능을 위해 Camera pVM과 AI pVM에 큰 메모리 풀을 항상 동시에 매핑한다.
2. AI pVM이 처리할 필요가 없는 미래·과거 프레임까지 읽을 수 있다.
3. 한 pVM이 침해되면 공유 메모리 풀 전체가 공격 표면이 되고 이전 프레임이 장기간 남는다.

정적 공유는 매핑 전환 비용을 줄이지만 최소 권한과 시간 제한 권한을 약화한다.

### 6.3 소유권 전환 중 동시 접근

1. Camera HW가 버퍼 쓰기를 완료하기 전에 AI pVM에 읽기 권한을 부여한다.
2. AI pVM이 불완전한 프레임을 읽거나 Camera pVM이 AI 처리 중 버퍼를 재사용한다.
3. 영상 손상, 추론 오류 또는 확인 시점과 사용 시점 사이의 데이터 변경 문제가 발생한다.

DMA fence, 캐시 정리/무효화와 Stage-2 권한 전환의 순서가 일치해야 한다.

### 6.4 비정상 종료 시 권한과 메모리 누수

1. AI pVM이 프레임을 소유한 상태에서 비정상 종료된다.
2. 반환 신호가 오지 않아 Camera pVM이 버퍼를 재사용하지 못한다.
3. 강제 회수 중 DMA가 남아 있으면 회수된 메모리에 접근하고, 회수하지 않으면 버퍼 pool이 고갈된다.

시간 초과, 중복 반환, 순서 역전, pVM 재시작을 포함한 회수 프로토콜이 필요하다.

## 7. 위협받는 품질 속성

| 품질 속성 | 위협 내용 |
|---|---|
| 보안성 | Host 중계, 과도한 공유 범위, 권한 중첩으로 프레임이 비인가 주체에 노출됨 |
| 성능 | 반복 복사, 페이지 재매핑, TLB/캐시 동기화가 프레임 예산을 잠식함 |
| 자원 효율 | pVM별 복제 버퍼와 고정 공유 메모리 풀로 메모리 사용량이 증가함 |
| 신뢰성 | 버퍼 고갈, 중복 반환, 비정상 종료 후 회수 실패로 파이프라인이 정지함 |
| 확장성 | 송수신 pVM이 늘어날수록 점대점 경로와 권한 조합이 급증함 |

## 8. 핵심 트레이드오프

- 프레임마다 권한을 전환하면 최소 권한은 강화되지만 Stage-2/SMMU 전환 비용이 증가한다.
- 고정 공유 메모리 풀은 반복 구간의 성능에 유리하지만 공격 표면과 메모리 사용량이 증가한다.
- Host 중계는 구현이 쉽지만 Host 비노출 요구를 위반한다.
- 암호화 중계는 Host 기밀성을 보완하지만 복사와 암복호화 비용이 추가된다.

따라서 이 문제는 **보안성–성능–메모리 효율 간 아키텍처 트레이드오프**다.

## 9. 단순 접근으로 해결되지 않는 이유

| 단순 접근 | 한계 |
|---|---|
| fd 숫자를 다른 pVM에 전달 | fd는 각 커널 인스턴스에 로컬이므로 같은 DMA-BUF를 가리키지 않음 |
| Host가 프레임을 복사해 중계 | Host 비노출 요구 위반, 복사 지연과 메모리 대역폭 증가 |
| pVM마다 별도 버퍼 유지 | 메모리 사용량과 복사 횟수 증가 |
| 모든 pVM에 공유 메모리 풀 영구 매핑 | 최소 권한 위반, 침해 영향 범위 확대, 이전 데이터 노출 |
| 매 프레임 전체 매핑 재구성 | Stage-2/SMMU 전환과 TLB 동기화 비용이 실시간성을 해칠 수 있음 |

## 10. 설계가 반드시 보장해야 할 조건

1. 실제 프레임 payload 경로와 권한 판정용 제어 경로를 분리하고, 제어 명령이 프레임마다 발생해도 payload를 싣지 않는다.
2. Host는 제어를 중계할 수 있어도 프레임을 읽거나 매핑할 수 없어야 한다.
3. 버퍼마다 소유자, 접근 모드, 버퍼 재사용 세대 번호와 상태를 추적한다.
4. 상태는 최소한 `FREE → CAMERA_OWNED → IN_TRANSFER → AI_OWNED → RECLAIMING → FREE`로 관리한다.
5. 송신자의 쓰기 완료와 권한 회수 후 수신자의 접근권을 부여한다.
6. CPU Stage-2 권한과 Camera/AI HW의 DMA 권한을 같은 버퍼 상태 전이에 맞춰 변경한다.
7. DMA fence, 캐시 동기화와 메모리 접근 순서 보장을 프로토콜에 포함한다.
8. 시간 초과, pVM 비정상 종료, 중복 반환, 잘못된 식별자 입력 시 버퍼를 안전하게 회수하거나 폐기한다.
9. 새로운 pVM 쌍을 추가해도 Framework 코어를 수정하지 않도록 통신 종단점과 정책을 데이터로 기술한다.

## 11. 검증 지표

- 프레임 전달 과정의 실제 프레임 `memcpy` 호출 횟수: **0회**
- 전송 중 Host가 프레임 페이지를 매핑할 수 있었던 횟수: **0회**
- 버퍼 권한 중첩 및 무소유 상태 위반 횟수: **0회**
- 비인가 pVM 접근 차단률: **100%**
- 1080p 30 fps 지속 입력 시 프레임 유실, 전체 구간 지연과 비격리 구성 대비 성능 저하 측정
- pVM 비정상 종료/시간 초과 후 버퍼 회수율: **100%**
- 다중 pVM 운용 시 버퍼 풀 크기와 추가 메모리 사용량 측정

위 수치는 완료 결과가 아니라 설계 판정 기준이다. 실제 HW가 준비되면 PoC와 오류 주입 시험으로 측정하고,
준비 전에는 실행 기록 기반 시뮬레이션으로 후보 구조를 비교한다.
