# 슬라이드 작성 원칙

> 원본: [`SW_Architect_개인과제/슬라이드1.png`](SW_Architect_개인과제/슬라이드1.png)
>
> 슬라이드의 본문과 검토 주석을 의미 단위로 재구성하였다. 파란색 문구는 강조점, 빨간색 문구는 부정 리뷰,
> 노란색 문구는 작성 시 보완해야 할 검토 의견이다.

## 1. Architect

- 시스템 전체를 볼 수 있어야 한다.
- 중요하고 어려운 문제를 선정한다.

## 2. Architecting

- 중요하고, 얼마나 어려우며, 내가 해냈다는 것을 증명하는 설득의 과정이다.

### 검토 의견

- 설계의 목표가 눈에 보이는 결과를 제시해야 한다.
- 숫자를 통해 증명해야 한다.
- 결과가 나오지 않았다면 AI를 활용한 시뮬레이션 결과라도 보여야 한다.
- 두괄식으로 결과를 설명해야 한다.

## 3. 개발 목표

- 사업부의 색깔과 냄새가 있어야 한다.

### 검토 의견

- AI를 통한 개발 프로세스 개선, 자동화 또는 환경 구축 사례가 있으면 적극적으로 드러낸다.

## 4. 평가

- 새로운 문제(New problem)
- 독창성
- 트레이드오프(Trade-off) 분석
- 기여도와 파급력

## 5. 과제 배경

- Hooking으로 시작한다.
  - 사업에 기여하는 내용인가?
  - 정말 회사에서 두고두고 많은 사람이 느끼는 부분인가?
  - 문제가 정말 어려워서 초기설계를 지금껏 못했는가?

## 6. 과제 설명의 흐름

`과제 개요 → 요구사항 → 설계`

- 과제 개요: 설명을 위해 필요한 용어를 설명한다.
- 요구사항: 앞에서 설명한 용어만 사용한다.
- 설계: 해당 설계 용어에 대해서만 추가 설명한다.
- 전체 문서에서 기술 용어는 최대한 적게 사용한다.

## 7. 문제 정의

- 중요하고 어려운 문제인가?
- 복잡한 문제인가?
- 구조적으로 어려운 문제인가?
- 기술적인 문제가 무엇인가?
- 너무 추상화되어 어떤 기술적인 문제가 있는지 알아보기 어려우면 안 된다.
- 독창성 없이 문제가 쉽거나, 이미 알려져 해결책이 있는 문제는 안 된다.

## 8. 후보 구조

- 모든 부분에 나오는 모듈이 들어가면 좋다.
- 트레이드오프를 분석한다.
- Static을 적용한다.
- 새로운 기술을 사용한다.
- 설명하거나 증명할 수 있는 기술이어야 한다.
- 인정받을 수 있는 기술이어야 한다.

### 검토 의견

- 코너 케이스와 예외 상황 처리가 중요하다.
- Tatic(원문 표기)을 통해 다른 비기능적 요구사항을 만족하도록 설계한다.
- "상황이 어쩔 수 없어서 이러한 설계를 했다"는 설명에 머물면 안 된다.
- 영향 없는 설계는 시스템에 대한 이해도가 낮음을 의미한다.

## 9. 부정 리뷰 사례

- 근거가 약함
  - 중요하지 않은 품질 속성(QA)을 사용함
  - 중요하지 않은 품질 속성으로 최종안을 선택함
  - 구체적인 평가 결과가 없음
- 쉬운 문제
  - 평이한 수준의 선택에 그침
- 트레이드오프가 없어 Decision Point가 성립하지 않음
