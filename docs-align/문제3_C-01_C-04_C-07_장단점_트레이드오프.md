# 문제 3 후보구조 C-01·C-04·C-07 장단점과 트레이드오프

## 1. 문서 성격과 사용 제한

이 문서는 문제 3의 암호 처리 위치 후보인 C-01·C-04·C-07을 빠르게 비교하고 PoC 우선순위를
검토하기 위한 **비정식 설계공간 비교**다. 정확히 두 후보와 하나의 구조 결정 변수만 비교하도록
정한 [후보 구조 품질 평가 규칙](후보_구조_품질_평가_규칙.md)의 정식 Decision Point 평가는 아니다.

- 모든 별점은 Gate 통과 여부와 분리해 현재 구조가 만드는 상대적 유·불리를 평가한
  **구조 휴리스틱 잠정 점수**다.
- Gate가 `확인 필요`여도 모든 구조 평가 축에 별점을 부여한다. 다만 별점은 KPI 기반 확정 평가나
  Gate 실패를 상쇄하는 근거가 아니며, 최종 결정에는 Gate 결과와 실측값을 함께 사용해야 한다.
- 보안·최신성·복구 정확성·실현 가능성 자체는 합격 여부가 중요한 필수 Gate로 유지하고,
  이와 구별되는 TCB 크기·복구 구현 난도·장애 반경 등의 구조 특성에 별점을 부여한다.
- 승인된 가중치가 없으므로 총점·평균·가중합을 계산하지 않는다.
- C-01과 C-04는 실행 위치와 처리 단위가 함께 바뀌므로 정식 DP에서는 D-01~D-03으로 나눠야 한다.
- C-04와 C-07은 블록 암호 연결 책임을 EL1과 EL2 중 어디에 둘지 묻는 D-06으로 비교할 수 있다.
- C-01과 C-07도 실행 위치·처리 단위·`virtio-blk` 경계가 함께 바뀌므로 직접 정식 DP로 비교하지 않는다.

세부 구조와 공통 저장·RPMB 절차는
[문제 3 virtio-blk 공용 저장 공간의 암호화 설계 공간](문제3_virtio-blk_공용저장_암호화_설계공간.md)을
기준으로 한다.

RPMB 사용은 위 설계공간 문서에만 적용한 국소 전제이며 상위 Baseline 전체를 바꾸지 않는다. 기존 문제 3의
GP 호출 경로와 달리 C-07의 EL2 경로까지 정식 범위에 넣으려면 Baseline 변경 승인을 별도 Gate로 받아야 한다.

| 후보 | 암호 연결 책임과 실행 위치 | 처리 단위 | Application 영향 | Privileged 변경·장애 반경 | 현재 판정 |
|---|---|---|---|---|---|
| **C-01** | pVM EL0의 명시적 저장 API가 큰 자료 조각을 TEE에 맡김 | 자료·객체 조각 | 전용 API 적용 필요 | Kernel·EL2 변경이 작고 오류는 주로 해당 Workload 과정에 한정 | 대표 PoC 후보, Gate 미확정 |
| **C-04** | pVM EL1의 전용 Device Mapper 대상이 블록 묶음을 TEE에 맡김 | 논리 블록 묶음 | 일반 파일 API 유지 | pVM Kernel 저장 경로가 커지고 오류는 해당 pVM 저장 전체에 영향 | 대표 PoC 후보, Gate·성능 미확정 |
| **C-07** | EL2의 보호된 `virtio-blk` 경계가 버퍼 소유권과 TEE 처리를 연결 | `virtio-blk` 요청·블록 | 상위 Stack 변경 최소화 가능 | EL2·virtio가 커지고 오류 영향이 여러 pVM으로 확산 가능 | 조건부, EL2 범위 확대와 비표준 경로 승인 필요 |

공통적으로 평문 키는 TEE에만 두고, Host 경로에는 암호문만 전달해야 한다. UFS의 암호문과
인증값만으로는 이전 상태 되돌리기를 막을 수 없으므로 최신 버전과 `root_hash`는 RPMB에서
확정해야 한다.

## 3. 후보별 장점과 단점

### 3.1 C-01 — pVM EL0 명시적 저장 API

**장점**

- pVM Kernel과 EL2를 거의 바꾸지 않아 구현, 감사, 배포와 rollback 범위가 가장 작다.
- 자료 의미를 아는 EL0에서 큰 조각으로 묶기 쉬워 TEE 호출 고정 비용을 분산할 가능성이 크다.
- 자료·객체 단위의 버전 목록과 확정 단위를 명시적으로 설계하기 쉽다.
- 저장 구성요소 오류가 주로 해당 Workload 과정에 머물러 높은 권한 경로의 장애 반경이 작다.
- 초기 PoC에서 chunk 크기, TEE 호출 수와 처리량을 빠르게 조정하기 쉽다.

**단점**

- 모든 Workload가 전용 저장 API를 사용해야 하며 기존 POSIX 파일 I/O를 자동으로 보호하지 못한다.
- 민감 자료를 일반 파일 경로에 쓰는 API 우회·미적용을 개발 규칙과 시험으로 차단해야 한다.
- 공통 SDK와 format contract가 없으면 Workload마다 조각·버전·오류 처리 구현이 중복될 수 있다.
- Host가 파일 크기, 갱신 시각과 접근 모양 같은 일부 정보를 관찰할 수 있다.
- Workload 종류가 늘어날수록 API 통합·호환성·version 관리 비용이 증가한다.

**핵심 트레이드오프**

> 조각화와 TEE 암호 호출 책임을 Workload 가까운 EL0에 두면 큰 묶음 처리, 빠른 변경과 작은
> Privileged 변경 범위를 얻는
> 대신 일반 파일 사용의 투명성과 Workload 도입 확장성을 희생한다.

### 3.2 C-04 — pVM EL1 전용 Device Mapper 대상

**장점**

- Application과 파일시스템을 바꾸지 않고 일반 파일 경로의 모든 블록 I/O를 보호할 수 있다.
- 파일 이름과 파일시스템 관리 정보도 암호문 블록 안에 들어가 C-01보다 파일 수준 정보 노출을 줄일 수 있다.
- 공통 pVM Kernel image에 한 번 구현하면 여러 Workload에 같은 정책을 일관되게 적용할 수 있다.
- Device Mapper와 Linux TEE Kernel Client라는 알려진 구성요소를 출발점으로 사용할 수 있다.
- EL2는 메모리 격리와 호출 주체 확인에 머물러 Hypervisor TCB 확대를 피할 수 있다.

**단점**

- 전용 Target 또는 수정한 `dm-crypt` 경로, 비동기 TEE 연결, 분리 Buffer와 인증값 관리가 필요하다.
- 작은 블록마다 TEE를 호출하면 성능이 크게 저하될 수 있어 Batch 정책과 back-pressure가 필수다.
- 재시도·취소·OOM·I/O 순서, `FLUSH`와 RPMB 확정 순서, 비정상 종료 복구를 Kernel에서 검증해야 한다.
- 블록 변환 계층의 오류가 해당 pVM의 전체 저장 경로와 파일시스템 일관성에 영향을 줄 수 있다.
- Kernel version 변경마다 공통 블록 경로의 회귀시험과 장기 유지보수가 필요하다.
- 파일시스템 관리 정보는 암호문 안에 둘 수 있지만 Block 크기·시각·접근 모양은 Host에 남는다.

**핵심 트레이드오프**

> 암호 연결 책임을 pVM EL1의 블록 계층에 두면 Application 투명성과 일관된 강제를 얻는 대신
> Kernel 코드, crash consistency 상태기계와 해당 pVM 전체 저장 장애 영향을 늘린다.

### 3.3 C-07 — EL2 보호 `virtio-blk` 경계

**장점**

- Application, 파일시스템과 상위 블록 계층의 변경을 최소화할 수 있다.
- Host와 공유하기 전에 EL2가 Buffer 소유권을 강제해 Host에는 암호문만 보이는 공통 경계를 만들 수 있다.
- 보호 I/O primitive가 완성되면 여러 pVM에 같은 정책을 중앙에서 적용할 잠재력이 있다.
- 해당 보호 `virtio-blk` 경로 안에서 Guest가 암호 절차를 우회하지 못하게 하는 공통 집행점을 둘 수 있다.

**단점**

- 표준 `virtio-blk`만으로 성립하지 않으며 보호 Front-end, 새 공유 규약과 TEE 연결 확장이 필요하다.
- EL2가 요청 상태, Buffer 수명, 취소, Timeout과 오류 복구를 알아야 해 작은 EL2 원칙과 충돌한다.
- EL2 TCB·ABI·검증 범위가 커지고 결함의 장애 반경이 여러 pVM 또는 Platform으로 넓어질 수 있다.
- Page 소유권 전환, 보호·공유 Buffer, 추가 EL2 진입과 TEE 호출이 겹쳐 공용 성능 병목이 될 수 있다.
- EL2 갱신은 배포·rollback과 Debug가 어렵고, Platform·Kernel version 결합 위험이 가장 크다.
- 파일시스템 정보는 암호문 안에 둘 수 있지만 Block 크기·시각·접근 모양은 Host에 남는다.
- 재부팅 때 EL2의 in-flight 상태는 폐기·재설정하고, TEE/RPMB의 확정 상태를 기준으로 M-04와 M-11이
  복구를 조정하는 절차가 필요하다.

**핵심 트레이드오프**

> 보호 경계를 세 후보 중 가장 높은 Non-secure 공용 특권 계층인 EL2로 올리면 Guest Stack의 투명성과
> 중앙 집행은 좋아질 수 있지만, EL2 코드·상태·전환 비용과 여러 pVM에 미치는 장애 영향을 함께 키운다.

## 4. 필수 Gate — 구조 별점과 별도 판정

아래 `G-*`는 이 비정식 검토에서 추적하기 위한 임시 ID다. G-01~G-09는 설계공간 문서 §11.1과
문제 3 품질 위협, G-10~G-12는 설계공간 문서 §2·§6.8·§13에서 도출했다. 정식 DP로 승격할 때
Architecture 요구 ID에 연결해야 한다. `해당 없음`은 통과 판정이 아니라 그 후보에만 적용되지 않는
후보 전용 Gate라는 뜻이다.

| 임시 ID·Gate | 판정 기준 | C-01 | C-04 | C-07 | 검증 방법 |
|---|---|---|---|---|---|
| G-01 키·파생 비밀 TEE 한정 | pVM EL0/EL1·EL2·Host·UFS에서 관찰 0건 | 확인 필요 | 확인 필요 | 확인 필요 | Key canary와 dump·trace를 결합해 TEE 밖 전체 검사 |

| G-09 공통 실현 가능성 | 보호된 pVM↔TEE 호출, Buffer lifecycle과 RPMB 안전 갱신 확인 | 확인 필요 | 확인 필요 | 확인 필요 | 대표 SoC PoC와 장시간 오류 주입 |
| G-10 RPMB 국소 전제 승인 | 이 설계공간에서 RPMB 사용을 문제 3의 전제로 승인 | 확인 필요 | 확인 필요 | 확인 필요 | 상위 Architecture Baseline과 영향 Review |

Gate를 하나라도 실패한 후보는 선택 대상에서 제외한다. 그 경우에도 구조 비교와 재설계 방향을 위해
별점은 남기지만, 높은 별점으로 Gate 실패를 상쇄할 수 없다. C-07은 EL2 범위 확대가 승인되지 않으면
`확인 필요`가 아니라 `실패`로 바뀐다.

## 5. 구조 휴리스틱 잠정 별점

별이 많을수록 해당 평가 축에서 구조적으로 유리할 가능성이 크다는 뜻이다.

| 잠정 별점 | 의미 |
|---|---|
| 잠정 ★★★ | 후보 정의에 해당 속성을 직접 지원하는 Mechanism이 있고 핵심 경로의 미정 사항이 작음 |
| 잠정 ★★☆ | 일부 지원하지만 결과가 후보에서 고정하지 않은 구현 Parameter나 추가 상태 검증에 의존함 |
| 잠정 ★☆☆ | 후보 정의가 해당 속성에 불리하거나 큰 계층 간 완화 Mechanism이 아직 해결되지 않음 |

공통 측정값과 승인된 별점 구간은 아직 `TBD`이고 근거 유형은 모두 **구조적 추론**이다. 상세 설계가
없는 부분도 현재 구조가 필연적으로 요구하는 계층 변경·상태·전환을 기준으로 보수적으로 점수를 정했다.
같은 SoC, 암호 형식, 자료 크기·I/O 분포, TEE·CPU·Memory 할당을 사용하고 후보별로 허용되는 최적
Batch를 적용해 재평가해야 한다.

> 이 표는 세 후보의 구조 Profile을 한눈에 보기 위한 참고용이다. 특히 C-01↔C-07의 점수 차이는
> 정식 후보 선택 근거가 아니며, 정식 평가는 D-01~D-03과 D-06의 쌍별 표로 분해한다.
> 같은 책임 배치에서 파생된 축은 아래 `평가 묶음`으로 표시했다. 서로 독립된 근거가 아니므로 축의
> 개수나 별 개수를 세어 우열을 정하거나 합산하지 않는다.

|---|---|---:|---:|---:|---|

구조 별점은 모든 축에 부여했지만 정식 DP의 승인된 KPI 구간은 아니다. 정식 사용 전에는 요구 ID와
KPI 구간을 승인하고, 공통 TEE·M-04·M-11 비용과 후보별 추가 비용을 PoC에서 분리해야 한다.

## 6. 선택 상황별 해석

| 상황 | 우선 검토 후보 | 이유 | 반드시 닫을 위험 |
|---|---|---|---|
| 신규·소수 Workload이고 전용 API 적용 가능, 빠른 PoC와 최소 Privileged 변경 우선 | **C-01** | 큰 조각 Batch와 EL0 중심 구현으로 성능 조절·실험이 쉽다. | API 우회, Workload별 중복, Metadata 노출과 호환성 |
| 기존 Application 변경이 어렵고 일반 파일시스템 전체를 투명하게 보호 | **C-04** | Application·파일시스템을 유지하면서 EL2 확대를 피하는 균형안이다. | Kernel 변경량, Block Batch, `FLUSH`·RPMB 순서와 crash recovery |
| 보호 `virtio-blk`가 Platform Roadmap으로 이미 승인되고 EL2 공통 집행이 필수 | **C-07, 조건부** | Guest 상위 Stack 변경을 줄이고 공통 경계 집행이 가능하다. | EL2 TCB·ABI 예산, 비표준 규약, 전역 장애·병목과 rollback |

현 단계에서는 **C-01과 C-04를 서로 다른 장점을 확인할 대표 PoC로 병렬 비교**하는 것이 합리적이다.
세 후보에 같은 보안·최신성·복구 Gate를 적용하고, C-07은 보호 `virtio-blk`와 EL2 범위 확대가 별도
Platform 결정으로 승인된 뒤 D-06에서 C-04와 비교할 장기 후보로 둔다. 이는 확정 선택이 아니라
검증 순서 제안이다.

## 7. PoC에서 같은 조건으로 측정할 항목

1. 자료 크기와 Random/Sequential 비율별 처리량, p50·p95·최댓값 지연
2. TEE 호출 고정 비용, 호출/GiB와 Chunk·Block Batch 크기별 처리량
3. User↔Kernel↔EL2↔TEE 구간별 복사 횟수와 전환 횟수
4. pVM·TEE·EL2 Peak memory, CPU 사용량과 outstanding request 상태 수
5. `FLUSH`·암호문 기록·RPMB 확정 각 단계의 강제 종료 복구 결과
6. 암호문·인증값·위치표·version 변조, replay와 다른 Workload 연결 차단 결과
7. 특정 Workload 과정, Device Mapper Target과 EL2 모듈 장애 시 비관련 pVM 영향률
8. 신규 Workload 한 종을 추가할 때 변경 LoC, 작업 인일과 Core 무수정 통합 여부
