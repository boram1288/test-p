# 후보 구조 품질 평가 규칙

## 1. 목적

이 문서는 동일한 Decision Point의 후보 구조 두 개를 품질속성 관점에서 공정하게 평가하기 위한 규칙을 정의한다.
평가는 필수 조건 충족 여부를 먼저 판정하고, 선택 가능한 후보 사이의 정도 차이와 트레이드오프를 설명해야 한다.

## 2. 기본 원칙

1. 후보 구조는 정확히 두 개를 같은 문제, 범위, 요구사항과 제약사항으로 평가한다.
2. 책임, 실행 위치, 신뢰 경계 또는 자원 소유권이 다른 구조적 대안만 평가한다.
3. 문제 상황에 명시된 품질속성만 평가한다.
4. 모든 후보에 같은 KPI, 점수 기준, 측정 조건과 검증 방법을 적용한다.
5. 필수 조건인 gate와 후보 간 정도 차이를 나타내는 별점을 분리한다.
6. 평가 결과에는 구조적 원인, KPI 값과 근거를 함께 기록한다.
7. 근거가 없거나 승인되지 않은 수치와 점수를 임의로 만들지 않는다.
8. 한 후보가 모든 품질속성에서 우월하면 두 후보가 실제 트레이드오프를 이루는지 다시 확인한다.

## 3. 평가 시작 조건

다음 조건을 모두 만족한 뒤 품질 평가를 시작한다.

- 문제 상황에 요구사항, 요구 ID, 품질속성, 충돌 또는 위험이 명시되어 있다.
- baseline으로 고정된 범위와 이번 DP에서 변경할 수 있는 project-custom 범위가 구분되어 있다.
- 결정 질문이 하나의 구조적 결정 변수만 묻는다.
- 후보 A와 후보 B가 결정 질문의 두 선택 방향에 각각 답한다.
- 후보별 책임, 실행 위치, 신뢰 경계와 자원 소유권이 설명되어 있다.
- 후보별 동작 구조에 데이터 흐름과 제어 흐름이 설명되어 있다.
- 후보별 설명, 동작 구조와 PlantUML 다이어그램이 서로 일치한다.
- 두 후보에 적용할 검증 방법과 운영 조건이 동일하다.

조건을 충족하지 못하면 평가 수치를 작성하지 않고 후보 구조 또는 문제 상황을 먼저 보완한다.

## 4. 품질속성 및 평가 항목 도출

평가 항목은 문제 상황에서 요구한 품질속성과 직접 연결되어야 한다.

1. 문제 상황에 명시된 품질속성을 모두 추출한다.
2. 각 품질속성을 요구 ID, 상위 QAS, 충돌 또는 위험과 연결한다.
3. 필수 임계값은 gate로 분류한다.
4. gate를 통과한 후보 사이의 정도 차이를 나눌 수 있는 측정값은 KPI로 분류한다.
5. pass/fail로만 판단할 수 있는 항목에는 별점용 KPI를 만들지 않는다.
6. 실현 가능성은 별도의 gate로 다루며 품질속성으로 분류하지 않는다.

보안성, 성능, 확장성, 변경 용이성과 자원 효율은 평가 항목을 찾기 위한 기본 목록이다.
문제 상황에 없는 기본 품질속성은 평가에 추가하지 않는다.
문제 상황에 가용성, 신뢰성 등 다른 품질속성이 있으면 평가 항목에 포함한다.

다음 표로 평가 항목의 추적 관계를 먼저 정리한다.

| 품질속성 | 요구 ID / 상위 QAS | 문제의 충돌 또는 위험 | 평가 방식 | KPI 또는 gate 출처 |
|---|---|---|---|---|
| 예: 성능 | 요구 ID | 문제 상황의 근거 | gate / 별점 | 문서와 항목 |

## 5. 필수 gate 평가

gate는 후보가 선택 가능한 최소 자격을 충족하는지 판정한다.

### 5.1 gate 작성 규칙

- 보안 노출 0건, 비인가 접근 0건과 같은 필수 임계값을 pass/fail 기준으로 작성한다.
- 각 gate에 요구 ID, 판정 기준, 측정 조건, 검증 방법과 근거 출처를 기록한다.
- 판정값은 `통과`, `실패`, `확인 필요`만 사용한다.
- gate를 실패한 후보는 선택 가능한 후보에서 제외하고 비교 기준선으로만 남긴다.
- gate를 실패한 후보에는 별점을 부여하지 않는다.
- gate가 `확인 필요`이면 예상 별점을 잠정적으로 작성할 수 있지만 확정 점수로 표현하지 않는다.
- 두 후보가 같은 필수 gate를 실패하면 평가를 중단하고 결정 금지 사유로 기록한다.
- 동일한 품질속성을 gate와 별점으로 모두 평가할 수 있다. 이때 gate는 최소 자격을, 별점은 통과 후보 간 정도 차이를 판정한다.

### 5.2 실현 가능성 gate

핵심 기술이나 구조 메커니즘의 실현 가능성이 확인되지 않으면 `확인 필요`로 기록한다.
실현 가능성 gate가 닫히기 전에는 조건부 결정 이상으로 진행하지 않는다.
실현 가능성은 품질속성 점수에 포함하지 않는다.

### 5.3 gate 결과 표

| gate | 요구 ID | 판정 기준 | 측정 조건 / 검증 방법 | 후보 A | 후보 B | 근거 |
|---|---|---|---|---|---|---|
| 필수 품질 gate | 요구 ID | pass/fail 임계값 | 동일 조건 | 통과/실패/확인 필요 | 통과/실패/확인 필요 | 출처 또는 관찰 결과 |
| 실현 가능성 gate | 해당 항목 | 확인 조건 | PoC 또는 공식 문서 확인 | 통과/실패/확인 필요 | 통과/실패/확인 필요 | 확인 자료 |

## 6. KPI 정의 규칙

KPI는 후보 구조가 품질속성에 미치는 정도 차이를 측정할 수 있어야 한다.

### 6.1 KPI 필수 요소

각 KPI에는 다음 내용을 기록한다.

- 연결된 품질속성과 요구 ID
- 측정 대상과 측정 목적
- 계산식 또는 집계 방식
- 단위와 값의 방향성(클수록 유리하거나 작을수록 유리함)
- 입력 데이터, 부하, 자원 할당, 장애 조건 등 측정 환경
- 최소 gate와 별점 구간
- 수치 임계값의 출처
- 실제 측정, 계산, 시뮬레이션 또는 구조적 추론 중 근거 유형

O/X로만 판정되는 항목은 KPI로 사용하지 않는다.
후보별로 다른 환경이나 방식으로 측정한 값은 직접 비교하지 않는다.

### 6.2 KPI와 임계값의 출처

KPI 임계값은 `docs/03_qa_quality_scenarios.md`와 같은 상위 QAS의 gate 또는 KPI 예산에서 배분하고 출처를 기록한다.
상위 기준이 없거나 예산 배분이 승인되지 않았으면 `TBD`로 표시하고 임의 수치를 입력하지 않는다.

외부 표준과 공식 문서는 다음 목적으로만 사용한다.

- KPI 산정 방식의 근거
- 기술 메커니즘의 설명
- 핵심 기술의 실현 가능성 확인

외부 문서를 기존 결론의 정답으로 인용하지 않는다.
기술 메커니즘을 설명하는 출처와 수치 임계값을 뒷받침하는 출처를 구분한다.

### 6.3 KPI 정의 표

| 품질속성 | KPI | 계산식 / 단위 | 값의 방향 | 측정 조건 | gate | 별점 구간 | 출처 |
|---|---|---|---|---|---|---|---|
| 품질속성명 | 측정 지표 | 계산식과 단위 | 클수록/작을수록 유리 | 공통 환경 | 최소 임계값 | 1~3점 구간 | 상위 QAS 항목 |

## 7. 별점 평가 규칙

별점은 필수 gate를 통과한 후보 사이의 품질 차이를 나타낸다.
별 1~3개의 3점 척도만 사용한다.

### 7.1 점수 기준

| 점수 | 의미 | 작성 조건 |
|---|---|---|
| ★★★ | 승인된 우수 구간 | KPI가 사전에 정의한 우수 구간에 해당하고 근거가 있음 |
| ★★☆ | 승인된 보통 구간 | KPI가 최소 gate를 넘고 사전에 정의한 중간 구간에 해당함 |
| ★☆☆ | 승인된 최소 구간 | KPI가 최소 gate를 통과하지만 허용 범위 중 가장 불리한 구간에 해당함 |

점수 구간은 평가 결과를 보기 전에 정의한다.
두 후보의 차이를 만들기 위해 사후에 점수 구간을 조정하지 않는다.
두 후보의 KPI가 같은 구간이면 같은 점수를 부여한다.
상대적으로 더 낫다는 이유만으로 높은 점수를 부여하지 않는다.

### 7.2 점수 근거 작성

각 별점에는 다음 세 가지 근거를 함께 기록한다.

1. **측정 또는 예상 값**: KPI 값, 범위 또는 `TBD`
2. **구조적 원인**: 책임, 실행 위치, 신뢰 경계, 흐름 또는 자원 소유권의 차이
3. **근거 자료**: 시험 결과, 계산 내역, 시뮬레이션, PoC 관찰 또는 공식 문서

예상 값은 실제 측정값처럼 표현하지 않고 가정과 산정 방법을 적는다.
PoC 결과는 관찰 근거로만 사용하며 실제 운영 환경을 대표하는지 별도로 확인한다.
운영 환경을 대표하지 않는 PoC만으로 점수나 결정을 확정하지 않는다.

KPI 임계값 또는 점수 구간이 `TBD`이면 확정 별점을 부여하지 않는다.
구조적 예상 점수가 필요하면 `잠정 ★★☆`처럼 표시하고 가정, 미확인 항목과 검증 계획을 함께 적는다.

### 7.3 복수 KPI 처리

하나의 품질속성에 KPI가 여러 개이면 각 KPI를 별도로 평가한다.
상위 QAS나 사용자가 집계 방식과 가중치를 승인한 경우에만 품질속성 대표 점수를 계산한다.
승인된 집계 기준이 없으면 임의 평균, 합산 또는 가중치를 사용하지 않는다.
품질속성 우선순위와 가중치가 승인되지 않았으면 전체 총점을 계산하지 않는다.

### 7.4 후보 평가 표

| 품질속성 / KPI | 후보 A 값 | 후보 A 별점 | 후보 A 근거 | 후보 B 값 | 후보 B 별점 | 후보 B 근거 |
|---|---:|---|---|---:|---|---|
| KPI명 | 측정값/예상값/TBD | ★~★★★ 또는 잠정 | 구조적 원인과 자료 | 측정값/예상값/TBD | ★~★★★ 또는 잠정 | 구조적 원인과 자료 |

## 8. 비교 근거의 신뢰 수준

평가 근거에는 다음 유형 중 하나를 표시한다.

| 근거 유형 | 의미 | 평가 시 처리 |
|---|---|---|
| 운영 관찰 | 대표 운영 조건에서 측정한 결과 | 조건과 원시 결과를 연결하면 확정 근거로 사용 가능 |
| 대표 PoC | 운영 조건을 대표하도록 구성한 시험 결과 | 대표성의 근거와 오차 범위를 기록 |
| 제한 PoC | 일부 조건만 재현한 관찰 결과 | 잠정 근거로만 사용 |
| 계산/시뮬레이션 | 명시한 모델과 입력으로 산출한 결과 | 가정, 계산식과 검증 범위를 기록 |
| 구조적 추론 | 구조 차이에서 예상한 영향 | 잠정 점수로만 사용하고 검증 계획을 기록 |
| 확인 필요 | 근거가 아직 없음 | 확정 평가와 확정 결정에 사용 금지 |

자료의 존재만으로 근거가 충분하다고 판단하지 않는다.
자료가 해당 KPI, 후보 구조와 측정 조건을 직접 뒷받침하는지 확인한다.

## 9. 핵심 트레이드오프 작성 규칙

핵심 트레이드오프에는 비교 결과에서 후보의 우열이나 선택 가능성을 실제로 가르는 품질속성만 기록한다.
구조적 원인과 품질속성 영향을 한 문장 안에서 연결한다.

다음 형식을 사용한다.

> 특정 책임을 신뢰 영역으로 이동하면 비인가 접근 경로가 줄어 보안성이 높아진다. 대신 신뢰 영역의 코드와 검증 범위가 증가해 변경 용이성이 낮아진다.

다음 표현은 단독으로 사용하지 않는다.

- 가장 좋다.
- 효율적이다.
- 안전하다.
- 확장성이 높다.

두 후보가 함께 통과한 gate와 별점이 같은 품질속성은 핵심 트레이드오프에서 생략할 수 있다.
두 후보가 함께 실패한 gate는 생략하지 않고 결정 금지 사유로 기록한다.
`확인 필요`, `TBD` 또는 잠정 점수는 확정적인 트레이드오프로 서술하지 않는다.

## 10. 품질속성 정렬 규칙

문제 상황, 품질속성 비교와 핵심 트레이드오프 사이에서 같은 품질속성을 추적할 수 있어야 한다.

- 문제 상황의 모든 품질속성이 gate 또는 후보 평가 표에 있어야 한다.
- gate와 후보 평가 표의 모든 품질속성은 문제 상황의 요구사항, 충돌 또는 위험에서 도출되어야 한다.
- 세 섹션에서 원칙적으로 같은 품질속성 이름을 사용한다.
- 요구 ID나 표현이 다르면 품질속성 비교 표에 대응 관계를 기록한다.
- 실현 가능성 gate는 품질속성 정렬 대상에서 제외한다.
- 핵심 트레이드오프의 품질속성은 gate 또는 별점 결과에서 추적되어야 한다.
- 문제 상황에 없던 품질속성을 평가나 트레이드오프에서 새로 추가하지 않는다.

## 11. 평가 결과와 결정 상태

후보 평가가 작성되면 DP 상태를 `평가 중`으로 변경한다.
다음 조건을 모두 충족해야 평가 결과를 확정 근거로 사용할 수 있다.

- 두 후보에 같은 gate, KPI, 점수 구간과 검증 방법을 적용했다.
- 필수 gate가 모두 확인되었다.
- 핵심 기술의 실현 가능성이 확인되었다.
- `TBD`, `확인 필요`와 잠정 점수가 선택 근거에 남아 있지 않다.
- 품질속성 우선순위가 정해졌다.
- PoC 또는 시험 결과가 실제 운영 환경을 대표한다.
- 선행 DP가 확정되었다.

선행 조건을 전제로 후보를 선택하면 `조건부 결정`으로 기록한다.
근거와 검증 기준을 사용자가 승인한 뒤에만 `확정`으로 변경한다.
최종 결정자는 사용자이며, 검토 전에는 최종 결정란을 비워 둔다.

다음 경우에는 결정을 확정하지 않는다.

- 품질속성 우선순위가 정해지지 않았다.
- 핵심 기술의 실현 가능성이 확인되지 않았다.
- 두 후보가 같은 필수 gate를 실패했다.
- 후보 간 검증 기준이나 측정 조건이 다르다.
- 선행 DP가 미확정이다.
- PoC 결과가 실제 운영 환경을 대표하지 않는다.
- 사용자가 결정을 확인하지 않았다.

## 12. 작성 후 점검

1. 두 후보가 같은 문제, 범위, 요구사항과 제약사항을 전제로 하는가?
2. 문제 상황의 모든 품질속성이 gate 또는 별점 평가에 포함되었는가?
3. 평가 항목마다 요구 ID와 상위 QAS를 추적할 수 있는가?
4. gate가 별점보다 먼저 평가되었는가?
5. gate 실패 후보에 별점을 부여하지 않았는가?
6. KPI에 계산식, 단위, 방향성, 측정 조건과 출처가 있는가?
7. 승인되지 않은 KPI 임계값과 점수 구간을 `TBD`로 표시했는가?
8. 두 후보에 같은 KPI, 점수 구간과 검증 방법을 적용했는가?
9. 별점마다 KPI 값, 구조적 원인과 근거 자료가 있는가?
10. 예상 값과 실제 측정값, 잠정 점수와 확정 점수를 구분했는가?
11. 승인되지 않은 평균, 가중치 또는 전체 총점을 사용하지 않았는가?
12. 핵심 트레이드오프가 비교 결과와 구조적 원인에서 직접 도출되는가?
13. 공통 실패 gate, `확인 필요`와 `TBD`가 누락되거나 확정 표현으로 가려지지 않았는가?
14. 결정 금지 조건이 남아 있으면 평가 상태를 확정하지 않았는가?
