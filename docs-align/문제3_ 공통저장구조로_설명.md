# 문제 3: 공통 저장 구조 설명

## 1. 문서 목적

이 문서는 다음 내용을 구체적인 이름과 명령을 사용해 설명한다.

- 논리 블록 장치가 무엇인지
- pVM의 파일이 논리 블록 장치에 어떻게 기록되는지
- 논리 블록 장치가 Host의 실제 UFS 공간과 어떻게 연결되는지
- 공용 저장 공간이 무엇을 공유하고 무엇을 분리하는지
- 전체 논리 장치를 복사하지 않고 변경된 블록만 새로 기록하는 방법
- `P-01`부터 `P-04`까지의 공용 저장 구조가 어떻게 다른지

이 문서의 저장 구조는 [문제 3 설계 공간](./문제3_virtio-blk_공용저장_암호화_설계공간.md)의 4절을 풀어서 설명한 것이다.

## 2. 먼저 구분할 대상

### 2.1 pVM 안의 파일

Workload가 직접 사용하는 파일이다.

```text
/data/config.json
/data/models/detection.bin
/data/results/result-0001.dat
```

이 파일 이름과 디렉터리는 pVM의 파일시스템이 관리한다.

### 2.2 논리 블록 장치

pVM에 일정한 크기의 블록 주소 범위를 제공하는 장치다. 다음 예에서는 Camera Workload에 100GB 장치를 제공한다.

```text
Workload                 camera
storage_id               camera-storage-01
pVM에서 보이는 장치      /dev/vdb
논리 장치 크기           100GB
파일시스템 마운트 위치   /data
```

논리 블록 장치는 실제 UFS의 연속된 100GB 구역을 뜻하지 않는다. pVM에는 100GB 주소 범위가 보이지만, Host는 그중 실제로 기록된 블록에 대해서만 UFS 공간을 할당할 수 있다.

### 2.3 Host의 공용 저장 공간

Host가 여러 Workload의 암호문을 저장하기 위해 관리하는 UFS 물리 공간이다.

```text
UFS 공용 저장 공간
├── Camera Workload에 할당된 물리 블록
├── AI Workload에 할당된 물리 블록
└── 아직 할당되지 않은 물리 블록
```

여기서 공용이라는 말은 다음 뜻이다.

- 여러 Workload가 하나의 물리 공간 관리 체계를 사용한다.
- 각 Workload가 실제로 기록할 때 필요한 물리 블록을 할당받는다.
- Workload마다 최대 논리 용량만큼 물리 공간을 미리 확보하지 않는다.

공용이라는 말이 다음을 뜻하지는 않는다.

- 여러 pVM이 같은 파일시스템을 동시에 마운트하지 않는다.
- 여러 Workload가 같은 논리 블록 장치를 함께 사용하지 않는다.
- 한 Workload가 다른 Workload의 자료를 읽을 수 있도록 허용하지 않는다.

## 3. 전체 연결 관계

```text
pVM의 파일
  /data/config.json
  /data/models/detection.bin
        ↓
pVM 파일시스템
  ext4 또는 선택한 파일시스템
        ↓
pVM의 논리 블록 번호
  /dev/vdb의 블록 100, 101, 1000, ...
        ↓
pVM의 암호 처리 계층
  평문 블록 → 암호문과 인증값
        ↓
virtio-blk
  storage_id와 논리 블록 요청 전달
        ↓
Host의 Workload별 논리 장치
  camera-storage-01
        ↓
Host의 위치표
  storage_id + 논리 블록 번호 → UFS 저장 위치
        ↓
UFS 공용 저장 공간
  암호문, 인증값과 버전별 위치표
```

`virtio-blk`는 `/data/config.json`이라는 파일 이름을 전달하지 않는다. 읽거나 쓸 논리 블록 번호와 블록 자료를 전달한다.

## 4. pVM 파일과 논리 블록의 관계

Camera Workload의 `/dev/vdb`를 `/data`에 마운트했다고 가정한다. pVM 파일시스템은 파일 내용을 다음처럼 논리 블록에 배치할 수 있다.

| pVM 파일 | pVM 논리 블록 예시 |
|---|---|
| `/data/config.json` | 100~103 |
| `/data/models/detection.bin` | 1000~5095 |
| `/data/results/result-0001.dat` | 8000~8255 |

파일 하나가 반드시 연속된 논리 블록만 사용하는 것은 아니다. 파일시스템 상태와 파일 변경에 따라 여러 위치로 나뉠 수 있다.

관계는 다음과 같다.

```text
pVM 파일 여러 개
        ↓
pVM 파일시스템 하나
        ↓
Workload별 논리 블록 장치 하나
```

따라서 pVM 파일 하나와 논리 블록 장치 하나가 직접 대응하지 않는다. 여러 pVM 파일이 하나의 논리 블록 장치 안에 들어간다.

## 5. 논리 블록과 UFS 물리 블록의 관계

설명을 위해 Host가 4KiB 단위로 공간을 관리한다고 가정한다.

| `storage_id` | 논리 블록 | UFS 물리 블록 예시 |
|---|---:|---:|
| `camera-storage-01` | 100 | 92001 |
| `camera-storage-01` | 101 | 92002 |
| `camera-storage-01` | 1000 | 31500 |
| `ai-storage-01` | 100 | 72000 |

Camera와 AI가 모두 논리 블록 100을 사용해도 `storage_id`가 다르므로 서로 다른 UFS 물리 블록에 연결된다.

```text
(camera-storage-01, 논리 블록 100) → UFS 물리 블록 92001
(ai-storage-01, 논리 블록 100)     → UFS 물리 블록 72000
```

pVM은 UFS 물리 블록 번호를 알 필요가 없다. pVM은 자신의 논리 블록 번호만 사용한다. 실제 UFS 위치는 Host가 바꿀 수 있다.

Host는 비신뢰 영역이므로 Host의 위치표 자체를 보안 판단의 근거로 사용하지 않는다. TEE는 다음 값을 암호문과 결합해 확인해야 한다.

- Workload 식별자
- `storage_id`
- 논리 블록 번호
- 자료 버전
- 키 세대

TEE는 버전별 위치표의 최상위 확인값과 최신 버전을 RPMB에 기록한다. Host가 다른 Workload의 암호문이나 이전 버전의 위치표를 대신 제공하면 확인에 실패해야 한다.

## 6. 실제 쓰기 과정

Camera Workload가 `/data/config.json`을 변경해 논리 블록 100의 내용이 달라졌다고 가정한다.

1. pVM 파일시스템이 `/data/config.json` 변경을 논리 블록 100의 쓰기 요청으로 바꾼다.
2. pVM의 암호 처리 계층이 평문 블록을 TEE에 맡긴다.
3. TEE가 암호문과 인증값을 만든다.
4. `virtio-blk`가 논리 블록 100의 쓰기 요청과 암호문을 Host에 전달한다.
5. Host가 공용 UFS 공간에서 새 물리 블록 94500을 할당한다.
6. 새 위치표가 Camera의 논리 블록 100을 물리 블록 94500에 연결한다.
7. pVM이 `FLUSH` 완료 응답과 새 위치표의 확인값을 TEE에 전달한다.
8. TEE가 새 버전과 위치표 확인값을 RPMB에 확정한다.
9. 확정 뒤 이전 물리 블록 92001을 회수한다.

변경 전과 변경 중의 위치표는 다음과 같다.

```text
변경 전 확정 상태
(camera-storage-01, 논리 블록 100, 버전 41) → UFS 물리 블록 92001

버전 42 기록 중
(camera-storage-01, 논리 블록 100, 버전 41) → UFS 물리 블록 92001
(camera-storage-01, 논리 블록 100, 버전 42) → UFS 물리 블록 94500

버전 42 RPMB 확정 뒤
(camera-storage-01, 논리 블록 100, 버전 42) → UFS 물리 블록 94500
물리 블록 92001은 회수 가능
```

## 7. 변경된 블록만 추가로 기록한다는 뜻

논리 장치가 100GB이고 이번 변경으로 8MB의 블록만 달라졌다고 가정한다.

- 이전 확정 상태의 100GB 논리 주소 범위는 그대로 유지한다.
- 실제로 달라진 8MB의 블록만 새 UFS 위치에 기록한다.
- 새 위치표와 인증값을 함께 기록한다.
- RPMB 확정 전까지 바뀐 부분의 이전 블록 8MB를 유지한다.
- RPMB 확정 뒤 이전 8MB를 회수한다.

추가로 필요한 공간은 두 번째 100GB 물리 볼륨이 아니다. 주로 다음 항목에 해당하는 공간이 필요하다.

- 변경된 블록의 새 암호문
- 새 인증값
- 새 위치표
- 확정 전까지 유지하는 변경 부분의 이전 블록

이 동작은 일반 희소 파일을 만드는 것만으로 자동 제공되지 않는다. 선택한 공용 저장 구조에서 새 위치 기록, 위치표 전환, RPMB 확정과 이전 블록 회수 순서를 구현해야 한다.

## 8. `P-01`: Device Mapper thin provisioning

`P-01`에서는 Host 파일을 만들지 않고, Device Mapper의 thin 논리 장치를 pVM에 제공한다.

아래 명령은 논리 장치와 실제 저장 공간의 연결을 보여 주는 시험 예시다. 이 명령만으로 TEE 암호 처리와 RPMB 확정 기능이 만들어지는 것은 아니다. 실제 구조에는 문제 3 설계 공간의 암호 처리 후보와 안전한 확정 절차를 함께 구현해야 한다.

```text
pVM /dev/vdb
        ↓ virtio-blk
Host /dev/pvm_vg/camera_storage_01
        ↓ Device Mapper 위치표
Host pvm_vg/pvm_pool
        ↓
UFS 물리 블록
```

이미 `pvm_vg/pvm_pool`이라는 thin pool이 준비되어 있다면 Camera용 100GB 논리 장치를 만드는 명령 예시는 다음과 같다.

```bash
sudo lvcreate -V 100G -T pvm_vg/pvm_pool -n camera_storage_01
sudo lvs -o lv_name,lv_size,pool_lv,data_percent,metadata_percent pvm_vg
```

이때 `/dev/pvm_vg/camera_storage_01`의 논리 크기는 100GB지만, thin pool에서는 실제로 기록한 블록에 대해서만 물리 공간을 사용한다.

실제 제품에서 thin pool을 만드는 명령은 UFS 분할과 장치 구성에 따라 달라지며 `pvcreate`, `vgcreate`는 대상 장치의 기존 자료를 지울 수 있다. 따라서 이 문서에는 실제 UFS 장치를 초기화하는 명령을 넣지 않는다.

## 9. `P-02`: Host 희소 저장 파일

`P-02`에서는 Workload의 논리 블록 장치 하나가 Host의 희소 저장 파일 하나와 연결된다.

```text
pVM /dev/vdb
        ↓ virtio-blk
Host /var/lib/pvm-storage/camera-storage-01/data.raw
        ↓ Host 파일시스템
UFS 물리 블록
```

### 9.1 Host에서 저장 파일 생성

다음 명령은 논리 크기가 100GB인 희소 파일을 만든다.

```bash
sudo install -d -m 0700 /var/lib/pvm-storage/camera-storage-01
sudo truncate -s 100G /var/lib/pvm-storage/camera-storage-01/data.raw
sudo ls -lh /var/lib/pvm-storage/camera-storage-01/data.raw
sudo du -h /var/lib/pvm-storage/camera-storage-01/data.raw
```

`ls -lh`에는 논리 크기 100GB가 표시된다. `du -h`에는 실제로 할당된 UFS 공간이 표시된다. 처음에는 대부분의 영역이 기록되지 않았으므로 실제 사용량이 매우 작다.

### 9.2 QEMU 시험 환경에서 virtio-blk로 연결

다음은 저장 경로를 설명하기 위한 QEMU 시험 명령의 저장장치 부분이다. 실제 pKVM 실행 도구에 맞게 바꿔야 한다.

```bash
sudo qemu-system-aarch64 \
  ... \
  -blockdev driver=file,node-name=camera_file,filename=/var/lib/pvm-storage/camera-storage-01/data.raw \
  -blockdev driver=raw,node-name=camera_raw,file=camera_file \
  -device virtio-blk-pci,drive=camera_raw,serial=camera-storage-01
```

이 명령의 연결 관계는 다음과 같다.

```text
camera-storage-01이라는 virtio-blk 장치
        ↓
camera_raw 블록 처리 노드
        ↓
camera_file 파일 처리 노드
        ↓
/var/lib/pvm-storage/camera-storage-01/data.raw
```

### 9.3 pVM에서 처음 파일시스템 생성

다음 명령에서 `/dev/vdb`가 새로 연결한 빈 장치인지 `lsblk`로 먼저 확인해야 한다. `mkfs.ext4`는 대상 장치의 기존 파일시스템을 지우므로 최초 생성 때만 실행한다.

```bash
lsblk -o NAME,SIZE,TYPE,SERIAL,FSTYPE,MOUNTPOINTS
sudo mkfs.ext4 -L camera-data /dev/vdb
sudo install -d -m 0700 /data
sudo mount /dev/disk/by-label/camera-data /data
```

pVM 세대가 바뀌어 기존 장치를 다시 연결할 때는 `mkfs.ext4`를 실행하지 않는다. 기존 파일시스템을 그대로 마운트한다.

```bash
lsblk -o NAME,SIZE,TYPE,SERIAL,FSTYPE,MOUNTPOINTS
sudo mount /dev/disk/by-label/camera-data /data
```

### 9.4 pVM에서 실제 파일 기록

```bash
sudo install -d -m 0700 /data/models /data/results
printf '%s\n' '{"model":"detection-v3","version":42}' | sudo tee /data/config.json
sudo dd if=/dev/urandom of=/data/models/detection.bin bs=1M count=64 conv=fsync status=progress
sudo sync
```

pVM에서는 두 개의 파일이 보인다.

```text
/data/config.json
/data/models/detection.bin
```

Host에는 두 파일이 각각 생기지 않는다. Host에는 다음 파일 하나만 있다.

```text
/var/lib/pvm-storage/camera-storage-01/data.raw
```

pVM의 두 파일은 pVM 파일시스템에 의해 여러 논리 블록으로 바뀌어 `data.raw`의 여러 위치에 기록된다. `mkfs.ext4`가 기록한 파일시스템 관리 정보도 공간을 사용하므로 Host의 실제 사용량은 파일 크기의 단순 합계보다 클 수 있다.

설명을 위해 4KiB 블록을 가정하면 다음처럼 계산할 수 있다.

```text
pVM 논리 블록 0   → data.raw의 0~4095 바이트
pVM 논리 블록 1   → data.raw의 4096~8191 바이트
pVM 논리 블록 100 → data.raw의 409600~413695 바이트
```

그 뒤 Host 파일시스템이 `data.raw`에서 실제로 기록된 범위를 UFS 물리 블록에 연결한다.

### 9.5 희소 파일만으로 해결되지 않는 부분

일반 raw 희소 파일의 기존 위치를 다시 쓰면 이전 내용이 덮어써진다. 따라서 다음 기능은 희소 파일과 별도로 필요하다.

- 변경 블록을 새 위치에 기록하는 기능
- 버전별 위치표 또는 변경 블록 목록
- RPMB에 새 버전을 확정하는 순서
- 확정 전 중단되면 이전 버전을 선택하는 복구 절차
- 확정 뒤 이전 블록을 회수하는 절차

이를 `M-11 (Secure Persistent Storage)`이 직접 구현하거나, 변경된 범위만 별도 저장하는 Host 블록 기능을 조합할 수 있다. 어떤 경우에도 Host의 확정 주장만 믿지 않고 TEE와 RPMB가 최신 상태를 결정해야 한다.

## 10. `P-03`: M-11 공용 블록 묶음 저장소

`P-03`에서는 `M-11 (Secure Persistent Storage)`이 위치표를 직접 관리한다.

```text
storage_id: camera-storage-01

논리 블록 100, 버전 41 → chunk-000092001
논리 블록 100, 버전 42 → chunk-000094500
논리 블록 101, 버전 42 → chunk-000092002
```

UFS에는 다음과 같은 내부 이름이나 이에 해당하는 블록 묶음이 있을 수 있다.

```text
/var/lib/pvm-storage/pool/chunks/chunk-000092001
/var/lib/pvm-storage/pool/chunks/chunk-000094500
/var/lib/pvm-storage/pool/manifests/camera-storage-01-v42.manifest
```

이 파일 이름은 구현 예시일 뿐이다. 실제 구현은 UFS의 큰 저장 파일 하나나 전용 블록 영역 안에서 조각 번호만 관리할 수도 있다.

`P-03`은 변경 블록과 버전별 위치표를 직접 관리하기 쉽다. 대신 위치표 손상 복구, 빈 공간 관리와 여러 번 실행해도 안전한 블록 회수 기능을 새로 구현해야 한다.

## 11. `P-04`: 공용 기본 이미지와 Workload별 변경 블록

`P-04`는 여러 Workload가 같은 읽기 전용 초기 자료를 사용할 때만 적용한다.

```text
공용 읽기 전용 기본 이미지
/var/lib/pvm-storage/base/camera-model-v3.img

Camera Workload 변경 블록
/var/lib/pvm-storage/delta/camera-storage-01.delta

AI Workload 변경 블록
/var/lib/pvm-storage/delta/ai-storage-01.delta
```

각 Workload의 논리 장치는 기본 이미지와 자신의 변경 블록을 합친 결과를 보여준다. 기본 이미지는 서명이나 고정된 확인값으로 검증해야 한다. Workload가 만든 쓰기 가능한 영구 자료 전체를 서로 공유하는 방식은 아니다.

## 12. pVM 세대가 바뀔 때 다시 연결

Camera pVM의 첫 번째 세대가 삭제되어도 다음 상태는 남는다.

```text
stable_workload_id: camera-workload
storage_id: camera-storage-01
Host 저장 대상: camera_storage_01 thin LV 또는 data.raw
TEE/RPMB 상태: 최신 확정 버전과 위치표 확인값
```

새 Camera pVM 세대가 생성되면 다음 순서로 다시 연결한다.

1. `M-05 (Workload Loader / Verifier)`가 Workload를 확인한다.
2. `M-02 (pVM Lifecycle Manager)`가 새 pVM 세대를 만든다.
3. `M-11 (Secure Persistent Storage)`이 `camera-storage-01`에 해당하는 기존 논리 장치를 찾는다.
4. Host가 그 논리 장치를 새 pVM에 `virtio-blk`로 연결한다.
5. TEE가 RPMB의 최신 버전과 UFS 위치표의 확인값을 비교한다.
6. 확인에 성공하면 pVM이 기존 파일시스템을 마운트한다.

새 pVM은 장치 이름이 `/dev/vdb`가 아닌 다른 이름으로 보일 수 있으므로 장치 이름만 믿지 않는다. `virtio-blk` 일련번호, 파일시스템 UUID나 레이블과 `storage_id`를 함께 사용해 대상 장치를 확인해야 한다.

## 13. 예시 용량

공용 UFS 공간의 실제 사용량을 다음과 같이 가정한다.

| Workload | pVM에 보이는 논리 크기 | 실제 기록한 암호문 | UFS에서 사용하는 주된 공간 |
|---|---:|---:|---:|
| Camera | 100GB | 20GB | 약 20GB와 관리 정보 |
| AI | 100GB | 5GB | 약 5GB와 관리 정보 |
| Navigation | 100GB | 30GB | 약 30GB와 관리 정보 |

세 Workload에는 합계 300GB의 논리 주소 범위가 보인다. 그러나 정상 상태의 실제 UFS 사용량은 약 55GB와 관리 정보다. 갱신 중에는 변경된 블록의 이전판과 새판이 잠시 함께 존재할 수 있다.

## 14. 핵심 정리

- 논리 블록 장치는 pVM에 제공하는 블록 주소 범위다.
- 논리 블록 장치는 실제 UFS의 고정된 연속 영역이 아니다.
- pVM의 여러 파일은 파일시스템을 통해 하나의 논리 블록 장치에 기록된다.
- `virtio-blk`는 파일 이름이 아니라 논리 블록 요청을 전달한다.
- Host는 `storage_id + 논리 블록 번호`를 UFS 저장 위치에 연결한다.
- 공용 저장 공간은 여러 Workload가 물리 공간 할당 체계를 함께 사용한다는 뜻이다.
- 각 Workload의 논리 장치, `storage_id`, 암호문과 접근 권한은 분리된다.
- `P-01`은 Device Mapper 위치표로, `P-02`는 Host 희소 파일로 논리 장치를 UFS에 연결한다.
- `P-03`은 `M-11 (Secure Persistent Storage)`이 블록 묶음과 위치표를 직접 관리한다.
- `P-04`는 검증된 읽기 전용 기본 이미지와 Workload별 변경 블록을 합친다.
- 안전한 갱신에서는 전체 논리 장치를 복사하지 않고 변경된 블록만 새 위치에 기록한다.
- TEE와 RPMB가 최신 버전을 확정한 뒤에만 이전 블록을 회수한다.
- Host의 위치표는 신뢰하지 않으며, TEE가 Workload·논리 위치·버전 결합과 RPMB의 확인값으로 검증한다.
