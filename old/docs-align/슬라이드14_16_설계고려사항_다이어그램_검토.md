# 슬라이드 14~16 설계 고려 사항과 다이어그램 검토

## 1. 목적과 범위

이 문서는 다음 슬라이드의 `설계 고려 사항` 문구와 다이어그램을 검토하고, 슬라이드 16의 보강안을 구체화한다.

- 슬라이드 14: `DP1: 성능과 기밀성이 보장되는 pVM간 Data 공유`
- 슬라이드 15: `DP2: HW IP 안전 공유 및 소유권 전환`
- 슬라이드 16: `DP3: 안전한 GP 기반 Secure OS 자산 관리`

슬라이드의 DP 번호와 현행 문서의 문제·DP 번호는 다르므로 제목과 결정 내용으로 연결했다.

| 슬라이드 | 품질 위협 문서 | 현행 DP 계열 |
|---|---|---|
| 14, pVM 간 Data 공유 | `품질위협_문제2_pVM간_데이터전달.md` | DP-03, DP-03-A/B/C |
| 15, HW IP 공유 | `품질위협_문제1_HW공유_기밀데이터_노출.md` | DP-04, DP-07 |
| 16, Secure OS 자산 관리 | `품질위협_문제3_pVM수명_암호화파일_유실.md` | DP-06 |

후보 구조를 설명하는 다음 슬라이드와 역할이 겹치지 않도록, 이 문서의 다이어그램은 모든 후보가 만족해야 할
불변조건과 실패 경로만 표현한다.

## 2. 핵심 결론

1. 슬라이드 16의 세 문장은 방향은 맞지만 품질 속성명과 확장 단위가 현행 요구사항과 어긋난다.
   - `신뢰성`은 구체적으로 `복구성`으로 표현한다.
   - 다른 Workload의 연결 차단은 단순 기밀성보다 `접근권 강제`가 직접적인 품질 속성이다.
   - 확장 단위는 새 pVM 인스턴스가 아니라 `신규 Workload와 저장 정책`이다.
2. 슬라이드 16은 세 문장을 세로 카드로 나누고 `수명주기`, `신원 결합 검증`, `정책 기반 확장`을 각각 작은
   다이어그램으로 설명하는 구성이 가장 읽기 쉽다.
3. 슬라이드 14와 15는 정상 경로 중심으로 구성돼 있어 오류·시간 초과·비정상 종료 시의 안전한 격리와 복구가
   보이지 않는다. 기존 그림에 빨간 실패 분기를 추가하는 것이 최우선 보강 사항이다.
4. 저장 서비스, 공유 버퍼 자료구조와 HW 스케줄러의 실행 위치는 아직 후보 비교 대상이므로 문제 정의 슬라이드에서
   특정 위치나 구현으로 확정하면 안 된다.
5. 슬라이드 16 하단 결론은 DP1의 `pVM간 Data 공유 구조 필요` 문구가 복사된 상태이므로 DP3의 영구 저장 문제에
   맞게 교정해야 한다.

## 3. 슬라이드 16 상세 보강안

### 3.1 문장 정리

| 기존 문장 | 검토 결과 | 슬라이드용 최종 문장 | 연결 품질 속성 |
|---|---|---|---|
| 암호화 파일의 수명은 pVM의 수명으로부터 독립적이어야 한다. | 방향은 정확하지만 재연결과 회수 시점이 보이지 않는다. | **pVM 삭제 후에도 암호화 파일 유지·재연결** | QA-07 복구성 |
| 다른 Workload의 연결 요청을 차단해야 한다. | `기밀성`보다 Workload 신원과 저장 공간의 결합을 강제하는 조건이다. | **Workload ID가 다른 연결 요청 차단** | QA-04 무결성 및 접근권 강제 |
| 기존 모듈 수정 없이 새로운 pVM을 추가할 수 있어야 한다. | pVM 재생성은 운용 수명주기이고, 설계 확장 단위는 Workload와 저장 정책이다. | **정책 등록만으로 신규 Workload 추가** | QA-08 적응성·모듈성 |

### 3.2 카드 1 — pVM 수명과 저장 수명 분리

목적은 pVM 삭제와 Workload 폐기가 서로 다른 사건임을 한눈에 보여 주는 것이다.

```text
Workload-A 실행

┌────────┐       pVM 삭제       ┌────────┐
│ pVM #1 │ ──────────X────────→ │ pVM #2 │
└───┬────┘                       └───┬────┘
    │ 저장                           │ 동일 WID로 재연결
    ▼                                ▼
┌──────────────────────────────────────────┐
│ 암호문 영구 저장 자원 — 배치 위치 미결정 │
└──────────────────────────────────────────┘
        유지 ────────────────────────▶

pVM 삭제: 저장 유지 / Workload 폐기: 저장·메타데이터 회수
```

다이어그램 구성:

- `pVM #1`과 `pVM #2`는 같은 녹색 계열로 표시하고 둘 다 `Workload-A`라고 표기한다.
- pVM 사이에는 빨간 `X`를 넣어 인스턴스가 연속되지 않음을 표현한다.
- 저장 자원은 pVM 박스 밖의 회색 레인으로 두고 `암호문`, `배치 위치 미결정`을 명시한다.
- pVM #2의 연결 결과는 단순 mount가 아니라 신원·버전·내용 검증을 통과한 정상 확정본임을 설명한다.
- 삭제·변조·되돌리기 검출 메커니즘은 아직 공통 확인 필요 gate이므로 특정 기술이나 완료 상태로 그리지 않는다.

짧은 캡션: `삭제해도 유지 · 동일 Workload 재연결 · 폐기 시 회수`

### 3.3 카드 2 — Workload 신원과 저장 공간 결합

목적은 Host가 제시한 경로나 이름이 아니라 신뢰할 수 있는 Workload 식별자와 저장 공간 소유 관계로 연결을
판정함을 보여 주는 것이다.

```text
┌──────────────┐       ┌────────────────┐       ┌──────────────┐
│ Workload-A   │ ────▶ │ 신뢰 결합 검증 │ ────▶ │ A 저장 자원  │
│ 연결 요청    │       │ WID == owner   │ 허용  │ 암호문       │
└──────────────┘       └────────────────┘       └──────────────┘

┌──────────────┐                  X
│ Workload-B   │ ───────────────▶ 거부
│ 교차 연결    │        WID != owner
└──────────────┘
```

다이어그램 구성:

- 허용 경로는 녹색, 교차 Workload 요청은 빨간 점선과 `X`로 표시한다.
- 판정 입력은 `검증된 WID`, `저장 자원 owner`, `연결 정책`으로 한정한다.
- Host가 요청을 전달할 수는 있지만 신원 결합 결과를 바꿀 수 없음을 작은 회색 캡션으로 표시한다.
- 오래된 버전 검출을 이미 해결된 연결 절차로 그리지 않는다. 비-RPMB 무결성·재생 방지는 별도 확인 필요 gate다.

짧은 캡션: `동일 WID 허용 · 교차 Workload 거부`

### 3.4 카드 3 — 정책 기반 확장

목적은 pVM 종류별 분기 코드를 Framework 코어에 추가하는 방식이 아니라 정책과 식별자 데이터를 등록해 신규
Workload를 연결하는 구조를 보여 주는 것이다.

```text
┌────────────────┐     ┌────────────────┐     ┌────────────────────┐
│ Workload 정책  │ ──▶ │ Policy Registry│ ──▶ │ 영구 저장 자원 연결 │
│ WID·보존·한도  │     │ 식별자·정책 조회│     │ 배치 위치 미결정     │
└────────────────┘     └───────┬────────┘     └────────────────────┘
                                │
                         ┌──────▼──────┐
                         │ Framework   │
                         │ Core 0 LoC  │
                         └─────────────┘
```

다이어그램 구성:

- 신규 Workload는 점선 외곽선으로 표시해 런타임 확장임을 보여 준다.
- 정책 데이터에는 WID, 보존 수명, 자원 한도와 연결 정책을 예시로 넣는다.
- `Framework Core 0 LoC`를 잠금 표시와 함께 배치한다.
- `공통 Storage Adapter`처럼 파일 입출력 주체를 하나로 고정하는 박스는 사용하지 않는다. 이는 DP-06 후보 A/B를
  미리 결정할 수 있다.

짧은 캡션: `정책 추가 · 코어 변경 없음`

### 3.5 하단 공통 gate

세 카드 아래에 다음 공통 gate를 한 줄 또는 두 줄의 연한 주황색 띠로 표시한다.

> **공통 Gate:** 저장 경로에는 암호문만 전달 · 불완전 상태는 정상 확정 금지 · 삭제·변조·되돌리기 검출은 확인 필요

이 띠는 현재 세 문장만으로 빠지는 기밀성, 저장 상태 정확성과 비-RPMB 무결성 위험을 보완한다. 다만 확인 필요
항목을 해결 완료로 표현하지 않는다.

### 3.6 최종 레이아웃

슬라이드 16의 오른쪽 패널을 다음처럼 사용한다.

```text
┌──────────────────────── 설계 고려 사항 ────────────────────────┐
│ [복구성] pVM 삭제 후에도 암호화 파일 유지·재연결              │
│   pVM #1 ──X── pVM #2 / 아래에 끊기지 않는 암호문 저장 레인    │
├────────────────────────────────────────────────────────────────┤
│ [접근권 강제] Workload ID가 다른 연결 요청 차단                │
│   W-A ─▶ 신뢰 결합 검증 ─▶ 저장 A / W-B ──X                    │
├────────────────────────────────────────────────────────────────┤
│ [유지보수성] 정책 등록만으로 신규 Workload 추가                │
│   정책 ─▶ Registry ─▶ 저장 연결 / Framework Core 0 LoC         │
├────────────────────────────────────────────────────────────────┤
│ 공통 Gate: 암호문 only · 불완전 상태 미확정 · 재생 방지 확인 필요│
└────────────────────────────────────────────────────────────────┘
```

패널의 세 카드는 같은 높이로 배치하고, 문장과 다이어그램을 합쳐 카드당 구성요소를 네 개 이하로 제한한다.

### 3.7 하단 결론 문구 교정

현재 문구인 `기밀성, 확장성을 동시에 보장하는 pVM간 Data 공유 구조 필요`는 슬라이드 14의 문제를 설명하므로
슬라이드 16과 맞지 않는다. 다음 문구로 교체한다.

> **복구성, 보안성, 확장성을 함께 보장하는 암호문 영구 저장 구조 필요**

## 4. 슬라이드 14 검토 — pVM 간 Data 공유

### 4.1 현재 내용의 정확성

| 현재 고려 사항 | 현재 표현의 한계 | 보강 권고 | 우선순위 |
|---|---|---|---:|
| Zero-copy로 최소 시간 공유 | `최소 시간`은 판정 기준이 아니며, 그림의 `암호화 필요 없음`, `Raw data 전송 필요 없음`은 과도한 단정이다. | `payload 복사 없이 동일 물리 페이지의 접근권만 전환`과 `할당된 전달 지연·처리량 예산 충족`으로 수정한다. | P0 |
| Host는 제어 중계 가능, Data 접근 불가 | Host만 배제하고 제3 pVM, 접근 기간과 CPU/DMA 권한 동기화를 표현하지 않는다. | `Host·제3 pVM 비매핑`, `해당 세대·필요 기간에만 접근`, `Stage-2와 SMMU/S2MPU 동시 전환`을 표시한다. | P0 |
| 기존 모듈 수정 없이 pVM 쌍 추가 | 텍스트만 있고 확장 경로가 없다. | `Endpoint/Policy 등록 → Core 변경 없이 새 송수신 관계 추가` 미니 다이어그램을 넣는다. | P1 |

`암호화 필요 없음`은 zero-copy의 필연적인 결과가 아니다. 이 DP의 공통 보장 조건은 Host가 payload를 매핑하지 못하고
보호 영역이 접근권을 강제하는 것이며, 암호화 사용 여부는 별도 위협과 경로에 따라 달라질 수 있다.

### 4.2 빠진 설계 고려 사항

1. **버퍼 상태 정확성:** owner, access mode, generation과 상태를 신뢰 영역에 기록해야 한다.
2. **오류 회수:** 시간 초과나 pVM 비정상 종료 시 새 사용권을 부여하지 않고 버퍼를 회수하거나 폐기해야 한다.
3. **자원 상한:** 버퍼 풀이 상한에 도달하면 흐름을 제어해 할당이 무한정 증가하지 않아야 한다.

권장 보강 그림은 특정 ring이나 페이지 대여 구조를 선택하지 않고 다음 추상 상태만 보여 준다.

```text
CAMERA_OWNED → IN_TRANSFER → AI_OWNED → RECLAIMING → FREE
                       └─ timeout / pVM 종료 ─▶ 격리·회수
```

현재 슬라이드가 이미 조밀하므로 새 큰 그림을 추가하지 않는다. 기존 첫 번째 그림 아래에 위 상태 스트립을 넣고,
오류 분기는 빨간 화살표 한 개로 표시한다. 유지보수성 문장 아래의 빈 영역에는 작은 `Endpoint/Policy Registry` 그림을
추가한다.

## 5. 슬라이드 15 검토 — HW IP 공유와 소유권 전환

### 5.1 현재 내용의 정확성

| 현재 고려 사항 | 현재 표현의 한계 | 보강 권고 | 우선순위 |
|---|---|---|---:|
| 특정 시점의 HW 소유자는 정확히 하나 | 전환·격리 중 접근권 보유자가 0인 상태와 정상 단일 소유 상태가 구분되지 않는다. | `정상 상태는 단일 소유, 전환·오류 상태는 무권한 격리, 동시 권한은 항상 금지`로 정교화한다. | P0 |
| 소유권 전환 중재자는 신뢰영역 | 중재자 한 박스만 있고 CPU와 DMA 접근권의 별도 강제가 보이지 않는다. | 중재자 아래에 `Stage-2/MMIO`와 `SMMU/S2MPU/DMA` 두 집행 레인을 분리한다. | P1 |
| 권한 전환 전 기밀 Data 노출 가능성 제거 | 정상 전환 순서만 있고 실패·시간 초과 경로가 없다. | 각 단계 실패 시 `QUARANTINED`로 가는 빨간 분기와 재개 전 검증을 추가한다. | P0 |
| 기존 모듈 수정 없이 신규 HW 추가 | 텍스트만 있고 HW별 차이의 분리 위치가 없다. | 고정된 코어 상태기계 옆에 `HW Policy/Adapter: quiesce·reset·zeroize` 플러그인 그림을 넣는다. | P1 |

### 5.2 전환 순서 보강

현재 6단계 그림은 다음 순서를 명확히 해야 한다.

```text
요청 차단 → DMA 정지·완료 확인 → pending transaction drain
          → MMIO·DMA·IRQ 권한 회수 → 잔류 상태 소거·검증
          → 새 소유자 권한 부여

모든 단계의 실패/시간 초과 ─▶ QUARANTINED ─▶ 검증 성공 시에만 재개
```

잔류 상태는 DMA 버퍼만 의미하지 않는다. MMIO 레지스터, DMA 작업 목록, 내부 SRAM·캐시와 IRQ 상태를 함께
표시해야 한다.

### 5.3 확장성 보강

```text
┌────────────────────┐       ┌──────────────────────────────┐
│ Framework Core     │       │ HW Policy / Adapter          │
│ 공통 상태기계 유지 │ ◀──── │ quiesce·drain·reset·zeroize  │
│ 변경 0 LoC         │       │ 신규 HW IP별 추가            │
└────────────────────┘       └──────────────────────────────┘
```

이 그림은 전환 실행 순서와 요청 큐를 Host에 둘지 EL2에 둘지 결정하지 않는다. 또한 HW를 교대 할당할지 서비스 pVM에
고정할지도 표현하지 않아 후보 구조 비교를 침범하지 않는다.

## 6. 공통 시각 언어

세 슬라이드는 다음 표기를 통일한다.

| 표현 | 의미 |
|---|---|
| 연녹색 박스 | 신뢰·격리된 pVM 또는 검증 주체 |
| 회색 박스 | 비신뢰 Host/저장 경로 또는 배치 미결정 자원 |
| 파란 실선 | 정상 제어·허용 경로 |
| 초록 실선 | 보호된 데이터 또는 정상 재연결 경로 |
| 빨간 점선과 X | 차단, 실패, 시간 초과 또는 비인가 요청 |
| 자물쇠/굵은 외곽선 | 신뢰 영역이 강제하는 상태나 정책 |

캡션은 8~12자 정도로 유지하고, 상세 검증 수치는 후속 검증 슬라이드나 문서에 둔다.

## 7. 후보 중립성 주의 사항

- 슬라이드 16의 영구 저장 자원을 Host나 pVM 내부에 고정하지 않는다.
- 슬라이드 14의 버퍼를 ring, 중앙 pool 또는 송신자 local DMA-BUF 중 하나로 그리지 않는다.
- 슬라이드 15의 재개 승인자를 Host나 EL2 중 하나로 확정하지 않고 `신뢰 검증 주체`로 표시한다.
- 비-RPMB 삭제·변조·되돌리기 검출을 해결 완료로 표현하지 않는다. 현재는 확인 필요 공통 gate다.
- `최소 시간`, `암호화 불필요`처럼 근거와 범위가 없는 절대 표현을 사용하지 않는다.

## 8. 반영 결과

- 슬라이드 14 PNG의 오른쪽 패널을 `zero-copy`, `Host·제3 pVM 비매핑`, `정책 기반 pVM 쌍 추가` 카드와
  `오류·자원 gate`로 보강한다.
- 슬라이드 15 PNG의 오른쪽 패널을 `정상 단일 소유`, `CPU·DMA 권한의 신뢰 집행`, `안전 전환 순서와 격리`,
  `HW Policy/Adapter 확장` 카드로 보강한다.
- 슬라이드 16 PNG의 오른쪽 패널을 `저장 수명 분리`, `Workload 신원 결합`, `정책 기반 Workload 추가` 카드와
  공통 gate로 보강한다.
- 세 슬라이드의 하단 결론 문구를 각 DP의 보안성·성능·복구성·확장성 범위에 맞게 정렬한다.
