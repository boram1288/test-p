# 발표 관점
    * 심사위원을 가르치는 자리가 아니다. 내 판단이 타당한지 결정하도록 근거를 제시하는 자리다.
    * 배경 → 필요성 → 해결책이 막힘없이 이어져야 한다. 기술 용어는 최대한 배제.

# 과제 필요성
    * 기술 상세(MMU, EL0/EL1)는 빼라. "필요하겠구나 / 부족하구나"만 직관적으로 인지시켜라.
    * 제목은 "~의 부재/한계"로. 흐름: ① 실행 중 데이터 보호 안 됨 → ② 기존 솔루션 부재 → ③ 확장성 구조 부재.
    * "가상화(VM) 필요"를 문구로 명시.
    * 회사 이익(비용 절감)과 연계될 수 있어야 한다.
    * 기존 자료는 지우지 말고 Appendix로 보관.

# 기능 요구사항
    * 제로 카피는 기능 아님 → "버퍼 전송 기능"으로. "동적 탑재"는 로딩·실행 기능으로 풀어서 표현.
    * 기능 요구사항 전까지 전체 구조(설계도)를 노출하지 마라.

# 품질 속성 / KPI
    * KPI의 근거가 핵심. "왜 10ms?", "100%의 의미?"에 답할 수 있어야 한다.
    * 근거는 사업 조건·임원 코멘트·고객사 요구사항에 연결하면 타당성이 생긴다.

# DP (설계 결정) — 가장 중요
    * 문제 정의와 제약(Constraint)이 핵심. "제로 카피 적용"이 아니라 "QA1(성능) 해결을 위한 구조 필요"로 정의.
    * 현재 DP1은 솔루션을 미리 정해 문제가 없다. 너무 단순해 좋은 DP가 아니다.
    * 제약을 찾거나 만들어내라: 벤더 소스/모듈 미제공, 제로카피 불가, 메모리 예산, 부서 비협조 등. 당연히 되던 게 안 되는 것이 제약.
    * 제약 극복을 위한 A안·B안 → 트레이드오프 수치 평가 → 선택 흐름.
    * 제약을 찾으면 QA 우선순위가 바뀐다. DP1·2는 제약 기반, DP3·4는 기존 방식 가능.

# 구조 그림 (DP 비교도)
    * 심사위원은 좌/우 "차이(diff)"만 본다. 차이가 확 드러나야 함.
    * 핵심 주체/모듈만 남기고 중간 단계(MMU, PK드라이버, 카메라HW)는 빼라.
    * 너무 간단 ↔ 이해 불가 사이 절충점을 찾을 것.
