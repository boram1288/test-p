# 신규 Decision Point 목록

## 1. 목록 확정 기준

이 목록은 `02_문제_커버리지_매트릭스.md`에서 7개 적격성 gate를 모두 통과한
`NEW-DP` 10건만 포함한다. 번호는 상세 문서 작성 순서이며 채택 우선순위나 최종
결정을 뜻하지 않는다. 각 DP는 하나의 구조 변수만 다루고, 선행 결과가 미확정이면
해당 결과를 후보 공통 가정으로 두고 `확인 필요`로 표시한다.

공통 baseline은 DP로 다시 열지 않는다.

| baseline ID | 고정 내용 | 근거 |
|---|---|---|
| BL-01 | Host kernel까지 비신뢰하며 pKVM/EL2와 TEE를 trust anchor로 둔다. | G-08, E-010, E-025~031, E-061~062, E-065, E-088 |
| BL-02 | Linux native stack과 GP 호환 경계를 유지하고 Android 의존성을 도입하지 않는다. | B-01, E-003, E-011~012, E-023~024 |
| BL-03 | 현재 저장 baseline은 RPMB를 사용하지 않는다. 변경에는 사용자 확인이 필요하다. | G-09B, E-059, E-076, E-089 |
| BL-04 | 현재 Reference Scenario와 검증 topology는 Camera domain과 AI domain의 2-domain pipeline이다. | A-05, A-11, A-17, E-018, E-037, E-039, E-084, E-086 |

## 3. 의존 관계

| 선행 | 후행 | 전달하는 계약 | 선행 결과가 바뀔 때 재검토할 항목 |
|---|---|---|---|
| DP-01 | DP-02 | pVM identity, process/failure domain, lifecycle event | recovery unit과 restart 범위 |
| DP-01 | DP-03 | 생성 경계와 검증 대상 pVM generation | secure loading endpoint와 시작 순서 |
| DP-01, DP-03 | DP-04 | pVM/Workload identity와 검증된 measurement/generation | authorization subject와 policy key |
| DP-04, C-02 | DP-05 | 허용된 subject/action과 buffer ownership 상태 | grant rule, ledger key, fail-closed 조건 |
| DP-04, DP-05, C-02 | DP-06 | policy endpoint, ledger owner, backing/descriptor 계약 | request endpoint, 인증 metadata, timeout 책임 |
| DP-03, DP-04 | DP-07 | verified caller identity와 호출 authorization 결과 | 종단 인증, relay/direct endpoint, GP adapter 경계 |
| DP-02, DP-07 | DP-08 | failure/termination event와 session 생성 경계 | cleanup trigger, generation, 최종 reclaimer |
| DP-01, DP-02, DP-04, C-01 | DP-09 | failure domain, recovery owner, HW authorization, 안전 전환 계약 | driver placement, lease lifetime, 장애 반경 |
| DP-01, DP-02, DP-03, DP-04 | DP-10 | 실행/복구 단위와 검증된 tenant identity/policy | entitlement key, dispatch/reclaim 주체, overload 격리 단위 |

DP-03은 image/manifest/version의 authenticity와 실행 gate를, DP-04는 검증된
identity를 사용한 cross-cutting resource authorization을 다룬다. 이 책임 분리로
두 문서 사이의 순환 의존을 만들지 않는다. DP-05는 buffer별 policy/ledger owner를,
DP-06은 그 authority까지 가는 control request route를 다루므로 같은 축을 중복하지
않는다.

## 4. 공유 품질 예산

end-to-end QAS를 여러 DP가 각각 전액 달성했다고 계산하지 않는다. 동일 trace에서
각 DP가 점유한 구간을 분해 계측하고, 직렬 구간은 합산하며 병렬 구간은 critical
path로 계산한다. 아래 원문의 수치는 예시치이므로 사용자 승인 전 상세 배분값과
후보별 별점은 `TBD`다.

| 공유 QAS/window | 소비 DP/외부 계약 | 예산 사용 규칙 | 상세 DP의 기록 의무 |
|---|---|---|---|
| QAS-PERF-07: 시작 요청→첫 frame cold start p95 2초 이하(예시치) | DP-01 pVM 생성, DP-03 검증·승인, DP-10 entitlement 배정; C-02/DP-05/06의 첫 channel 구성은 외부 구간 | 각 DP가 2초 전체를 재청구하지 않고 동일 시작 trace의 자기 구간만 사용한다. 구간별 배분값은 `TBD`다. | 구간 시작/종료 timestamp, 직렬/병렬 여부, end-to-end 합산 결과 |
| QAS-AVL-02: 검출→회수→재기동 p99 3초(0.5/1/1.5초 분해) | DP-02 recovery orchestration, DP-08 TEE session 회수, DP-09 HW lease 회수, DP-10 CPU/memory 회수 | DP-02가 end-to-end window를 소유하고 DP-08/09/10은 회수 구간의 병렬 또는 직렬 기여만 청구한다. 기존 분해값을 DP별 할당값으로 임의 전용하지 않는다. | 장애 ID가 같은 trace, 하위 회수 구간, critical path, 서비스 재개 시점 |
| QAS-PERF-02: frame 전달 p99 5ms, 전환 1ms 이하(예시치) | C-02 backing/mapping, DP-05 policy/ledger, DP-06 request route | data/control 전 구간의 동일 frame ID로 측정하며 각 구조가 전체 5ms를 별도 예산으로 사용하지 않는다. | request, grant, mapping, receiver-ready timestamp와 총 전달 지연 |
| QAS-PERF-01: 30fps·drop 0.1% 이하·비격리 대비 저하 10% 이내(예시치) | DP-09 physical HW lease, DP-10 CPU/memory entitlement, C-01 HW 전환 | 같은 부하/stream/SoC 조건의 end-to-end 결과로 판정하고 HW·scheduler 기여를 분해한다. | 공통 시험 조건, frame deadline miss/drop, 단계별 stall 원인 |
| QAS-PERF-04: HW 권한 전환 p95 10ms(가정치) | C-01 revoke/drain/reset/zeroize/regrant 계약, DP-09 physical owner·driver placement | 같은 transition generation의 단계별 timestamp로 합성하며 C-01과 DP-09가 10ms 전체를 각각 재청구하지 않는다. | revoke accepted, drain/reset, SMMU 전환, driver ready와 new-owner ready timestamp |
| QAS-PERF-03: capture→판단 E2E p99 100ms, inference 상대 성능 90%(출처 보완 필요) | C-01/C-02, DP-05/06/07/09/10과 Workload inference 외부 구간 | 어느 DP도 100ms 전체를 자기 예산으로 재청구하지 않는다. 각 DP의 control/data/HW/TEE 구간과 Workload inference 구간을 같은 frame trace의 critical path로 합성한다. | capture PTS, 단계별 시작/종료, 판단 완료 timestamp, 누락 구간과 출처 확인 상태 |

DP별 상세 문서는 이 표의 end-to-end 결과를 자기 후보의 단독 성과로 표현하지
않는다. 선행 결과가 없으면 구간 값과 전체 예산 충족 여부를 `확인 필요`로 둔다.

## 5. 작성 순서와 병렬 가능 범위

| 묶음 | 작성 순서 | 이유 | 병렬 작성 조건 |
|---|---|---|---|
| 실행 기반 | DP-01 → DP-02 | failure domain을 먼저 고정해야 recovery unit을 비교할 수 있다. | 없음 |
| 신뢰 신원과 정책 | DP-03 → DP-04 | 검증된 Workload identity가 authorization subject의 입력이다. | DP-03은 DP-02와 후보를 공유하지 않아 DP-01 뒤 문제 정의만 병렬 검토 가능 |
| pVM 간 control path | DP-05 → DP-06 | ledger owner를 추상 endpoint로 먼저 정한 뒤 request route를 비교한다. | C-02 계약을 공통 가정으로 고정할 때만 가능 |
| TEE 경로와 회수 | DP-07 → DP-08 | session 생성/호출 경로가 cleanup trigger와 reclaimer 범위를 제공한다. | DP-07 문제 정의는 DP-05/06과 병렬 검토 가능 |
| HW 배치 | DP-09 | 실행·복구·정책 계약과 C-01 안전 전환 계약을 소비한다. | 선행 결과가 미정이면 모두 `확인 필요`로 표시 |
| 자원/QoS | DP-10 | 앞선 identity, failure/recovery unit, policy 경계를 entitlement 단위로 사용한다. | 없음 |

최종 상세 문서 작성 순서는 `DP-01 → DP-02 → DP-03 → DP-04 → DP-05 →
DP-06 → DP-07 → DP-08 → DP-09 → DP-10`이다. 이 그래프에는 후행 DP에서
선행 DP로 돌아가는 필수 입력이 없으므로 순환 의존이 없다.

## 6. 범위 경계와 역추적 규칙

- G-05의 backing/descriptor join, timeout과 reclaimer protocol은 DP-05/06의
  후보 선택 뒤 `SUBDECISION`으로 작성한다.
- manifest/package schema(A-04), current 2-domain pipeline schema(A-05), public
  API negotiation(A-06)은 DP-03/04/06의 interface contract 하위 결정이다.
- pVM warm pool(A-01)은 DP-01/02, multi-stream capacity(A-11)은 C-02/DP-10의
  후보별 parameter와 검증 항목이다.
- N-domain topology(A-17), future HW abstraction(A-07), 운영·fleet 항목(A-10),
  guest runtime 제품 선택(A-13), 일정/인력(A-16)은 이번 상세 DP에서 다루지 않는다.
- 선행 DP의 후보가 바뀌면 3절 관계표의 해당 후행 문서에서 문제 공통 가정,
  다이어그램 endpoint, gate 측정 조건과 `확인 필요` 항목을 다시 검토한다.
- C-01/C-02(기존 문제 1/2)의 최종 결정이 확정되거나 후보 계약이 바뀌면 이를
  입력으로 쓰는 DP-05, DP-06, DP-09도 같은 역추적 재검토 대상에 포함한다.
- 이 목록은 후보나 최종 결론을 채택하지 않는다. 모든 상세 DP의 초기 상태는
  `도출`, gate/KPI 평가 후 상태는 `평가 중`이며 사용자 선택 전 `확정`하지 않는다.
