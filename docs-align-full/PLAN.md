# docs-align-full 문제 도출/후보 구조 생성/품질 평가 계획

## 1. 목적

`docs-align`에서 상세하게 다룬 세 문제 이외의 품질 위협을 누락 없이 찾고, 아키텍처 결정이 필요한 문제만 선별하여 다음 순서로 문서화한다.

1. 현재 구조에서 발생하는 문제를 요구사항과 품질속성에 연결해 정의한다.
2. 하나의 결정 질문에 답하는 상호 배타적인 후보 구조를 정확히 두 개 만든다.
3. 필수 gate와 동일한 KPI 조건으로 두 후보를 평가한다.
4. 최종 선택은 기록하지 않고 사용자의 결정을 기다린다.

이 문서는 작업 방법과 완료 조건을 정하는 계획이다. 신규 문제 목록, 후보 구조와 평가 결과를 확정하는 문서가 아니다.

## 2. 작업 원칙과 기준 문서

### 2.1 규칙 우선순위

규칙이 충돌하면 다음 순서를 따른다.

1. `docs-align/DP-RULE.md`
2. `docs-align/후보_구조_작성_규칙.md`
3. `docs-align/후보_구조_품질_평가_규칙.md`
4. `docs-align`의 문제/요구사항/품질속성 문서와 모든 이미지
5. `docs`, `docs-new`, `docs-dp`의 요구사항, 문제 상황, 시나리오, PoC 관찰 결과

`docs-dp/DP-RULE.md`를 포함한 다른 디렉터리의 작성 규칙은 차이 분석 자료로만 사용하고, 산출물의 형식과 평가 방식은 위 1~3의 `docs-align` 규칙으로 통일한다.

### 2.2 기존 후보와 결정의 취급

- 기존 후보 구조와 채택 결과는 신규 후보를 만드는 입력으로 사용하지 않는다.
- 기존 문서에서는 현재 구조, 위협, 요구사항, 품질 시나리오, 제약, PoC로 확인된 사실만 추출한다.
- 문제와 결정축을 독립적으로 고정한 뒤에만 기존 후보/결정 문서를 대조하여 중복 여부와 빠진 실현 가능성 조건을 확인한다.
- 기존 후보를 조합하거나 이름만 바꿔 신규 후보로 재사용하지 않는다.
- 현재 working tree의 파일을 기준으로 하며, 이전 대화나 되돌리기 전 문서 내용은 근거로 사용하지 않는다.

### 2.3 범위

반드시 조사할 범위는 다음과 같다.

- `docs-align`
  - 모든 Markdown 파일
  - `SW_Architect_개인과제` 본편 슬라이드 1~33
  - 소문자 확장자 변형 슬라이드 1, 6
  - `SW_Architect_개인과제_appendix` 슬라이드 1~17
  - 품질 위협 인포그래픽 3개
  - 임시/바이너리 파일은 형식을 확인하고 아키텍처 근거인지 여부를 기록한다.
- `docs`
  - 최상위 Markdown/DOCX 등 모든 파일
  - `DP`, `DP_old` 하위 문서
  - 요구사항, VOS, 품질 시나리오, Reference Scenario, DP 후보/목록, 조사 문서
- `docs-new`
  - PoC 프로젝트 전용 변경과 Decision Point 분석 문서
- `docs-dp`
  - `DP-LIST.md`, `DP-01`~`DP-07`과 세부 DP, 배경/후보 문서, 작성 규칙
  - `DP-01-배경.png`를 포함한 이미지/비문서 파일

네 디렉터리 모두 확장자별 예상 목록만 보지 않고 실제 파일 목록을 먼저 고정한다. 이미지가 추가로 발견되면 모두 시각 검토하고, 읽을 수 없는 형식은 누락시키지 않고 형식/크기/판독 불가 사유를 인벤토리에 남긴다.

현재 지정된 로컬 자료 밖의 웹/외부 자료는 문제를 새로 만들어 내는 근거로 사용하지 않는다. 이후 기술 실현 가능성이나 KPI 경계값의 출처가 필요하면 별도 조사 필요 항목으로 표시하고, 사용자 승인 후 보조 근거로만 사용한다.

## 3. 현재 커버리지 기준선

다음 세 문제는 `docs-align`에서 이미 문제 정의, 두 후보 구조와 품질 평가까지 다룬 것으로 등록한다. 신규 문제 도출 단계에서 같은 결정축을 다시 만들지 않는다.

| 기존 문제 | 현재 결정축의 요약 | 대표 근거 |
|---|---|---|
| 문제 1: Camera/AI HW 공유 | HW 사용 순서 결정과 신뢰 영역의 최종 권한 집행 책임 | `docs-align/품질위협_문제1_HW공유_기밀데이터_노출.md`, `docs-align/후보구조_문제1_HW공유.md` |
| 문제 2: pVM 간 대용량 데이터 전달 | 프레임별 페이지 소유권 전환과 사전 등록 보호 버퍼 풀/slot 사용권 | `docs-align/품질위협_문제2_pVM간_데이터전달.md`, `docs-align/후보구조_문제2_pVM간_데이터전달.md` |
| 문제 3: pVM 수명과 암호화 파일 | pVM과 독립적인 암호화 파일의 보관/입출력 책임 위치 | `docs-align/품질위협_문제3_pVM수명_암호화파일_유실.md`, `docs-align/후보구조_문제3_암호화파일_영구보관.md` |

기존 문제와 신규 문제의 중복 여부는 `문제의 원인 + 결정 변수 + 책임/실행 위치/신뢰 경계`가 같은지로 판단한다. 같은 기능 영역이어도 이 세 요소 중 결정 변수가 독립적이면 신규 문제 후보가 될 수 있다.

### 4.2 목록 밖까지 조사할 보조 신호

다음 항목도 누락 검사표에 넣되 곧바로 DP로 승격하지 않는다.

| 묶음 | 조사할 문제 신호 | 최초 분류 가설 |
|---|---|---|
| 자원/운영 | pVM 생성 시점, vCPU/메모리 예약, 스케줄링/QoS, Host 과부하 중 이웃 간섭 | G-01의 하위 결정 또는 별도 자원 정책 DP |
| 실행 파이프라인 | 동기/비동기 실행, interrupt/polling 알림, descriptor와 buffer join/timeout | 기존 문제 2의 하위 결정 또는 G-05와 독립인 실행 모델 DP |
| Workload 진화 | 패키지/manifest schema, 파이프라인 topology, API version/capability 협상 | G-02의 하위 결정인지 독립 변경 용이성 DP인지 판정 |
| HW 진화 | device assignment topology, HW class 추상화, SoC별 adapter | 기존 문제 1/G-06의 하위 결정 또는 현재 Camera/AI HW 범위 밖 |
| 모델 운용 | AI 모델 가중치의 reload/cache/hot swap과 평문 상주 시간 | Workload 내부 구현인지 저장/실행 경계를 바꾸는 구조인지 판정 |
| 증빙/감사 | attestation, 격리 증빙, 변조 방지 감사 로그, 검증 hook | 아키텍처 책임축과 시험 방법을 분리. 시험 방법만 다르면 DP에서 제외 |
| 제품 운영 | OTA/rollback, fleet 배포, SLA/MTBF, glass-to-glass, 다중 stream | 현재 Secure Vision AI Framework 범위인지 확인 후 범위 밖이면 근거와 함께 제외 |
| API/사용성 | Host 노출 API, 동기/비동기 job, 비보안 전문가용 단순 API | 신뢰 경계를 바꾸지 않으면 interface 하위 결정으로 분류 |
| 실행 환경 | guest OS/RTOS/unikernel, 실제 HW와 simulator 선택 | 제품 선택 또는 검증 환경만의 차이면 DP에서 제외 |

특히 다음 “목록 불일치”를 명시적으로 해소한다.

- `docs-dp/DP-07.md`는 상세 문서가 있지만 `docs-dp/DP-LIST.md`의 선정 DP에는 없다.
- `docs-dp/DP-LIST.md`는 pVM 소멸 시 TEE 세션/자원 정리를 별도 후보로 남겼다.
- `docs/05_decision_points.md`의 Reference Scenario 2단계 “요청 권한/정책 확인”은 어느 DP에도 매핑되지 않았다.
- `docs-new`의 protected metadata queue와 frame backing/descriptor 분리는 `docs-align`의 대용량 데이터 전달 문제와 동일한 축인지 판정되지 않았다.
- `docs/04_vos_requirement_matrix.md`에서 VOS-04, VOS-06, VOS-13, VOS-14는 Architectural Driver에 직접 매핑되지 않았다. 각각 자원 예산, 일정 제약, 객관적 격리 검증, API 사용성으로 분해하여 DP/제약/검증/범위 밖 중 하나로 분류한다.
- `docs/03_qa_quality_scenarios.md`의 운영 단계 항목(SEC-07, PERF-05/06, EXT-04/05/07, AVL-06/07)이 현재 구조 결정 범위에 포함되는지 확인한다.

## 6. 단계별 실행 계획

### 단계 0. 작업 기준선 고정과 Herdr/Claude 협업 준비

1. `rtk git status --short`로 working tree를 기록하고 기존 사용자 변경을 식별한다.
2. `rtk proxy rg --files`와 별도 파일 탐색으로 추적/미추적/무시 파일을 모두 나열한다.
3. 조사 시작 시 파일 hash를 기록하여 조사 중 원본 변경 여부를 감지한다.
4. `HERDR_ENV=1`을 확인하고 `herdr --help`, 사용할 하위 명령의 `--help`를 먼저 확인한다.
5. 현재 pane 오른쪽에 50% pane을 `--no-focus`로 열고 Claude를 시작한다. 이미 오른쪽 Claude pane이 있으면 재사용한다.

명령 형태는 현재 Herdr CLI의 도움말로 다시 확인한 뒤 다음 패턴을 사용한다.

```bash
rtk proxy herdr pane split --current --direction right --ratio 0.5 --no-focus
rtk proxy herdr agent start <name> --kind claude --pane <right-pane-id>
rtk proxy herdr agent prompt <name> '<검토 요청>' --wait --until idle --timeout <ms>
```

pane 생성/재사용, Claude prompt 제출, Claude 답변 때문에 작업을 멈추는 시점은 사용자에게 commentary로 알린다.

단계 1~6은 각각 종료 전에 오른쪽 Claude pane의 checkpoint를 통과해야 한다. 인벤토리 누락, 커버리지 분류, 문제 인과/결정축, 후보 상호 배타성, gate/KPI 대칭성, DP 의존성 순서에 관해 중대한 이견이 남으면 다음 단계로 넘어가지 않고 원문 근거로 해소하거나 `확인 필요`로 기록한다.

### 단계 1. 전수 인벤토리와 원자 근거 추출

1. 모든 Markdown의 제목, 요구사항 표, 문제 상황, 결정 질문, TBD/미해결/제외 문구를 추출한다.
2. 이미지마다 슬라이드 번호, 보이는 요구 ID, 문제 문장, 구조 단서와 중복 여부를 기록한다.
3. DOCX는 텍스트/이미지를 추출해 같은 방식으로 기록하고, 임시/바이너리 파일은 아키텍처 내용이 없으면 `EVIDENCE-ONLY` 또는 비근거로 표시한다.
4. 동일 ID가 디렉터리별로 다른 뜻을 갖는 경우 원문 ID를 유지하고 별도 정규화 ID를 부여한다.
5. 요구사항은 `기능/품질/제약/관찰 사실/기존 결정 주장`으로 구분한다.

Claude에는 같은 파일 범위만 주고 독립적으로 다음을 요청한다.

- 기존 세 문제로 커버되는 항목
- 기존 세 문제와 결정축이 다른 항목
- 어떤 목록에도 직접 올라가지 않은 시나리오/요구사항 공백
- baseline, 하위 결정, 검증 방법, 범위 밖으로 보이는 항목

Codex와 Claude의 분류 결과는 서로 보기 전에 각각 고정하고, 그 뒤 차이를 `REVIEW_LOG.md`에 남긴다.

### 단계 2. 문제 커버리지와 DP 적격성 판정

각 문제 신호에 다음 순서로 판정한다.

1. **요구 추적성**: 하나 이상의 FR/QA/VOS/제약 또는 명시된 현재 구조의 실패에 연결되는가?
2. **실제 문제성**: 기술 이름이 아니라 현재 구조의 원인→실패 사건→품질 영향이 설명되는가?
3. **project-custom 범위**: 고정된 pKVM/TEE/HW baseline이 아니라 이번 Framework의 책임/배치/경계를 결정하는가?
4. **구조 결정성**: 제품/라이브러리/알고리즘/시험 방법 선택이 아니라 책임, 실행 위치 또는 신뢰 경계를 바꾸는가?
5. **기존 커버리지**: 기존 세 문제 또는 다른 신규 문제와 결정 변수가 같은가?
6. **독립성**: 다른 DP 선택 이후 자동으로 결정되는 하위 구현이 아닌가?
7. **실현 가능성**: 필수 제약을 만족할 수 있는 구조가 최소 두 개 존재할 가능성이 있는가?

판정 값은 다음 중 하나만 사용한다.

- `COVERED`: 기존 세 문제의 같은 결정축에서 이미 다룸
- `NEW-DP`: 독립 문제/결정축으로 상세 작성
- `SUBDECISION`: 다른 DP 선택 후 정할 하위 구현
- `BASELINE-CONSTRAINT`: 후보 공통의 고정 전제
- `DUPLICATE`: 다른 문제 신호와 병합
- `EVIDENCE-ONLY`: PoC/시험/설명 자료이며 결정 문제가 아님
- `OUT-OF-SCOPE`: 현재 과제 경계 밖

`DUPLICATE`, `SUBDECISION`, `BASELINE-CONSTRAINT`, `OUT-OF-SCOPE`에는 반드시 흡수 대상 또는 제외 근거를 기록한다.

이 단계의 매트릭스 초안은 Claude가 독립 작성한 분류표와 전 행 대조한다. 특히 `NEW-DP`와 제외 계열 판정이 엇갈리는 행은 합의 없이 확정하지 않는다.

### 단계 3. 문제 정의와 결정 질문 작성

`NEW-DP`마다 먼저 후보를 보지 않고 다음 내용을 작성한다.

1. 현재 구조와 참여 주체
2. 신뢰/비신뢰 경계
3. 보호 자원 또는 관리 자원의 owner와 수명
4. 자극/실패 사건/직접 영향/품질 영향의 인과 사슬
5. baseline과 project-custom 범위
6. 관련 FR/QA/VOS/제약
7. 문제를 해결하기 위해 정해야 하는 하나의 구조 변수
8. “누가/어디에서/어떤 경계로 책임질 것인가” 형태의 단일 결정 질문

문제 상황에 등장하지 않은 품질속성을 평가 단계에서 새로 추가하지 않는다. 문제 정의가 둘 이상의 독립 결정 질문을 포함하면 문서를 나누고 선행 관계를 기록한다.

후보 생성 전에 Claude가 문제 인과 사슬과 단일 결정 변수를 검토하여, 해결책이 문제 정의에 미리 들어갔거나 baseline을 선택지로 오인한 부분을 제거한다.

### 단계 4. 정확히 두 후보 구조의 독립 도출

후보 구조는 다음 조건을 모두 만족해야 한다.

- 정확히 두 개만 둔다.
- 같은 결정 질문에 답하고 추상화 수준이 같다.
- 책임, 실행 위치 또는 신뢰 경계가 실제로 다르다.
- 각 후보에 구성 요소 책임, 제어 흐름, 데이터 흐름, 신뢰 경계, 자원 owner/reclaimer, 정상/실패 동작을 적는다.
- 공통 기반과 후보 고유 요소를 분리한다.
- 다른 DP의 세부 선택은 후보 안에 숨기지 않고 `후속 결정`으로 표시한다.
- 두 후보 모두 필수 gate를 통과할 가능성이 있어야 한다.

상호 배타성은 다음 두 검사를 통과해야 한다.

1. **XOR 검사**: 결정 변수에 대해 한 배포 구성에서 A와 B를 동시에 참으로 만들 수 없어야 한다.
2. **결합 개선안 검사**: A의 일부와 B의 일부를 합쳐 양쪽 단점을 줄인 제3 구조가 가능하면, 현재 두 후보는 트레이드오프 쌍이 아니다. 결정축을 다시 좁히거나 후보를 다시 만든다.

각 후보에는 동일한 view/방향/공통 요소/색/범례를 쓰는 PlantUML 다이어그램을 정확히 하나씩 둔다. 신뢰/비신뢰 영역, 제어/데이터 흐름, owner/reclaimer와 두 후보의 차이가 그림에서 바로 보여야 한다.

Codex와 Claude가 후보쌍을 독립 도출한 뒤 결정 변수만 대조한다. 후보 내용이 같다는 이유가 아니라 XOR/결합 개선안/지배 관계 검사를 모두 통과했다는 근거가 있을 때만 다음 단계로 진행한다.

### 단계 5. 필수 gate와 품질속성 평가

평가 순서는 바꾸지 않는다.

1. baseline/제약 준수와 핵심 기술 실현 가능성을 먼저 gate로 판정한다.
2. 보안/무결성/격리 등 상위 필수 기준을 같은 조건으로 두 후보에 적용한다.
3. 각 gate에 요구 ID, 판정 기준, 공통 측정 조건/검증 방법과 근거 출처를 기록한다.
4. 판정은 `통과/실패/확인 필요`만 사용한다.
5. gate 하나라도 실패한 후보에는 별점을 주지 않는다.
6. 두 후보가 모두 실패하면 평가를 멈추고 후보 생성 단계로 돌아간다.
7. `확인 필요`는 통과로 간주하지 않으며 별점은 명시적으로 잠정 상태로 둔다.
8. KPI는 측정 대상, 공식, 단위, 좋고 나쁨의 방향, 동일 시험 조건, 경계값과 출처를 적는다.
9. 승인되지 않은 수치와 속성은 `TBD`로 두고 임의 별점/가중치를 만들지 않는다.
10. 별점은 사전에 선언한 동일 경계로만 1~3개를 부여한다.
11. 임의 총점이나 가중합으로 승자를 만들지 않는다.

모든 평가 근거에는 `운영 관찰/대표 PoC/제한 PoC/계산·시뮬레이션/구조적 추론/확인 필요` 중 하나를 표시한다. 대표성이 확인되지 않은 PoC와 구조적 추론은 잠정 근거로만 사용한다.

별점을 작성하기 전에 Claude가 gate와 KPI 표의 행/조건/출처가 두 후보에 대칭인지 검토한다. 비대칭이거나 문제 상황에 없던 품질속성이 있으면 표를 먼저 수정한다.

문제 인과 사슬, gate/KPI, 핵심 트레이드오프는 같은 품질속성으로 추적되어야 한다. 핵심 트레이드오프에는 각 후보가 얻는 것과 반드시 치르는 구조적 비용을 대칭적으로 적는다.

### 단계 6. DP 문서 작성 순서와 의존성 정리

최종 순서는 단계 2의 판정 뒤 확정하되 다음 방향으로 진행한다.

1. 신뢰 모델/secure boot 항목을 `결정 DP`와 `공통 baseline`으로 먼저 분해한다.
2. pVM 실행 경계/생명주기/복구 책임을 정리한다.
3. Workload 최종 검증과 secure loading 구조를 정리한다.
4. 요청 정책/권한 집행과 pVM 신원 사용 지점을 정리한다.
5. metadata/control path와 backing 결합 책임을 정리한다.
6. pVM-TEE 호출 경로와 TEE 세션 회수 책임을 정리한다.
7. HW 물리 lease 보유 단위가 기존 문제 1과 독립이면 정리한다.
8. 작은 파일/상태 저장이 기존 문제 3과 독립일 때만 정리한다.
9. 자원/QoS, interface 진화, attestation/감사 항목은 범위/독립성 gate를 통과한 경우에만 후속 DP로 작성한다.

선행 DP 결과가 없으면 후보 공통 가정으로 임시 고정하고 `확인 필요`로 표시한다. 선행 결정이 바뀌면 영향받는 문서를 역추적할 수 있도록 관계표를 유지한다.

작성 순서를 확정하기 전에 Claude가 순환 의존성, 암묵적 선행 결정과 같은 품질 예산의 중복 사용을 검토한다.

### 단계 7. Claude 반대 검토와 사용자 결정 대기

각 신규 DP마다 Herdr 오른쪽 Claude pane에서 최소 두 번 검토한다.

1. **문제/결정축 검토**: 중복, baseline 혼입, 인과 비약, 요구 추적 누락을 공격적으로 찾는다.
2. **후보/평가 검토**: 두 후보의 결합 가능성, 우월 후보, 추상화 불일치, gate 비대칭, 근거 없는 별점을 찾는다.

이견은 `쟁점/Claude 의견/Codex 의견/원문 근거/해결/남은 확인` 형식으로 기록한다. Claude와 Codex가 같은 파일을 동시에 편집하지 않으며 Codex가 검토 결과를 반영한다. 긴 답변이 pane에서 잘리면 Claude가 `/tmp` 파일에 전체 답변을 쓰게 한 뒤 읽는다.

두 검토를 통과해도 `12. 최종 결정`은 비워 두고 사용자 선택 전에는 상태를 `확정`으로 바꾸지 않는다.

## 7. DP 문서 표준 목차

각 `DP-NN_<문제명>.md`는 다음 순서를 사용한다.

1. 상태 (`도출` → gate/KPI 평가 후 `평가 중`)
2. 결정 목적
3. 문제 상황
4. 결정 질문
5. 후보 구조
6. 후보별 구조 다이어그램
7. 후보별 동작 구조
8. 품질속성 비교
9. 핵심 트레이드오프
10. 검증 기준
11. 검토 결과
12. 최종 결정

후보를 생성한 시점에는 `도출`, 실제 gate/KPI 평가를 수행한 뒤에는 `평가 중`으로 둔다. `최종 결정`에는 사용자가 후보를 선택하기 전까지 내용을 쓰지 않는다.

## 8. 검증과 완료 조건

### 8.1 인벤토리 완료 조건

- 지정한 네 디렉터리의 모든 파일/이미지가 `00_소스_인벤토리.md`에 한 번씩 나타난다.
- 본편/소문자 변형/appendix/인포그래픽은 각각 시각 검토 여부가 표시된다.
- 요구 ID 충돌과 문서 간 상충 주장이 근거 원장에 기록된다.
- 계획 수립 중 확인한 G-01~G-10과 보조 신호가 모두 최종 분류를 받는다.

### 8.2 신규 DP 적격성 완료 조건

- 모든 `NEW-DP`에 원문 근거, 관련 요구, 결정 변수와 기존 세 문제와의 차이가 있다.
- “같은 기능”이 아니라 “같은 결정축” 기준으로 중복 검사를 통과한다.
- 각 문제는 하나의 결정 질문만 가진다.
- baseline/제품 선택/하위 구현/검증 방법이 DP로 승격되지 않는다.

### 8.3 후보/평가 완료 조건

- 후보가 정확히 두 개다.
- XOR와 결합 개선안 검사를 통과한다.
- 한 후보가 다른 후보를 구조적으로 포함하거나 지배하지 않는다.
- 후보별 PlantUML이 하나씩 있고 동일한 관점을 사용한다.
- gate를 별점보다 먼저 평가하고 `확인 필요`/`TBD`를 숨기지 않는다.
- 같은 KPI 공식/단위/조건/경계값이 두 후보에 적용된다.
- gate마다 요구 ID, 공통 측정 조건/검증 방법과 출처가 있다.
- 평가 근거의 유형과 운영 환경 대표성이 표시된다.
- 문제→gate/KPI→트레이드오프의 품질속성 추적이 닫힌다.
- Herdr Claude의 문제축 검토와 후보/평가 검토가 기록된다.
- 최종 결정은 비어 있다.

### 8.4 저장소 검증

- Markdown 링크와 상대 경로가 실제 파일을 가리키는지 확인한다.
- PlantUML 문법 검사가 가능한 환경이면 모든 다이어그램을 렌더링한다. 도구가 없으면 `확인 필요`로 기록한다.
- 변경된 파일 목록과 diff를 검토한다.
- 원본 `docs-align`, `docs`, `docs-new`, `docs-dp`는 조사 중 수정하지 않는다.
- 작업 파일만 stage/commit/push하고 기존 사용자 변경은 포함하지 않는다.

## 9. 중단/재작업 조건

다음 상황에서는 결론을 만들지 않고 해당 단계로 돌아간다.

- 두 후보를 합친 제3 구조가 양쪽 단점을 줄인다: 단계 4에서 결정축을 다시 정의한다.
- 한 후보가 필수 gate를 구조적으로 통과할 수 없다: 그 후보를 제거하고 동일 질문의 실현 가능한 대안을 다시 찾는다.
- 두 후보가 모두 필수 gate를 실패한다: 평가를 중단하고 문제 범위 또는 baseline 가정을 재검토한다.
- 문제에 대응하는 상위 요구/품질속성이 없다: 신규 요구 승인이 필요한 항목으로 분리한다.
- source 간 baseline/제약이 충돌한다: 임의 선택하지 않고 충돌표와 영향 범위를 작성한다.
- Claude와의 이견이 원문 근거만으로 해소되지 않는다: 양쪽 해석과 필요한 사용자 결정을 기록한다.

이 계획의 완료 결과는 “많은 DP 문서”가 아니라, 근거를 전수 추적하고 중복/하위 결정/범위 밖을 제거한 뒤 남은 각 문제에 대해 서로 결합할 수 없는 두 구조를 공정하게 평가한 문서 집합이다.
