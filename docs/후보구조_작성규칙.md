# 후보 구조 및 Decision Point 작성·평가 통합 규칙

## 1. 목적과 적용 범위

이 문서는 Decision Point의 선정과 문서 구성, 후보 구조와 다이어그램 작성,
품질속성 평가, 검토 및 최종 결정에 적용할 규칙을 정의한다.

적용 범위는 Decision Point의 도출부터 후보 구조 작성, 품질 평가, 검토와 최종
결정까지다. 이 문서만으로 전체 작성·평가 절차를 수행하며 최종 결정자는 사용자다.

## 2. Decision Point 선정 규칙

다음 조건을 모두 만족하는 항목만 Decision Point로 선정한다.

1. 아키텍처 구조를 바꾸는 결정이다.
2. 후보 구조는 정확히 두 개다.
3. 두 후보의 책임과 실행 위치가 다르다.
4. 두 후보의 신뢰 경계가 다르다.
5. 두 후보 사이에 품질속성 트레이드오프가 있다.
6. 두 후보는 과제 범위 안에서 결정할 수 있다.

다음 항목은 별도 Decision Point로 만들지 않는다.

- 구현 라이브러리나 제품의 선택
- 다른 Decision Point에 속하는 세부 구현
- 구조는 같고 검증 방법만 다른 선택
- 하나의 후보가 모든 품질속성에서 우월해 실제 트레이드오프가 없는 선택

## 3. DP 문서 작성 순서

각 DP는 다음 순서로 작성한다.

1. 상태
2. 결정 목적
3. 문제 상황
4. 결정 질문
5. 후보 구조
6. 후보별 구조 다이어그램
7. 후보별 동작 구조
8. 품질속성 비교
9. 핵심 트레이드오프
10. 검증 기준
11. 검토 결과
12. 최종 결정

문제 상황, 결정 질문과 후보 구조는 하나의 스토리라인으로 이어져야 한다.

## 4. 문제에서 후보까지 작성하는 규칙

### 4.1 문제 상황

문제 상황은 구조 결정을 해야 하는 이유를 다음 순서로 설명한다.

1. 현재 구조와 운영 상황을 적는다.
2. 지켜야 할 요구사항과 품질속성을 이름과 요구 ID로 명시한다.
3. 신뢰 경계와 제약사항을 적는다.
4. 현재 구조로 품질속성을 동시에 만족하기 어려운 충돌이나 위험을 적는다.
5. baseline으로 고정된 범위와 이번 DP에서 바꿀 수 있는 project-custom 범위를
   구분한다.
6. 선행 또는 연관 DP가 있으면 이번 결정에 영향을 주는 내용만 적는다.
7. 마지막 문장은 이번 DP에서 선택할 구조적 갈림길로 마무리한다.

문제 상황에서 해결책이나 후보 이름을 먼저 제시하지 않는다. 문제 상황에 없는
요구사항을 결정 질문이나 후보 구조에서 새로 추가하지 않는다.

### 4.2 결정 질문

결정 질문은 문제 상황의 마지막 갈림길을 하나의 질문으로 압축한다.

- 하나의 구조적 결정 변수만 묻는다.
- 책임, 실행 위치, 신뢰 경계 또는 자원 소유권 중 무엇을 정하는지 드러낸다.
- 두 선택 방향이 대비되도록 “A할 것인가, B할 것인가?” 형식으로 작성한다.
- 후보의 세부 구현, 제품명과 평가 결과를 넣지 않는다.
- 질문에 등장하는 개념은 문제 상황에서 먼저 설명한다.

### 4.3 후보 구조 개요

후보 A와 후보 B는 결정 질문에 대한 서로 다른 두 답이어야 한다.

- 후보 A는 결정 질문의 첫 번째 선택 방향을 구체화한다.
- 후보 B는 결정 질문의 두 번째 선택 방향을 구체화한다.
- 두 후보는 같은 범위, 요구사항과 제약사항을 전제로 한다.
- 각 후보가 문제의 충돌이나 위험을 어떤 책임 배치로 다루는지 설명한다.
- 후보 이름은 구조적 차이를 드러내야 한다.
- 후보 설명에서 새로운 결정 질문을 만들지 않는다.
- 세부 동작은 후보별 동작 구조에서, 평가는 품질속성 비교에서 작성한다.

### 4.4 스토리라인 점검

1. 문제 상황만 읽어도 구조 결정이 필요한 이유를 알 수 있는가?
2. 결정 질문이 문제 상황의 충돌이나 위험에서 직접 도출되는가?
3. 후보 A와 후보 B가 결정 질문의 두 방향에 각각 직접 답하는가?
4. 두 후보가 같은 문제와 같은 범위를 다루는가?
5. 후보를 제거해도 결정 질문이 성립하고, 질문을 제거해도 문제 상황에 구조적
   갈림길이 남는가?

하나라도 아니면 앞 섹션으로 돌아가 연결을 수정한다.

## 5. 후보 구조와 동작 구조 작성 규칙

각 후보에 다음 내용을 명시한다.

- 컴포넌트 이름, 실행 위치와 책임
- 신뢰 주체, 비신뢰 주체와 신뢰 경계
- 데이터 흐름과 제어 흐름
- 결정 대상 자원의 소유 주체
- 장애 또는 종료 시 자원의 회수 주체
- 후보 간 비교가 가능한 구조적 장점과 단점

후보별 동작 구조는 데이터 흐름과 제어 흐름을 구분하고, 정상 동작뿐 아니라 장애와
종료 시 소유권 회수 흐름도 설명한다. 후보 설명, 동작 구조와 다이어그램의
컴포넌트·흐름·책임은 서로 일치해야 한다.

## 6. 후보 구조 다이어그램 작성 규칙

- 후보 A와 후보 B에 각각 하나의 PlantUML 다이어그램을 작성한다.
- 다이어그램은 plantuml 코드 블록으로 작성한다.
- 두 다이어그램은 같은 관점, 추상화 수준과 흐름 방향을 사용한다.
- 공통 컴포넌트는 같은 이름, 색상과 표기 방식을 사용한다.
- 각 컴포넌트의 실행 위치와 책임을 표시한다.
- 신뢰 주체, 비신뢰 주체와 신뢰 경계를 구분한다.
- 데이터 흐름과 제어 흐름은 다른 선 모양이나 색으로 구분하고 범례를 적는다.
- 결정 대상 자원의 소유 주체와 장애·종료 시 회수 주체를 표시한다.
- 두 후보에서 달라지는 책임, 실행 위치, 신뢰 경계 또는 자원 소유권을 시각적으로
  드러낸다.
- 결정 질문과 무관한 구현 상세나 아직 정하지 않은 하위 결정을 추가하지 않는다.
- 다이어그램의 구성 요소와 흐름은 후보 구조 및 후보별 동작 구조와 일치해야 한다.

## 7. 품질속성 평가 규칙

### 7.1 기본 원칙

1. 정확히 두 후보를 같은 문제, 범위, 요구사항과 제약사항으로 평가한다.
2. 책임, 실행 위치, 신뢰 경계 또는 자원 소유권이 다른 구조적 대안만 평가한다.
3. 문제 상황에 명시된 품질속성만 평가한다.
4. 두 후보에 같은 gate, KPI, 점수 기준, 측정 조건과 검증 방법을 적용한다.
5. 필수 조건인 gate와 후보 간 정도 차이를 나타내는 별점을 분리한다.
6. 평가 결과에 구조적 원인, KPI 값과 근거를 함께 기록한다.
7. 근거가 없거나 승인되지 않은 수치와 점수를 임의로 만들지 않는다.
8. 한 후보가 모든 품질속성에서 우월하면 실제 구조적 트레이드오프인지 다시
   확인한다.

### 7.2 평가 시작 조건

다음 조건을 모두 만족한 뒤 품질 평가를 시작한다.

- 문제 상황에 요구사항, 요구 ID, 품질속성, 충돌 또는 위험이 명시되어 있다.
- baseline과 project-custom 범위가 구분되어 있다.
- 결정 질문이 하나의 구조적 결정 변수만 묻는다.
- 후보 A와 후보 B가 질문의 두 선택 방향에 각각 답한다.
- 후보별 책임, 실행 위치, 신뢰 경계와 자원 소유권이 설명되어 있다.
- 후보별 동작 구조에 데이터 흐름과 제어 흐름이 설명되어 있다.
- 후보 설명, 동작 구조와 PlantUML 다이어그램이 서로 일치한다.
- 두 후보의 검증 방법과 운영 조건이 동일하다.

조건을 충족하지 못하면 평가 수치를 작성하지 않고 문제 상황이나 후보 구조를 먼저
보완한다.

### 7.3 평가 항목 도출

1. 문제 상황에 명시된 품질속성을 모두 추출한다.
2. 각 품질속성을 요구 ID, 상위 QAS, 충돌 또는 위험과 연결한다.
3. 필수 임계값은 gate로 분류한다.
4. gate 통과 후보 사이의 정도 차이를 나눌 수 있는 측정값은 KPI로 분류한다.
5. pass/fail로만 판단할 수 있는 항목에는 별점용 KPI를 만들지 않는다.
6. 실현 가능성은 별도 gate로 다루고 품질속성으로 분류하지 않는다.

보안성, 성능, 확장성, 변경 용이성과 자원 효율은 평가 항목을 찾기 위한 기본
목록이다. 문제 상황에 없는 기본 품질속성은 추가하지 않는다. 문제 상황에 가용성,
신뢰성 등 다른 품질속성이 있으면 평가 항목에 포함한다.

| 품질속성 | 요구 ID / 상위 QAS | 문제의 충돌 또는 위험 | 평가 방식 | KPI 또는 gate 출처 |
|---|---|---|---|---|
| 품질속성명 | 요구 ID | 문제 상황의 근거 | gate / 별점 | 문서와 항목 |

### 7.4 필수 gate 평가

gate는 후보가 선택 가능한 최소 자격을 충족하는지 판정한다.

- 보안 노출 0건, 비인가 접근 0건과 같은 필수 임계값을 pass/fail 기준으로
  작성한다.
- 각 gate에 요구 ID, 판정 기준, 측정 조건, 검증 방법과 근거 출처를 기록한다.
- 판정값은 **통과**, **실패**, **확인 필요**만 사용한다.
- gate 실패 후보는 선택 가능한 후보에서 제외하고 비교 기준선으로만 남긴다.
- gate 실패 후보에는 별점을 부여하지 않는다.
- gate가 확인 필요이면 예상 별점을 잠정적으로 작성할 수 있지만 확정 점수나 확정
  근거로 표현하지 않는다.
- 두 후보가 같은 필수 gate를 실패하면 평가를 중단하고 결정 금지 사유로 기록한다.
- 같은 품질속성을 gate와 별점으로 모두 평가할 때 gate는 최소 자격을, 별점은
  통과 후보 간 정도 차이를 판정한다.

핵심 기술이나 구조 메커니즘의 실현 가능성이 확인되지 않으면 실현 가능성 gate를
**확인 필요**로 기록한다. 이 gate가 닫히기 전에는 조건부 결정 이상으로 진행하지
않으며, 실현 가능성을 품질속성 점수에 포함하지 않는다.

| gate | 요구 ID | 판정 기준 | 측정 조건 / 검증 방법 | 후보 A | 후보 B | 근거 |
|---|---|---|---|---|---|---|
| 필수 품질 gate | 요구 ID | pass/fail 임계값 | 동일 조건 | 통과/실패/확인 필요 | 통과/실패/확인 필요 | 출처 또는 관찰 결과 |
| 실현 가능성 gate | 해당 항목 | 확인 조건 | PoC 또는 공식 문서 확인 | 통과/실패/확인 필요 | 통과/실패/확인 필요 | 확인 자료 |

### 7.5 KPI 정의

각 KPI에는 다음 내용을 기록한다.

- 연결된 품질속성과 요구 ID
- 측정 대상과 측정 목적
- 계산식 또는 집계 방식
- 단위와 값의 방향성
- 입력 데이터, 부하, 자원 할당과 장애 조건 등 측정 환경
- 최소 gate와 별점 구간
- 수치 임계값의 출처
- 실제 측정, 계산, 시뮬레이션 또는 구조적 추론 중 근거 유형

O/X로만 판단되는 항목은 KPI로 사용하지 않는다. 후보별로 환경이나 측정 방식이
다르면 값을 직접 비교하지 않는다.

KPI 임계값은 현재 과제에서 승인된 요구사항이나 상위 QAS에 정의된 gate 또는 KPI
예산에서 배분하고 출처를 기록한다. 승인된 상위 기준이 없거나 예산 배분이 승인되지
않았으면 **TBD**로 표시하고 임의 수치를 입력하지 않는다.

외부 표준과 공식 문서는 KPI 산정 방식, 기술 메커니즘 설명과 핵심 기술의 실현
가능성 확인에만 사용한다. 외부 문서를 기존 결론의 정답으로 인용하지 않는다.
기술 메커니즘 출처와 수치 임계값 출처를 구분한다.

| 품질속성 | KPI | 계산식 / 단위 | 값의 방향 | 측정 조건 | gate | 별점 구간 | 출처 |
|---|---|---|---|---|---|---|---|
| 품질속성명 | 측정 지표 | 계산식과 단위 | 클수록/작을수록 유리 | 공통 환경 | 최소 임계값 | 1~3점 구간 | 상위 QAS 항목 |

### 7.6 별점 평가

별점은 필수 gate를 통과한 후보 사이의 품질 차이에만 사용한다. 척도는 별
1~3개의 3점 척도다.

| 점수 | 의미 | 작성 조건 |
|---|---|---|
| ★★★ | 승인된 우수 구간 | KPI가 사전 정의한 우수 구간에 해당하고 근거가 있음 |
| ★★☆ | 승인된 보통 구간 | KPI가 최소 gate를 넘고 사전 정의한 중간 구간에 해당함 |
| ★☆☆ | 승인된 최소 구간 | KPI가 최소 gate를 통과하지만 허용 범위 중 가장 불리한 구간에 해당함 |

- 점수 구간은 평가 결과를 보기 전에 정의한다.
- 후보 차이를 만들기 위해 사후에 점수 구간을 조정하지 않는다.
- 두 후보의 KPI가 같은 구간이면 같은 점수를 부여한다.
- 상대적으로 더 낫다는 이유만으로 높은 점수를 부여하지 않는다.

각 별점에 다음 세 근거를 함께 기록한다.

1. 측정 또는 예상 값: KPI 값, 범위 또는 TBD
2. 구조적 원인: 책임, 실행 위치, 신뢰 경계, 흐름 또는 자원 소유권의 차이
3. 근거 자료: 시험 결과, 계산, 시뮬레이션, PoC 관찰 또는 공식 문서

예상 값은 실제 측정값처럼 표현하지 않고 가정과 산정 방법을 적는다. KPI 임계값이나
점수 구간이 TBD이면 확정 별점을 부여하지 않는다. 구조적 예상 점수는
**잠정 ★★☆**처럼 표시하고 가정, 미확인 항목과 검증 계획을 함께 적는다.
운영 환경을 대표하지 않는 PoC만으로 점수나 결정을 확정하지 않는다.

하나의 품질속성에 KPI가 여러 개이면 각각 평가한다. 상위 QAS나 사용자가 집계
방식과 가중치를 승인한 경우에만 대표 점수를 계산한다. 승인된 기준이 없으면 임의
평균·합산·가중치 또는 전체 총점을 사용하지 않는다.

| 품질속성 / KPI | 후보 A 값 | 후보 A 별점 | 후보 A 근거 | 후보 B 값 | 후보 B 별점 | 후보 B 근거 |
|---|---:|---|---|---:|---|---|
| KPI명 | 측정값/예상값/TBD | ★~★★★ 또는 잠정 | 구조적 원인과 자료 | 측정값/예상값/TBD | ★~★★★ 또는 잠정 | 구조적 원인과 자료 |

### 7.7 비교 근거의 신뢰 수준

각 평가 근거에 다음 유형 중 하나를 표시한다.

| 근거 유형 | 의미 | 평가 시 처리 |
|---|---|---|
| 운영 관찰 | 대표 운영 조건에서 측정한 결과 | 조건과 원시 결과를 연결하면 확정 근거로 사용 가능 |
| 대표 PoC | 운영 조건을 대표하도록 구성한 시험 결과 | 대표성 근거와 오차 범위를 기록 |
| 제한 PoC | 일부 조건만 재현한 관찰 결과 | 잠정 근거로만 사용 |
| 계산/시뮬레이션 | 명시한 모델과 입력으로 산출한 결과 | 가정, 계산식과 검증 범위를 기록 |
| 구조적 추론 | 구조 차이에서 예상한 영향 | 잠정 점수로만 사용하고 검증 계획을 기록 |
| 확인 필요 | 근거가 아직 없음 | 확정 평가와 확정 결정에 사용 금지 |

자료의 존재만으로 근거가 충분하다고 판단하지 않는다. 자료가 해당 KPI, 후보
구조와 측정 조건을 직접 뒷받침하는지 확인한다. PoC 결과는 관찰 근거로만 사용하며
실제 운영 환경을 대표하는지 별도로 확인한다.

## 8. 품질속성 정렬 규칙

문제 상황, 품질속성 비교와 핵심 트레이드오프에서 같은 품질속성을 추적할 수 있어야
한다.

- 문제 상황의 모든 품질속성은 gate 또는 후보 평가 표에 나타나야 한다.
- gate와 후보 평가 표의 모든 품질속성은 문제 상황의 요구사항, 충돌 또는 위험에서
  도출되어야 한다.
- 세 섹션에서 원칙적으로 같은 품질속성 이름을 사용한다.
- 요구 ID나 표현이 다르면 품질속성 비교에서 대응 관계를 기록한다.
- 실현 가능성 gate는 품질속성 정렬 대상에서 제외한다.
- 핵심 트레이드오프는 비교 결과에서 우열이나 선택 가능성을 실제로 가르는
  품질속성만 다룬다.
- 두 후보가 함께 통과한 gate와 별점이 같은 품질속성은 핵심 트레이드오프에서
  생략할 수 있다.
- 두 후보가 함께 실패한 gate는 생략하지 않고 결정 금지 사유로 기록한다.
- gate로만 평가한 품질속성은 합격 여부에 미친 영향만 설명하고 별점 우열처럼
  서술하지 않는다.
- 확인 필요, TBD와 잠정 점수는 조건부로 서술한다.
- 문제 상황에 없던 품질속성을 비교나 트레이드오프에서 추가하지 않는다.

작성 후 다음을 확인한다.

1. 문제 상황의 품질속성이 gate 또는 후보 평가 표에 모두 있는가?
2. gate와 후보 평가 표의 품질속성이 문제 상황에서 모두 도출되는가?
3. 핵심 트레이드오프의 품질속성이 비교 결과에서 모두 추적되는가?
4. 비교했지만 트레이드오프에서 생략한 속성은 공통 통과 gate이거나 별점이 같은가?
5. 공통 실패 gate, 확인 필요와 TBD가 확정 표현이나 누락으로 가려지지 않았는가?

## 9. 핵심 트레이드오프 작성 규칙

후보의 우열이나 선택 가능성을 실제로 가르는 품질속성만 기록한다. 구조적 원인과
품질속성 영향을 한 문장 안에서 연결한다.

> Host relay를 제거하면 frame 기밀성이 높아진다. 대신 EL2 코드와 검증 범위가
> 증가해 변경 용이성이 낮아진다.

다른 예는 다음과 같다.

> 특정 책임을 신뢰 영역으로 이동하면 비인가 접근 경로가 줄어 보안성이 높아진다.
> 대신 신뢰 영역의 코드와 검증 범위가 증가해 변경 용이성이 낮아진다.

“가장 좋다”, “효율적이다”, “안전하다”, “확장성이 높다”처럼 근거 없는 표현을
단독으로 사용하지 않는다. 확인 필요, TBD 또는 잠정 점수를 확정적인
트레이드오프로 서술하지 않는다.

## 10. 검증, 검토와 최종 결정

- 검증 기준은 두 후보에 동일하게 적용한다.
- 검토 결과에는 사용자 피드백을 요약한다.
- 최종 결정란은 검토 전까지 비워 둔다.
- 선행 조건을 전제로 후보를 선택하면 조건부 결정으로 기록한다.
- 다음 조건을 모두 충족해야 평가 결과를 확정 근거로 사용할 수 있다.

1. 두 후보에 같은 gate, KPI, 점수 구간과 검증 방법을 적용했다.
2. 필수 gate가 모두 확인되었다.
3. 핵심 기술의 실현 가능성이 확인되었다.
4. TBD, 확인 필요와 잠정 점수가 선택 근거에 남아 있지 않다.
5. 품질속성 우선순위가 정해졌다.
6. PoC 또는 시험 결과가 실제 운영 환경을 대표한다.
7. 선행 DP가 확정되었다.

근거와 검증 기준을 사용자가 승인한 뒤에만 최종 결정을 확정한다.

## 11. 결정 상태 규칙

상태는 다음 다섯 개만 사용한다.

| 상태 | 적용 조건 |
|---|---|
| 도출 | 결정 목적, 문제 상황과 결정 질문까지 작성됨 |
| 후보 작성 | 후보 구조가 작성됨 |
| 평가 중 | 품질속성 비교가 진행 중 |
| 조건부 결정 | 선행 조건을 전제로 후보가 선택됨 |
| 확정 | 근거와 검증 기준이 승인됨 |

새 문서는 **도출** 상태로 시작한다. 후보 평가가 작성되면 **평가 중**으로
변경한다. **확정**으로 전환하려면 10절의 일곱 조건을 모두 충족해야 한다.
조건부 결정은 해당 선행 조건의 충족을 사용자가 확인한 뒤 **확정**으로 전환한다.

## 12. 결정 금지 규칙

다음 경우에는 결정을 확정하지 않는다.

- 품질속성 우선순위가 정해지지 않았다.
- 핵심 기술의 실현 가능성이 확인되지 않았다.
- 두 후보가 같은 필수 gate를 실패했다.
- 후보 간 검증 기준이나 측정 조건이 다르다.
- 선행 DP가 미확정이다.
- PoC 결과가 실제 운영 환경을 대표하지 않는다.
- 사용자가 결정을 확인하지 않았다.

## 13. 문서 규칙

- 파일 하나에 DP 하나만 작성한다.
- 파일명에는 순서 번호를 붙인다.
- 문장은 짧게 작성한다.
- 외부 문서를 기존 결론의 정답으로 인용하지 않는다.
- KPI 근거와 실현 가능성 확인에는 외부 표준이나 공식 문서 링크를 짧게 기록할 수
  있다.
- 다른 DP 파일은 선행·연관 관계와 gate 의존성을 설명할 때만 참조한다.
- 기존 결론을 정답처럼 사용하지 않는다.
- PoC 결과는 관찰 근거로만 사용한다.
- 최종 결정란은 검토 전까지 비워 둔다.
- 결정자는 사용자다.

## 14. 작성 완료 점검

### 14.1 후보 구조 점검

1. 두 후보가 같은 문제, 범위, 요구사항과 제약사항을 다루는가?
2. 구조적 차이가 책임, 실행 위치, 신뢰 경계 또는 자원 소유권으로 설명되는가?
3. 두 후보 사이에 실제 품질속성 트레이드오프가 있는가?
4. 각 컴포넌트의 실행 위치와 책임이 명시되어 있는가?
5. 데이터 흐름과 제어 흐름, 신뢰·비신뢰 주체가 구분되어 있는가?
6. 자원 소유권과 장애·종료 시 회수 주체가 명시되어 있는가?
7. 후보별 설명과 다이어그램의 구성 요소, 흐름과 책임이 일치하는가?
8. 후보별 구조적 장점과 단점이 비교 가능한 형태로 적혀 있는가?

### 14.2 품질 평가 점검

1. 문제 상황의 모든 품질속성이 gate 또는 별점 평가에 포함되었는가?
2. 평가 항목마다 요구 ID와 상위 QAS를 추적할 수 있는가?
3. gate를 별점보다 먼저 평가했는가?
4. gate 실패 후보에 별점을 부여하지 않았는가?
5. KPI에 계산식, 단위, 방향성, 측정 조건과 출처가 있는가?
6. 승인되지 않은 임계값과 점수 구간을 TBD로 표시했는가?
7. 두 후보에 같은 KPI, 점수 구간과 검증 방법을 적용했는가?
8. 별점마다 KPI 값, 구조적 원인과 근거 자료가 있는가?
9. 예상 값과 실제 측정값, 잠정 점수와 확정 점수를 구분했는가?
10. 승인되지 않은 평균, 가중치 또는 전체 총점을 사용하지 않았는가?
11. 핵심 트레이드오프가 비교 결과와 구조적 원인에서 직접 도출되는가?
12. 공통 실패 gate, 확인 필요와 TBD가 누락되거나 확정 표현으로 가려지지 않았는가?
13. 결정 금지 조건이 남아 있으면 평가 상태를 확정하지 않았는가?
