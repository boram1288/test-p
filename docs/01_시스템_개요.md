# 시스템 개요

## 1. 시스템 정의

이 시스템은 로봇용 Custom SoC의 Linux 환경에서 보안 Workload를 pVM으로 격리해
실행하고, pVM의 수명주기와 Camera/AI HW, 도메인 간 데이터, Secure OS, 저장소와
runtime 자원을 통합 관리하는 pKVM 기반 가상화 보안 Framework다.

첫 번째 검증 대상은 Camera 도메인에서 획득한 영상을 AI 도메인으로 전달해 추론한
뒤 판단 결과만 Host Application에 제공하는 Secure Vision AI 파이프라인이다.

## 2. 목적

### 2.1 핵심 목적

Linux Host가 침해되더라도 영상 원본, AI 모델, 추론 중간 데이터, 암호 키와
보호 상태가 노출되거나 변조되지 않도록 보안 실행 환경을 제공한다. 동시에
Camera/AI HW 가속과 기존 Secure OS 기능을 활용해 로봇 제품에 필요한 실시간성과
기존 보안 자산의 호환성을 유지한다.

### 2.2 제공해야 하는 기능

- pVM 생성, 시작, 정지와 종료 및 할당 자원 회수
- Secure Camera와 Secure AI pVM의 독립적 동시 운용
- 서명, manifest, version과 freshness가 검증된 Workload의 동적 탑재
- Host와 pVM 사이의 Camera/AI HW 배타 사용과 안전한 사용 주체 전환
- pVM 간 또는 pVM/Host 간 대용량 데이터의 보호된 전달
- pVM Workload의 GlobalPlatform 호환 Secure OS 기능 호출
- pVM 수명보다 오래 유지되는 암호화 데이터의 저장과 재연결
- 장애 격리, 자원 회수, 재시작과 도메인별 CPU/memory entitlement 관리
- 단순하고 안정적인 관리 API 및 객관적인 격리/성능 검증 증거 제공

### 2.3 목표 사용 흐름

1. Host Application이 보안 파이프라인 실행을 요청한다.
2. 시스템은 검증된 Secure Camera와 Secure AI Workload를 각각의 pVM에서
   실행한다.
3. Camera/AI HW와 데이터 버퍼의 접근 권한을 필요한 도메인에만 부여하고,
   Camera 도메인의 frame을 AI 도메인으로 전달한다.
4. AI 도메인은 추론 결과만 Host에 반환하며 원본 frame, 모델과 중간 데이터는
   보호 경계 안에 유지한다.
5. 종료나 장애가 발생하면 channel, HW, TEE session, memory와 CPU 자원을
   회수하고 필요한 서비스를 재시작하거나 fail-closed 상태로 종료한다.

## 3. 신뢰 및 실행 원칙

| 경계 | 역할 | 신뢰 원칙 |
|---|---|---|
| Host Linux | 관리 process, relay, 저장 backend와 kernel mechanism 실행 | Linux kernel을 포함해 비신뢰로 본다. Host의 판단만으로 최종 보안 허가나 실제 권한 상태를 확정하지 않는다. |
| pVM | Camera/AI Workload와 guest adapter 실행 | Host와 다른 pVM으로부터 격리하며, pVM identity와 generation을 모든 권한 및 자원 수명에 결합한다. |
| pKVM/EL2 | Stage-2 기반 메모리 격리와 protected enforcement | Host 밖의 trust anchor다. 작은 TCB를 유지하고 필요한 interface와 최소 extension만 허용한다. |
| protected service pVM | 정책, buffer, HW 또는 QoS authority의 후보 실행 경계 | 고정 구성요소로 전제하지 않고 후보 구조의 책임 배치에 따라 사용한다. |
| TEE/Secure OS | key, session과 기존 보안 기능 실행 | trust anchor로 유지하며 pVM caller identity와 request integrity가 종단 간 보존되어야 한다. |
| Camera/AI HW와 S2MPU | 영상/추론 처리와 DMA 접근 통제 | 외부 물리 자원이지만 할당, 회수, reset, zeroize와 접근 제어 계약은 Framework가 통합한다. |

Framework의 논리적 시스템 경계와 신뢰 경계는 같지 않다. 비신뢰 Host에서 실행되는
컴포넌트도 Framework의 일부일 수 있지만, 보호 자원의 최종 허가와 집행 근거는
보호 경계에서 확인되어야 한다.

## 4. 제약사항

### 4.1 고정 기술 및 호환성 제약

1. **Linux native**
   Android Framework나 Android system service에 의존하지 않고 Yocto/Ubuntu
   계열 Linux에서 동작해야 한다.

2. **Host 비신뢰**
   Host Application뿐 아니라 Linux kernel이 침해된 상황도 가정한다. 보안
   설계는 Host의 memory, metadata, policy와 lifecycle 상태를 신뢰해서는 안 된다.

3. **pKVM 기반 격리**
   기 포팅된 pKVM과 Stage-2 격리를 전제로 한다. pKVM 자체 포팅과 일반 core 개발은
   범위 밖이지만, Framework interface, hypercall/ABI와 자원별 enforcement 연동은
   범위 안이다.

4. **작은 EL2 TCB**
   EL2에 기능을 무제한 추가하지 않는다. EL2 extension이 필요한 후보는 platform
   owner 확인과 feasibility 검증을 통과해야 한다.

5. **GlobalPlatform 호환**
   기존 GlobalPlatform TEE interface, TrustZone Secure OS 기능과 SMC 경로를
   유지해야 한다. 기존 Secure OS의 pVM 연동을 위한 adapter와 제한적 수정은
   허용하지만 신규 Secure OS를 처음부터 개발하지 않는다.

6. **현재 2-domain topology**
   현재 설계와 검증은 Camera→AI의 두 도메인 파이프라인을 기준으로 한다.
   일반화된 N-domain graph, fan-in/fan-out과 미래 제품군 topology는 범위 밖이다.

7. **Camera/AI HW 배타 사용**
   단일 Context HW에는 한 시점에 하나의 주체만 접근할 수 있다. Host와 pVM의
   논리적 동시 사용은 고속 시분할로 제공하며 실제 병렬 접근은 허용하지 않는다.

8. **안전한 HW 전환**
   사용 주체 전환은 권한 회수, 진행 작업 drain, reset, 잔류 데이터 zeroize,
   S2MPU 갱신과 새 주체 권한 부여가 완료된 뒤에만 성립한다. 권한 중첩이나
   비할당 도메인의 DMA 접근을 허용하지 않는다.

9. **검증된 Workload만 실행**
   Workload image, manifest, signature와 version 검증이 실패하거나 freshness를
   확인할 수 없으면 실행하지 않는다. 동적 탑재가 Framework core의 수정으로
   이어져서는 안 된다.

10. **현재 저장 baseline**
    보호 데이터는 pVM 수명과 분리해 암호문으로 유지하되 현재 baseline에서는
    RPMB를 사용하지 않는다. 이 전제의 변경은 별도 결정이 필요하다.

### 4.2 Embedded 자원 및 저장 제약

이 시스템은 서버가 아니라 Embedded SoC 환경을 대상으로 한다. CPU, memory,
전력과 저장장치는 모두 제한된 자원이며 필요에 따라 무한히 확장할 수 없다.

| 영역 | 자원 제약 | 설계 영향 |
|---|---|---|
| REE/Host | Embedded Linux가 사용하는 UFS의 용량은 유한하다. | 암호문, 로그와 임시 데이터에 quota, retention, 공간 부족 처리와 회수 정책이 필요하다. 저장 공간 증가를 전제로 문제를 회피하지 않는다. |
| TEE/Secure OS | TEE 영역에는 직접 접근하거나 소유하는 영구 저장장치가 없고, 할당된 memory도 작다. | 대용량 파일이나 장기 보관 데이터를 TEE memory에 상주시킬 수 없다. TEE에는 실행 중 필요한 최소 key/state만 유지하고 bulk data는 외부 암호문으로 관리한다. |

TEE에서 사용하는 암호 키를 영속화할 때는 다음 경로를 사용한다.

1. Secure OS는 TEE 내부의 암호 키를 암호화하거나 봉인해 ciphertext key blob을
   만든다.
2. Host의 **Secure OS Adapter**는 ciphertext key blob을 전달받아 REE의 UFS에
   기록한다.
3. 복원할 때 Secure OS Adapter는 UFS의 ciphertext key blob을 읽어 TEE로
   전달하고, Secure OS가 TEE 내부에서 복호화하거나 봉인을 해제한다.

평문 암호 키는 REE, Secure OS Adapter 또는 UFS에 노출하지 않는다. Host가 저장
파일이나 metadata를 관찰하거나 변조할 수 있으므로 ciphertext의 무결성, Workload
identity binding, version/freshness와 rollback 대응도 보호 경계에서 검증해야 한다.

### 4.3 품질 및 운영 제약

| 구분 | 제약 |
|---|---|
| 보안 | Host 침해에도 pVM memory와 보호 데이터가 노출되지 않아야 한다. 미검증 Workload 실행, 비인가 HW/DMA 접근과 비인가 TEE 호출은 허용하지 않는다. |
| 성능 | Secure Vision AI의 실시간 frame 처리를 유지해야 한다. data path의 불필요한 payload copy를 피하고, 시작/전달/HW 전환/추론의 end-to-end 지연을 같은 trace에서 측정한다. |
| 확장성 | 신규 보안 Workload와 Secure OS 구현을 안정된 package/API/adapter 경계로 수용해야 하며 Framework core 변경을 최소화한다. |
| 가용성 | 하나의 pVM 장애가 Host나 다른 pVM으로 전파되지 않아야 한다. 장애 후 모든 권한과 자원의 실제 상태를 회수/대조하고 재시작 또는 fail-closed 종료해야 한다. |
| 자원 효율 | CPU, memory, 전력과 protected resource 사용량은 제품 탑재 가능한 범위여야 하며, overload가 다른 도메인의 격리와 가용성을 훼손해서는 안 된다. |
| 검증 가능성 | 격리, 권한 전환, 데이터 전달, 장애 회수와 성능 결과를 동일 identity/generation/trace로 객관적으로 확인할 수 있어야 한다. |

성능, 복구 시간, 자원 효율의 일부 수치 목표는 아직 승인된 예산이 아니다. 확정되지
않은 수치를 설계 제약이나 후보 평가의 확정 기준으로 사용하지 않고 TBD 또는
확인 필요로 유지한다.

### 4.4 구현 범위 제약

과제 범위에 포함되는 항목은 다음과 같다.

- Host 측 Framework process와 pVM/HW 제어 kernel driver
- pVM의 measured bootstrap과 buffer/TEE/storage/HW guest adapter
- pVM lifecycle, pipeline orchestration, policy, recovery와 resource/QoS 관리
- Camera/AI HW 할당/회수/격리 및 native driver 배치 계약
- pVM 간 data/control channel과 buffer ownership/mapping/reclaim 계약
- 기존 Secure OS의 pVM 연동, caller binding과 TEE session lifecycle
- 암호화 persistent storage와 Workload identity/metadata binding
- 필요한 경우의 최소 EL2 interface/extension 후보와 feasibility 검증

다음 항목은 직접 구현 범위에서 제외한다.

- Linux 또는 guest OS 제품 자체
- Host Application과 Camera/AI Workload의 업무 로직
- pKVM 자체 포팅과 일반 Hypervisor core 개발
- 신규 Secure OS와 TA 제품 기능의 처음부터의 개발
- Camera/AI HW, S2MPU와 저장 매체의 물리 설계
- 특정 guest OS/RTOS/unikernel 제품 선택
- 미래 HW class의 범용 SoC abstraction
- fleet OTA, fleet SLA/MTBF와 상용 운영 체계
- 일반화된 N-domain pipeline

## 5. 완료 상태

시스템은 다음 조건을 함께 만족할 때 목적을 달성한 것으로 본다.

- Host가 침해되어도 보호 자산과 pVM 간 격리가 유지된다.
- Secure Camera와 Secure AI 파이프라인이 Camera/AI HW를 사용해 동작한다.
- 보호 데이터가 승인된 도메인과 Secure OS 경로에서만 처리된다.
- 신규 Workload가 Framework core 변경 없이 검증/탑재된다.
- 장애와 종료 뒤 권한, session, buffer, HW, CPU와 memory가 누수 없이 회수된다.
- 결과를 기능 시험, 공격/장애 주입과 end-to-end 계측으로 재현할 수 있다.
