# Decision Point 작성 규칙

## DP 선정 규칙

1. 아키텍처 구조를 바꾸는 결정만 DP로 선정한다.
2. 구현 라이브러리나 제품 선택은 DP로 만들지 않는다.
3. 후보 구조는 정확히 두 개다.
4. 후보별 책임과 실행 위치가 달라야 한다.
5. 후보별 신뢰 경계가 달라야 한다.
6. 품질속성 간 트레이드오프가 명확해야 한다.
7. 하나의 후보가 모든 품질속성에서 우월하면 DP로 보지 않는다.
8. 과제 범위 안에서 결정 가능한 항목만 다룬다.
9. 다른 DP의 세부 구현은 하위 결정으로 둔다.
10. 검증 방법만 다른 경우에는 별도 DP로 만들지 않는다.

## DP 작성 규칙

각 DP는 다음 순서로 작성합니다.

1. 상태
2. 결정 목적
3. 문제 상황 (선행/연관 DP, baseline과 project-custom 범위 명시)
4. 결정 질문
5. 후보 구조
6. 후보별 구조 다이어그램
7. 후보별 동작 구조
8. 품질속성 비교
9. 핵심 트레이드오프
10. 검증 기준
11. 검토 결과 (사용자 피드백 요약)
12. 최종 결정 (선택된 후보와 근거)

`문제 상황 → 결정 질문 → 후보 구조`는 하나의 스토리라인으로 이어져야 합니다.

### 1. 문제 상황

문제 상황은 구조 결정을 해야 하는 이유를 설명합니다.

1. 먼저 현재 구조와 운영 상황을 적습니다.
2. 다음으로 지켜야 할 요구사항과 품질속성을 이름과 요구 ID로 명시하고, 신뢰 경계와 제약사항을 적습니다.
3. 현재 구조로 품질속성을 동시에 만족하기 어려운 충돌이나 위험을 적습니다.
4. baseline으로 고정된 범위와 이번 DP에서 바꿀 수 있는 project-custom 범위를 구분합니다.
5. 선행/연관 DP가 있으면 결정에 영향을 주는 내용만 적습니다.
6. 마지막 문장은 이번 DP에서 선택해야 할 구조적 갈림길로 마무리합니다.

해결책이나 후보 이름을 먼저 제시하지 않습니다.
문제 상황에 없는 요구사항을 뒤의 결정 질문이나 후보 구조에서 새로 추가하지 않습니다.

### 2. 결정 질문

결정 질문은 문제 상황의 마지막 갈림길을 하나의 질문으로 압축합니다.

- 하나의 구조적 결정 변수만 묻습니다.
- 책임, 실행 위치, 신뢰 경계 또는 자원 소유권 중 무엇을 정하는지 드러냅니다.
- 두 선택 방향이 대비되도록 `A할 것인가, B할 것인가?` 형식으로 작성합니다.
- 후보의 세부 구현, 제품명, 평가 결과를 질문에 넣지 않습니다.
- 질문에 등장하는 개념은 문제 상황에서 먼저 설명합니다.

### 3. 후보 구조

후보 구조는 결정 질문에 대한 서로 다른 두 답이어야 합니다.

- 후보 A는 질문의 첫 번째 선택 방향을 구체화합니다.
- 후보 B는 질문의 두 번째 선택 방향을 구체화합니다.
- 두 후보는 문제 상황에서 정한 동일한 범위, 요구사항과 제약사항을 전제로 합니다.
- 각 후보가 문제 상황의 충돌이나 위험을 어떤 책임 배치로 다루는지 설명합니다.
- 후보 설명에서 새로운 결정 질문을 만들지 않습니다.
- 후보별 세부 동작과 평가는 뒤의 `후보별 동작 구조`와 `품질속성 비교`에서 작성합니다.

### 스토리라인 점검

작성 후 다음 질문을 순서대로 확인합니다.

1. 문제 상황만 읽어도 왜 지금 구조 결정이 필요한지 알 수 있는가?
2. 결정 질문이 문제 상황의 충돌이나 위험에서 직접 도출되는가?
3. 후보 A와 B가 결정 질문에 각각 직접 답하는가?
4. 두 후보가 같은 문제와 같은 범위를 다루는가?
5. 후보를 제거해도 결정 질문이 성립하고, 질문을 제거해도 문제 상황에 구조적 갈림길이 남는가?

하나라도 아니면 앞 섹션으로 돌아가 연결을 수정합니다.

## 후보 구조 작성 규칙

- 후보 이름은 구조적 차이를 드러내야 한다.
- 각 컴포넌트의 실행 위치를 명시한다.
- 각 컴포넌트의 책임을 명시한다.
- 데이터 흐름과 제어 흐름을 구분한다.
- 신뢰 주체와 비신뢰 주체를 구분한다.
- 자원 소유권과 회수 주체를 명시한다.
- 후보 A와 후보 B를 각각 설명하는 구조 다이어그램을 반드시 포함한다.

## 후보 구조 다이어그램 작성 규칙

- 후보 A와 후보 B에 각각 하나의 PlantUML 다이어그램을 작성한다.
- 다이어그램은 `plantuml` 코드 블록으로 작성한다.
- 두 다이어그램은 같은 관점, 추상화 수준과 흐름 방향을 사용한다.
- 공통 컴포넌트는 두 다이어그램에서 같은 이름, 색상과 표기 방식을 사용한다.
- 각 컴포넌트의 실행 위치와 책임을 표시한다.
- 신뢰 주체, 비신뢰 주체와 신뢰 경계를 구분한다.
- 데이터 흐름과 제어 흐름은 서로 다른 선 모양이나 색으로 구분하고 범례를 적는다.
- 결정 대상 자원의 소유 주체와 장애·종료 시 회수 주체를 표시한다.
- 두 후보에서 달라지는 책임, 실행 위치, 신뢰 경계 또는 자원 소유권이 시각적으로 드러나야 한다.
- 결정 질문과 무관한 구현 상세나 아직 정하지 않은 하위 결정을 다이어그램에 추가하지 않는다.
- 다이어그램의 구성 요소와 흐름은 후보 구조 및 후보별 동작 구조의 설명과 일치해야 한다.

## 품질속성 비교 규칙

모든 후보를 동일한 기준으로 평가합니다.

별점 전에 상위 QAS와 제약사항의 필수 gate를 평가합니다.

- gate는 보안 노출 0건, 비인가 접근 0건처럼 pass/fail로 판정합니다.
- gate 실패 후보는 선택 가능한 후보가 아니라 비교 기준선으로만 남깁니다.
- gate 실패 후보에는 별점을 부여하지 않습니다.
- 핵심 기술의 실현 가능성이 확인되지 않으면 `확인 필요`로 표시합니다.
- 실현 가능성 gate가 닫히기 전에는 조건부 결정 이상으로 진행하지 않습니다.
- 두 후보가 같은 필수 gate에 실패하면 결정을 중단하고 결정 금지 사유로 기록합니다.
- 동일한 품질속성을 gate와 별점으로 모두 다루면 gate는 최소 자격을, 별점은 그 기준을 통과한 후보 간 정도 차이를 평가합니다.
- gate가 `확인 필요`이면 구조 예상 별점을 잠정 부여할 수 있지만, 평가 근거와 트레이드오프를 확정적으로 서술하지 않습니다.

다음 품질속성은 비교 항목을 고를 때 사용하는 기본 목록입니다.

- 보안성
- 성능
- 확장성
- 변경 용이성
- 자원 효율

문제 상황에 없는 기본 품질속성은 제외합니다.
문제 상황에 가용성, 신뢰성 등 다른 품질속성이 있으면 비교 항목에 추가합니다.
필수 임계값은 gate로 평가합니다.
gate를 통과한 후보 간 정도 차이를 나눌 KPI가 있으면 같은 품질속성을 별점으로도 평가합니다.
pass/fail로만 판정할 수 있으면 별점을 추가하지 않습니다.
실현 가능성 gate는 기술의 확인 상태이며 품질속성이 아닙니다.

KPI 임계값은 `docs/03_qa_quality_scenarios.md` 등 상위 QAS의 gate/KPI에서 배분하고 출처를 기록합니다.
상위 기준이 없거나 예산 배분이 승인되지 않았으면 `TBD`로 표시하고 임의 수치를 넣지 않습니다.
외부 표준과 공식 문서는 KPI 산정 근거와 기술 실현 가능성 확인에만 사용합니다.
기술 메커니즘을 설명하는 출처와 수치 임계값을 뒷받침하는 출처를 구분합니다.
O/X로 판단되는 평가는 KPI가 될 수 없습니다.
별 1~3개의 3점 척도로 평가하고, 각 점수의 기준과 근거를 짧게 기록합니다.
별점 기준은 두 후보에 동일하게 적용합니다.
평가 이유를 짧게 기록합니다.

## 품질속성 정렬 규칙

문제 상황, 품질속성 비교와 핵심 트레이드오프의 품질속성은 서로 정렬되어야 합니다.
정렬은 세 섹션에서 문구를 기계적으로 반복하는 것이 아니라, 같은 의미의 품질속성을 문제에서 평가로, 평가에서 선택 근거로 추적하는 것입니다.

- 문제 상황에서 언급한 모든 품질속성은 품질속성 비교의 gate 또는 후보 평가 표에 나타나야 합니다.
- 품질속성 비교의 모든 품질속성은 문제 상황의 요구사항, 충돌 또는 위험에서 근거를 찾아야 합니다.
- 세 섹션에서는 원칙적으로 같은 품질속성 이름을 사용합니다.
- 요구 ID나 표현을 다르게 써야 하면 품질속성 비교에서 대응 관계를 명시합니다.
- 실현 가능성 gate는 품질속성 정렬 대상에서 제외합니다.
- 핵심 트레이드오프는 비교한 품질속성 중 후보의 우열이나 선택 가능성을 실제로 가르는 속성만 설명합니다.
- 두 후보가 함께 통과한 gate와 별점이 같은 품질속성은 핵심 트레이드오프에서 생략할 수 있습니다.
- 두 후보가 함께 실패한 gate는 생략하지 않고 결정 금지 사유로 기록합니다.
- gate로만 평가한 품질속성은 합격 여부나 선택 가능성에 미친 영향만 설명하고, 별점 우열처럼 서술하지 않습니다.
- `확인 필요` 또는 `TBD`인 속성은 평가 근거와 핵심 트레이드오프에서 조건부로 서술합니다.
- 문제 상황에 없던 품질속성을 비교나 핵심 트레이드오프에서 새로 추가하지 않습니다.

작성 후 다음을 확인합니다.

1. 문제 상황의 품질속성이 gate 또는 후보 평가 표에 모두 있는가?
2. gate와 후보 평가 표의 품질속성이 문제 상황에서 모두 도출되는가?
3. 핵심 트레이드오프의 품질속성이 비교 결과에서 모두 추적되는가?
4. 비교했지만 트레이드오프에서 생략한 속성은 공통 통과 gate이거나 별점이 같은가?
5. 공통 실패 gate, `확인 필요`와 `TBD`가 확정 표현이나 누락으로 가려지지 않았는가?

## 트레이드오프 작성 규칙

다음 형식으로 작성합니다.

> Host relay를 제거하면 frame 기밀성이 높아진다. 대신 EL2 코드와 검증 범위가 증가해 변경 용이성이 낮아진다.

다음 표현은 피합니다.

- 가장 좋다.
- 효율적이다.
- 안전하다.
- 확장성이 높다.

근거 없는 평가이기 때문입니다.

대신 구조적 원인과 품질속성에 미치는 영향을 함께 명시합니다.

## 결정 상태 규칙

상태는 다음 다섯 개만 사용합니다.

- 도출: 결정 목적, 문제 상황, 결정 질문까지 작성됨
- 후보 작성: 후보 구조가 작성됨
- 평가 중: 품질속성 비교가 진행 중
- 조건부 결정: 선행 조건을 전제로 후보가 선택됨
- 확정: 근거와 검증 기준이 승인됨

새 문서는 모두 도출 상태로 시작합니다.
후보 평가가 작성되면 상태를 `평가 중`으로 변경합니다.
조건부 결정은 선행 조건 충족을 사용자가 확인하면 확정으로 전환합니다.

## 결정 금지 규칙

다음 경우에는 확정하지 않습니다.

- 품질속성 우선순위가 정해지지 않은 경우
- 핵심 기술의 실현 가능성이 확인되지 않은 경우
- 두 후보가 같은 필수 gate에 실패한 경우
- 후보 간 검증 기준이 다른 경우
- 선행 DP가 미확정인 경우
- PoC 결과가 실제 운영 환경을 대표하지 않는 경우
- 사용자가 결정을 확인하지 않은 경우

## 문서 규칙

- 파일 하나에 DP 하나만 작성합니다.
- 파일명에는 순서 번호를 붙입니다.
- 문장은 짧게 작성합니다.
- 외부 문서를 기존 결론의 정답으로 인용하지 않습니다.
- KPI 근거와 실현 가능성 확인에는 외부 표준/공식 문서 링크를 짧게 기록할 수 있습니다.
- 다른 DP 파일은 선행/연관 관계와 gate 의존성을 설명할 때만 참조합니다.
- 기존 결론을 정답처럼 사용하지 않습니다.
- PoC 결과는 관찰 근거로만 사용합니다.
- 최종 결정란은 검토 전까지 비워 둡니다.
- 결정자는 사용자입니다.
