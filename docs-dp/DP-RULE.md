# Decision Point 작성 규칙

## DP 선정 규칙

1. 아키텍처 구조를 바꾸는 결정만 DP로 선정한다.
2. 구현 라이브러리나 제품 선택은 DP로 만들지 않는다.
3. 후보 구조가 두 개어야 한다.
4. 후보별 책임과 실행 위치가 달라야 한다.
5. 후보별 신뢰 경계가 달라야 한다.
6. 품질속성 간 트레이드오프가 명확해야 한다.
7. 하나의 후보가 모든 품질속성에서 우월하면 DP로 보지 않는다.
8. 과제 범위 안에서 결정 가능한 항목만 다룬다.
9. 다른 DP의 세부 구현은 하위 결정으로 둔다.
10. 검증 방법만 다른 경우에는 별도 DP로 만들지 않는다.

## DP 작성 규칙

각 DP는 다음 순서로 작성합니다.

1. 상태
2. 결정 목적
3. 문제 상황
4. 결정 질문
5. 후보 구조
6. 후보별 동작 구조
7. 품질속성 비교
8. 핵심 트레이드오프
9. 검증 기준
10. 검토 결과
11. 최종 결정

## 후보 구조 작성 규칙

- 후보 이름은 구조적 차이를 드러내야 한다.
- 각 컴포넌트의 실행 위치를 명시한다.
- 각 컴포넌트의 책임을 명시한다.
- 데이터 흐름과 제어 흐름을 구분한다.
- 신뢰 주체와 비신뢰 주체를 구분한다.
- 자원 소유권과 회수 주체를 명시한다.
- 필요하면 간단한 구조도를 포함한다.

## 품질속성 비교 규칙

모든 후보를 동일한 기준으로 평가합니다.

- 보안성
- 성능
- 확장성
- 변경 용이성
- 자원 효율

관련 없는 속성은 제외합니다.

평가는 웹조사를 통해서 객관적인 KPI를 선정하고, KPI선정 근거를 기록한다. (짧게)
O/X로 판단되는 평가는 KPI가 될 수 없다.
별 3개로 평가하고, 별 1, 2, 3개의 기준을 선정하고, 근거를 기록한다. (짧게)
평가 이유를 짧게 기록합니다.

## 트레이드오프 작성 규칙

다음 형식으로 작성합니다.

> 후보 A는 보안성을 높인다. 대신 구현 복잡도가 증가한다.

다음 표현은 피합니다.

- 가장 좋다.
- 효율적이다.
- 안전하다.
- 확장성이 높다.

근거 없는 평가이기 때문입니다.

대신 조건을 명시합니다.

> Host relay를 제거하면 frame 기밀성이 높아진다. 대신 EL2 코드와 검증 범위가 증가한다.

## 결정 상태 규칙

상태는 다음 다섯 개만 사용합니다.

- 도출: 결정 질문만 정의됨
- 후보 작성: 후보 구조가 작성됨
- 평가 중: 품질속성 비교가 진행 중
- 조건부 결정: 선행 조건을 전제로 후보가 선택됨
- 확정: 근거와 검증 기준이 승인됨

새 문서는 모두 도출 상태로 시작합니다.

## 결정 금지 규칙

다음 경우에는 확정하지 않습니다.

- 품질속성 우선순위가 정해지지 않은 경우
- 핵심 기술의 실현 가능성이 확인되지 않은 경우
- 후보 간 검증 기준이 다른 경우
- 선행 DP가 미확정인 경우
- PoC 결과가 실제 운영 환경을 대표하지 않는 경우
- 사용자가 결정을 확인하지 않은 경우

## 문서 규칙

- 파일 하나에 DP 하나만 작성합니다.
- 파일명에는 순서 번호를 붙입니다.
- 문장은 짧게 작성합니다.
- 기존 문서를 인용하지 않습니다.
- 기존 결론을 정답처럼 사용하지 않습니다.
- PoC 결과는 관찰 근거로만 사용합니다.
- 최종 결정란은 검토 전까지 비워 둡니다.
- 결정자는 사용자입니다.
